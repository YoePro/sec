Primitive Types

This page is the lookup reference for Sec's primitive scalar types. It documents the language-level type surface first and the current compiler/core implementation second. A missing implementation does not remove a member that the language or compiler-known registry requires.

Reference rule: exact language semantics and compiler-known members take precedence over today's implementation gaps. The Implementation field records what is currently available in the compiler and sec/core; it is not a second language specification.

Reference Status

Each member entry separates its contract from implementation coverage. This is important while Sec 0.1 is still being implemented.

Normative Core-declared Partial Required, not complete
  • Normative means the language or compiler-known registry requires the surface.
  • Core-declared means a matching declaration currently exists in sec/core.
  • Partial means the declaration exists but its behavior or lowering is incomplete.
  • Required, not complete means the contract exists even though implementation work remains.

Allocation and fallibility are documented independently. An infallible operation may still have a compile-time validity requirement or a panic/runtime-check contract. Such behavior is stated separately under Failure behavior.

bool

Normative Core-declared

bool is Sec's logical scalar type and has exactly two values: false and true. Conditions require bool; numeric values do not implicitly become booleans.

Valuesfalse, true
Defaultfalse
Literaltrue / false
Numeric conversionExplicit, infallible
let enabled: bool := true
let ready := bool(count) // false for zero, true otherwise

byte

Normative Partial

byte is Sec's byte-oriented unsigned scalar. It is intended for raw binary data, buffers, protocols and FFI. Equal storage width does not make byte semantically identical to uint8 for every purpose.

Exact Decimal Types

Normative Backend incomplete

decimal and decimal128 are exact base-10 numeric types. Unsuffixed fractional and exponent literals default to decimal when no stronger context selects another type. The explicit decimal-family suffix is m.

TypeCanonical representationDefaultLiteral selectionImplementation
decimal{ int64 coefficient, int32 scale }0Default fractional type / mFrontend substantial; arithmetic/lowering incomplete
decimal128{ int128 coefficient, int32 scale }0Context / m familyLanguage type; implementation partial
 
let amount := 3.14
let explicit := 3.14m
let wide: decimal128 := 8m

Decimal literals are interpreted from their exact source spelling. They must not be converted through binary floating point first.

Implementation Status

Primitive type identity is substantially implemented, but this reference intentionally exposes several language/core contracts that are ahead of current code generation.

  • int128, int256, uint128, uint256 and decimal128 are real Sec language types, not future syntax.
  • Target-sized int/uint semantics are canonical, while legacy backend paths still contain width-mapping debt.
  • Compiler-known Ptr, SizeOf and universal ToString() belong to the reference even when a core helper body is absent.
  • int.ToString(), uint.ToString() and decimal.ToString() currently contain TODO bodies.
  • rune is a Unicode scalar type, but its current core classification/case-conversion implementation is incomplete; case conversion is currently stubbed.
  • char.ToLower() and char.ToUpper() currently cover ASCII only.
  • Materializing ToString() operations may require an allocation context; Sec must not silently fall back to an unrelated heap.

This status section is intentionally separate from the member contracts. As implementation progresses, the status can change without changing the documented API unless the normative rulebooks themselves are revised.
