# Correction 21 — infinite-loop exit detection counts breaks belonging to nested loops

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/control-flow/flowcontrol_for.md`
- Related rulebook: `rules/control-flow/flowcontrol_while.md`
- `for` document revision: **2.0**
- Created: `2026-08-16`
- Last updated: `2026-08-16`
- Reviewed rulebook baseline: `56be75d`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2.0 states that `break` exits the nearest enclosing loop and that an
infinite `for {}` has no normal fallthrough path unless a reachable `break`
can exit **that loop**.

Current Sema has correct loop-frame tracking for actual break-flow state, but
the independent return/fallthrough helper `blockContainsBreak()` does not
preserve loop-target identity. It recursively searches nested `for` and `while`
bodies and reports any nested break as though it could exit the outer loop.

Consequently an outer infinite loop can be classified as continuing merely
because an inner loop contains a valid break targeting only the inner loop.

The same helper is used for `while true`, so the defect crosses both loop
families.

---

## Normative requirements

`rules/control-flow/flowcontrol_for.md` revision 2.0 states:

> `break` exits the nearest enclosing loop.

and:

> An infinite loop with no reachable `break` is non-continuing for return-path
> analysis.

The "reachable break" in the second statement means a break whose resolved
target is that infinite loop.

For example:

```sec
for {
    for {
        break
    }
}
```

The inner `break` exits only the inner loop.

The outer loop still has no exit and is therefore non-continuing.

The same target rule applies to:

```sec
while true {
    for {
        break
    }
}
```

and the reverse nesting.

# Bug — `blockContainsBreak()` ignores the nearest-loop boundary

## Affected code

`internal/sema/analyzer.go`

Infinite-loop return analysis currently uses:

```go
case *ast.ForStatement:
    return len(stmt.Bindings) == 0 &&
        stmt.Iterable == nil &&
        !blockContainsBreak(stmt.Body)

case *ast.WhileStatement:
    return isBoolLiteral(stmt.Condition, true) &&
        !blockContainsBreak(stmt.Body)
```

The helper then recursively descends into nested loops:

```go
func statementContainsBreak(stmt ast.Statement) bool {
    switch stmt := stmt.(type) {
    case *ast.BreakStatement:
        return true

    case *ast.IfStatement:
        return blockContainsBreak(stmt.Consequence) ||
            blockContainsBreak(stmt.Alternative)

    case *ast.ForStatement:
        return blockContainsBreak(stmt.Body)

    case *ast.WhileStatement:
        return blockContainsBreak(stmt.Body)

    ...
    }
}
```

The `ForStatement` and `WhileStatement` recursion is wrong for determining
whether the **current** loop has an exiting break.

Once the traversal enters another loop, an unlabeled `break` inside that loop
targets the nested loop, not the outer one.

---

# Observable incorrect behavior

Conceptually:

```sec
fn RunForever() int {
    for {
        for {
            break
        }
    }
}
```

The outer `for {}` is infinite.

Execution is:

```text
enter outer iteration
    enter inner loop
        break inner loop
    end outer body
repeat outer iteration
```

There is no path from the outer loop to the function end.

Therefore `RunForever()` satisfies return-path analysis as a non-continuing
function body and does not require a `return int`.

Current helper logic sees the nested `break`, reports:

```text
blockContainsBreak(outerBody) == true
```

and therefore refuses to classify the outer `for {}` as non-continuing.

That can incorrectly produce:

```text
function RunForever must return int
```

despite the function having no reachable fallthrough path.

---

# Related false reachability

The same target-insensitive helper participates in
`statementDefinitelyReturns()` / `statementCanFallThrough()` decisions.

Therefore code after the outer infinite loop may fail to receive the canonical
unreachable-code diagnostic merely because a nested loop contains `break`.

Example:

```sec
fn Test() void {
    for {
        while true {
            break
        }
    }

    Work()
}
```

`Work()` is unreachable.

A break that only exits the nested `while` must not make the outer `for`
fall through.

---

# Switch boundary

Sec deliberately differs from C-like switch semantics:

```text
switch does not create a break target
```

Therefore this is valid target propagation:

```sec
for {
    switch value {
        case 1 {
            break
        }
    }
}
```

The `break` inside the switch targets the surrounding loop.

So the correction must **not** simply stop recursion at every nested control-flow
construct.

Target-aware traversal must distinguish:

- nested `if` / ordinary block:
  - continue searching for a break targeting the current loop;
- nested `switch`:
  - continue searching, because switch creates no Sec break target;
- nested `for`:
  - stop searching for unlabeled breaks belonging to the outer loop;
- nested `while`:
  - stop searching for unlabeled breaks belonging to the outer loop;
- future labeled control flow:
  - resolve by explicit target identity if/when the language adds it.

# Existing loop-frame analysis already has the correct concept

`analyzeForStatement()` and `analyzeWhileStatement()` use loop break frames:

```go
frame := a.pushLoopBreakFrame()
...
breakFrame := a.popLoopBreakFrame(frame)
```

Actual `break` analysis records state against the active nearest-loop frame.

That architecture already knows which loop owns a break.

The defect exists because later structural helpers throw away that resolved
target and perform a fresh target-insensitive AST search.

The durable fix should reuse resolved control-flow facts rather than infer loop
exit behavior again from syntax.

---

# Required correction

## 1. Make break-exit detection target-aware

For determining whether a specific loop can exit through `break`, use either:

- the loop's resolved break frame / CFG fact; or
- a traversal carrying the target loop identity and stopping at nested loop
  boundaries.

Do not use a generic "contains any break anywhere below this AST node" query.

## 2. Preserve switch semantics

Continue through nested `switch` bodies because Sec switch creates no break
target.

A `break` directly inside a switch nested in the loop still exits the loop.

## 3. Preserve conditional reachability

A syntactically present break is not sufficient if its branch is statically
unreachable.

Where Sema has already proven branch reachability, loop-exit facts should consume
that semantic result rather than raw syntax.

This correction's proven defect is nested-loop target identity; complete
reachability should use the same resolved CFG path.

## 4. Use one canonical loop-exit fact

Before lowering, each loop should expose something conceptually equivalent to:

```text
LoopCanExitNormally
LoopHasReachableBreakToSelf
LoopIsNonContinuing
```

computed from resolved CFG/control-flow edges.

Consumers should include:

- function return-path analysis;
- post-loop reachability;
- definite assignment;
- ownership-state merging;
- cleanup planning;
- Semantic IR;
- diagnostics/LSP.

Do not let each consumer perform its own AST search.

## 5. Apply the fix to `while true`

Because `statementDefinitelyReturns()` uses the same helper for both loop kinds,
the correction must cover `while true` at the same time.

# Governance reconciliation

The current `frontend.for-loops-v2` entry lists as implemented:

```text
finite-loop zero-iteration preservation and infinite-loop non-continuation
without reachable break
```

and its required tests include:

```text
infinite for block without reachable break is non-continuing
reachable break restores a continuing post-loop path
```

That wording is too broad at baseline `c515862`.

The implementation handles direct/current-loop breaks, but nested-loop breaks can
be mistaken for outer-loop exits in return/fallthrough analysis.

The `frontend.while-statements-v2` required matrix already explicitly asks for:

```text
nested break does not exit outer loop
```

but the shared structural helper contradicts that rule for
`statementDefinitelyReturns()`.

Add the shared limitation to both governance entries.

Do not downgrade:

- nearest-loop validation during actual break statement analysis;
- loop break-frame state capture;
- direct break continuation merging;
- break inside switch nested in a loop targeting the loop;
- backend branch target handling where already implemented.

The defect is specifically the secondary structural return/fallthrough query.

# Required regression tests

## Infinite `for`

1. outer `for {}` with no break remains non-continuing;
2. direct break in outer `for {}` creates a post-loop path;
3. break inside `if` in outer loop creates a post-loop path when reachable;
4. break inside `switch` nested directly in outer loop targets outer loop;
5. break inside nested `for` does **not** create an outer-loop exit;
6. break inside nested `while` does **not** create an outer-loop exit;
7. several nested loop levels preserve nearest-loop targeting;
8. unreachable nested/current-loop break does not create a false exit when
   reachability is proven.

## `while true`

9. direct break in `while true` creates a post-loop path;
10. break inside nested `for` does not exit outer `while true`;
11. break inside nested `while` does not exit outer `while true`;
12. break inside switch nested in `while true` exits the while.

## Return/reachability

13. non-void function ending in outer infinite `for` plus nested inner break does
    not require a return;
14. statement after such an outer infinite loop is diagnosed unreachable;
15. non-void function ending in `while true` plus nested inner-loop break has the
    same behavior;
16. direct outer-loop break still requires normal post-loop return analysis.

## Cross-layer

17. resolved loop-exit fact refers to a specific loop identity;
18. Semantic IR/CFG preserves nearest-loop break target;
19. return-path analysis consumes resolved loop-exit facts rather than generic
    recursive AST break search;
20. switch remains transparent to loop break targeting.

---

# Applied 2026-08-23

- Infinite-loop return analysis now searches only for reachable breaks that
  target the current `for` or `while true` loop.
- Nested loop bodies form target boundaries, while `switch`, `select`, `unsafe`,
  and ordinary conditional blocks remain transparent.
- Constant-unreachable conditional branches no longer create false loop exits.
- Repository governance and focused Sema tests record the corrected behavior.
