# Correction 13 — register `bit[N]` value ranges are truncated to 64 bits

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/declarations/registers.md`
- Document revision: **2**
- Created: `2026-08-13`
- Last updated: `2026-08-13`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2 permits positive compile-time-known register widths and `bit[N]`
field widths without imposing a 64-bit semantic limit. The implementation-status
ledger currently marks `bit`/`bit[N]` fields and constant assignment range
checking against field width as implemented.

Current Sema constructs the semantic value range of raw `bit[N]` fields through
`uint64`. For every width `N >= 64`, the maximum representable field value is
therefore capped at `2^64 - 1`.

This makes the semantic field value domain disagree with the declared field
width.

---

## Normative requirements

`rules/declarations/registers.md` revision 2 states:

- `register[N]` uses a positive compile-time constant width;
- `bit[N]` contributes exactly `N` bits;
- register width is exact and compile-time known;
- field values and conversions must respect the declared bit width;
- fixed-width register semantics are not defined as "up to 64 bits".

The language already has wider integer types such as `uint128` and `uint256`, so
a register field wider than 64 bits has meaningful source-level values.

For an unsigned raw `bit[N]` field, the numeric bit-pattern domain is:

```text
0 .. 2^N - 1
```

where numeric access/conversion is applicable.

---

# Bug — `registerFieldType()` caps every field of width >= 64 at `uint64`

## Affected code

`internal/sema/analyzer.go`

Current implementation:

```go
func (a *Analyzer) registerFieldType(field *ast.RegisterField) Type {
    if field.Width == 1 && field.Unit == "" {
        return Type{Name: "bool", Kind: BoolType}
    }

    max := uint64(0)
    if field.Width >= 64 {
        max = ^uint64(0)
    } else if field.Width > 0 {
        max = 1<<uint(field.Width) - 1
    }

    typ := unsignedType("uint", max)
    ...
}
```

For:

```text
bit[64]
bit[65]
bit[128]
bit[256]
```

the semantic maximum is always:

```text
18446744073709551615
```

instead of:

```text
2^64  - 1
2^65  - 1
2^128 - 1
2^256 - 1
```

respectively.

`unsignedType()` then copies this `uint64` maximum into the arbitrary-precision
semantic fields:

```go
MaxInteger: new(big.Int).SetUint64(max)
```

so later range checking has already lost the declared width.

---

# Example

```sec
type Wide register[128] {
    Value: bit[128],
}
```

The field occupies all 128 declared bits and should have the raw unsigned
bit-pattern domain:

```text
0 .. 2^128 - 1
```

A compile-time value such as:

```text
2^100
```

fits the declared field width.

Current Sema models `Value` with:

```text
MaxInteger = 2^64 - 1
```

and the ordinary assignment path invokes:

```go
checkIntegerExpressionRange(targetType, stmt.Value)
```

against that incorrect maximum.

A valid value above `2^64 - 1` can therefore be rejected even though it fits
`bit[128]`.

---

# Why this is not merely an unimplemented-wide-backend limitation

The defect occurs in frontend semantic representation before lowering.

A backend may later lack support for a particular physical width and report an
explicit unsupported-lowering diagnostic.

It must not cause Sema to redefine the source field's value domain as 64 bits.

The frontend must preserve the exact declared width independently of backend
capabilities.

---

# Required correction

## 1. Compute field bounds with arbitrary-precision integers

For raw `bit[N]`, construct:

```text
min = 0
max = (1 << N) - 1
```

using `math/big.Int`.

Do not route the semantic maximum through `uint64`.

The implementation can use the existing arbitrary-precision `MinInteger` and
`MaxInteger` fields already present on `sema.Type`.

## 2. Do not label every raw bit field as target-sized `uint`

The current representation:

```go
unsignedType("uint", max)
```

also gives a raw register field the source type name `uint`, even when its bit
width is unrelated to the target-sized `uint` width.

This becomes increasingly misleading for:

```text
bit[12]
bit[65]
bit[128]
```

The semantic representation should preserve that this is a register-field
bit-pattern value with an exact declared width.

Possible implementations include:

- an explicit register-bit-field semantic type/fact; or
- an integer-like semantic type carrying exact register-field width separately
  from ordinary source `uint` identity.

Do not make target-sized `uint` identity the source of truth for register-field
width.

## 3. Preserve existing 1-bit source semantics deliberately

The current implementation maps plain `bit` to `bool`.

If that is the intended canonical source-access type, retain it explicitly and
test it.

If the intended rule is instead an exact one-bit unsigned bit-pattern semantic
type, that decision belongs in the register rulebook and must be implemented
consistently.

This correction does not change the existing one-bit rule; it addresses width
truncation for wider `bit[N]`.

## 4. Audit every field-width-dependent check

Verify at least:

- compile-time literal assignment;
- compound assignment where permitted;
- explicit integer/register conversions;
- bit-backed enum interoperability;
- masks and extraction/insertion once lowering is implemented;
- formatter/LSP type display;
- constant propagation;
- Semantic IR facts.

All such logic must use the exact declared field width, not host or target
`uint64` limits.

## 5. Keep backend capability separate

If a maintained backend cannot lower a 128-bit or larger register field, it
must:

1. preserve the correct frontend semantic width; and
2. issue an explicit unsupported-lowering diagnostic.

It must not silently narrow to 64 bits.

---

# Governance reconciliation

The current `frontend.registers` entry lists as implemented:

```text
bit and bit[N] fields with positive integer-literal widths and exact total-width
validation
```

and:

```text
unit annotations and constant assignment range checks against field width
```

These statements are too broad for field widths above 64 bits.

Suggested narrowing:

```text
bit and bit[N] declaration/layout widths are retained exactly; raw field value
range representation and assignment range checks are currently correct only
through 64 bits
```

until this correction is implemented.

The already documented remaining items for:

- nested registers;
- general compile-time width expressions;
- access semantics;
- integer-to-register checked conversion;
- extraction/insertion lowering;

remain separate.

---

# Required regression tests

Add tests covering at least:

1. `bit[2]` accepts 0 through 3 and rejects 4;
2. `bit[63]` accepts its exact maximum;
3. `bit[64]` accepts `2^64 - 1`;
4. `bit[64]` rejects `2^64`;
5. `bit[65]` accepts `2^64`;
6. `bit[65]` accepts `2^65 - 1`;
7. `bit[65]` rejects `2^65`;
8. `bit[128]` accepts a value such as `2^100`;
9. `bit[128]` accepts `2^128 - 1`;
10. `bit[128]` rejects `2^128`;
11. exact total register-width validation remains independent from field value
    range checking;
12. frontend retains exact width even when a backend later rejects lowering;
13. field-width semantics do not depend on host or target-sized `uint`;
14. bit-backed enum field semantics remain unchanged.

## Applied

Applied on 2026-08-23 to `internal/sema/analyzer.go`, focused Sema tests, and
`implementation-status.yaml`. Raw bit fields now retain exact `bit[N]` identity,
`BitWidth`, and arbitrary-precision bounds. Verified with:

```text
go test ./internal/sema -run 'TestWideRegisterField|TestRegister' -count=1
```
