The Sec compiler is implemented as a sequence of explicit compilation stages.

Each stage must have a clearly defined input, output and responsibility.

A later stage must not compensate for missing validation in an earlier stage.

The compiler pipeline is:

1. source loading
2. lexical analysis
3. parsing
4. syntax validation
5. symbol collection
6. name resolution
7. type resolution
8. semantic analysis
9. ownership and borrow analysis
10. control-flow analysis
11. compile-time evaluation
12. target and platform validation
13. Sec semantic IR generation
14. MLIR lowering and optimization
15. LLVM IR lowering
16. target code generation
17. object generation
18. linking

Compilation must stop before lowering when semantic errors remain.

## Project initialization

Project initialization is not a compilation stage.

It creates the project structure and default compiler configuration consumed by
later pipeline stages.

The canonical project, manifest, target and variant model is defined in
`rules/projects/projects.txt`. This section records the current implementation status
only.

The command is:

```text
sec init [path] [--name <name>] [--target <os-arch>] [--profile <profile>]
```

Current behavior:

* creates the project directory when needed
* creates `cmd/<target-name>/`
* creates `bin/`
* creates `.sec/`
* creates `internal/`
* creates `cmd/<target-name>/main.sec` when it does not already exist
* creates `.sec/sec.toml`
* does not overwrite an existing `.sec/sec.toml`
* treats a compatible existing `.sec/sec.toml` as an idempotent no-op
* rejects creation of a nested `.sec/sec.toml` below an existing Sec project

The generated `cmd/<target-name>/main.sec` is the smallest valid executable entry point:

```sec
module main

fn main() int {
    return 0
}
```

When the project name is not provided:

* interactive use may prompt for a project name
* non-interactive use uses the directory base name

When the target is not provided, `sec init` selects the current host target from
the compiler target registry.

The initial configuration file currently has this shape:

```toml
[project]
name = "my project"
uuid = "generated-project-uuid"
imports = []

[build]
backend = "mlir"
profile = "server"
diagnostics = "default"

[profile.server]
optimization = "none"
debug = "line"
strip = false

[variant.linux-amd64]
os = "linux"
arch = "amd64"
llvm_triple = "x86_64-pc-linux-gnu"

[target.my-project]
kind = "command"
source = "cmd/my-project"
artifact = "my-project"
variants = ["linux-amd64"]
output = "bin/my-project/linux-amd64/server/my-project"
```

`[project]` contains project identity.

`[build]` contains project-wide compiler defaults.

`[profile.<name>]` contains reusable build-profile defaults.

`[variant.<name>]` contains the selected Sec platform identity. The current
implementation also stores `llvm_triple` as a derived backend detail for the
active LLVM/MLIR path.

`[target.<name>]` contains the logical build product and its selected variants.

## Source loading

Source loading is responsible for:

* locating source files
* resolving modules
* validating module paths
* validating file encoding
* normalizing source locations
* loading target configuration
* loading build configuration

Source loading must preserve:

* file path
* byte offset
* line number
* column number
* module identity

All later diagnostics must be able to refer to the original source location.

## Lexical analysis

The lexer converts source text into tokens.

The lexer is responsible for:

* identifiers
* keywords
* literals
* operators
* punctuation
* comments
* annotations
* source positions

The lexer must not perform semantic analysis.

The lexer may validate lexical correctness, including:

* malformed numeric literals
* malformed string literals
* invalid escape sequences
* unterminated comments
* unsupported characters

The lexer must preserve sufficient literal information for later type resolution.

## Parsing

The parser converts tokens into an abstract syntax tree.

The parser is responsible for:

* declarations
* statements
* expressions
* type syntax
* annotations
* generic syntax
* control-flow syntax
* unsafe syntax

The parser must preserve source ranges for every node.

The parser must not perform:

* ownership analysis
* borrow analysis
* target layout validation
* LLVM-specific decisions
* implicit type conversion decisions

The parser may perform limited syntax recovery to report multiple errors.

Recovered nodes must be marked invalid and must not be lowered.

## Syntax validation

Syntax validation verifies structural language rules that are easier to express after parsing.

Examples include:

* invalid modifier combinations
* duplicate modifiers
* invalid declaration placement
* missing required declaration components
* illegal statement placement
* invalid use of extern syntax
* invalid use of unsafe syntax

Syntax validation must not depend on target machine details.

## Symbol collection

Symbol collection registers declarations before full semantic analysis.

The compiler must collect symbols for:

* modules
* imports
* types
* functions
* methods
* interfaces
* constants
* variables where applicable
* enum members
* struct fields
* generic parameters

Symbol collection must detect:

* duplicate declarations
* duplicate fields
* duplicate parameters
* invalid shadowing where forbidden
* conflicting method declarations
* conflicting imports

Symbol collection should allow forward references where the language permits them.

## Name resolution

Name resolution binds identifiers to declarations.

Name resolution is responsible for:

* local scopes
* module scopes
* imported symbols
* type names
* function names
* method names
* field names
* enum members
* generic parameters

Every resolved identifier must reference a unique symbol.

Ambiguous names must be rejected.

Unresolved names must not reach later stages.

Name resolution must enforce visibility rules.

## Type resolution

Type resolution converts type syntax into canonical compiler types.

Type resolution is responsible for:

* built-in types
* named types
* distinct types
* generic types
* function types
* reference types
* RawPtr types
* arrays
* slices
* structs
* enums
* unions
* interfaces
* Result and Option types
* unit types
* register types

Equivalent types must share a canonical internal representation where appropriate.

Named semantic types must remain distinguishable from their base types.

Type resolution must not erase:

* ownership semantics
* mutability
* unit information
* enum representation
* layout annotations
* unsafe function status
* extern calling convention

## Semantic analysis

Semantic analysis validates language meaning.

Semantic analysis is responsible for:

* expression typing
* assignment validity
* mutability
* function call validation
* return validation
* operator resolution
* method resolution
* interface conformance
* generic constraint validation
* explicit and implicit conversion rules
* annotation validation
* unsafe-context validation
* Result handling
* exhaustiveness validation
* compile-time contract validation where possible

Semantic analysis must reject invalid programs before IR generation.

Semantic analysis must not depend on LLVM behavior.

## Ownership and borrow analysis

Ownership and borrow analysis follows semantic type resolution.

It is responsible for:

* ownership establishment
* copy and move classification
* moved-value detection
* destruction responsibility
* borrow creation
* borrow conflicts
* reference lifetime validation
* reference escape validation
* mutable alias validation
* ownership transfer across calls
* ownership transfer across returns
* defer capture validation

Ownership analysis rules are defined in ownership.md.

Reference rules are defined in references.md.

Borrow rules are defined in `rules/memory/borrowing.md`.

Unsafe rules are defined in `rules/memory/unsafe.md`.

Unsafe code does not bypass ownership analysis for normal Sec values.

## Control-flow analysis

Control-flow analysis builds and validates the function control-flow graph.

It is responsible for:

* reachable blocks
* unreachable code
* definite assignment
* all-path return validation
* break validation
* continue validation
* loop exit analysis
* switch exhaustiveness
* match exhaustiveness
* divergent expressions
* defer execution paths
* termination analysis where required

The compiler should report unreachable code according to the language warning rules.

Control-flow analysis must complete before lowering.

## Compile-time evaluation

Compile-time evaluation resolves expressions that are required to be known during compilation.

Examples include:

* constant expressions
* enum values
* array lengths
* ranges
* annotations
* register widths
* memory addresses
* platform conditions
* type contracts
* layout parameters
* build conditions

Compile-time evaluation must use Sec language semantics.

It must not rely on host-language integer overflow, floating-point behavior or pointer width.

Target-dependent expressions must be evaluated using the selected target configuration.

## Target and platform validation

Target validation occurs after general semantic validation and before lowering.

It is responsible for:

* target architecture support
* operating-system support
* pointer width
* integer width assumptions
* ABI support
* calling conventions
* struct layout requirements
* register layout
* address validity
* syscall availability
* inline assembly availability
* platform-specific imports
* platform-specific source selection

Target validation must not change general Sec semantics.

A program valid for one target may be rejected for another target when it uses unavailable platform features.

## Sec semantic IR

The compiler must generate a Sec-specific semantic intermediate representation before MLIR lowering.

The semantic IR must represent validated language semantics directly.

It should contain:

* canonical types
* typed values
* typed instructions
* explicit control flow
* ownership operations
* copy operations
* move operations
* borrow operations where still required
* destruction operations
* defer operations
* Result operations
* checked conversions
* unsafe operations
* extern calls
* source locations

The semantic IR must not contain unresolved syntax.

The semantic IR must not depend directly on LLVM types or instructions.

Every semantic IR operation must represent a program that has already passed semantic validation.

Semantic IR generation may simplify syntax but must preserve observable language behavior.

Examples of syntax removed during semantic IR generation include:

* syntactic sugar
* implicit return forms
* range-loop syntax
* switch syntax
* match syntax
* method-call syntax
* compound assignment syntax

Lowering must preserve source mapping for diagnostics and debugging.

## MLIR lowering

MLIR is the primary lowering and optimization layer between Sec semantic IR and LLVM IR.

MLIR lowering is responsible for converting validated Sec operations into lower-level representations.

MLIR may be used for:

* structured control-flow lowering
* data-flow analysis
* ownership lowering
* destruction placement
* bounds-check elimination
* scalar optimization
* loop optimization
* unit erasure after validation
* register-operation lowering
* target-independent optimization
* target-specific dialect lowering

MLIR must not define Sec language semantics.

An optimization is valid only when it preserves Sec observable behavior.

MLIR passes must not introduce:

* hidden heap allocation
* hidden ownership transfer
* changed destruction order
* removed required checks
* altered integer overflow behavior
* altered error propagation
* altered defer behavior

Ownership information may be removed only after all ownership-dependent operations have been lowered safely.

Unit information may be erased only after all unit validation and conversions are complete.

## LLVM IR lowering

LLVM IR lowering converts validated and optimized MLIR into LLVM IR.

LLVM lowering is responsible for:

* LLVM type selection
* LLVM control flow
* calling convention lowering
* target data layout
* stack allocation
* explicit heap allocator calls
* function attributes
* platform intrinsics
* inline assembly emission
* debug metadata
* object-level symbol names

LLVM lowering must not perform language-level validation.

LLVM lowering must not decide:

* whether a conversion is legal
* whether a borrow is valid
* whether ownership may move
* whether null is permitted
* whether unsafe is required
* whether a match is exhaustive
* whether a type contract is satisfied

These decisions must already exist in validated semantic IR or MLIR.

## Target code generation

Target code generation converts LLVM IR into target machine code.

It is responsible for:

* instruction selection
* register allocation
* machine-level optimization
* target object format
* relocation generation
* debug information
* target CPU features

Target code generation must use the selected target rather than the compiler host.

Cross-compilation must not depend on executing target binaries.

## Object generation

The compiler must support producing object files without linking.

Object generation must preserve:

* exported symbols
* imported symbols
* section information
* relocation information
* target ABI
* debug metadata when requested

The object format is determined by the selected target.

## Linking

Linking is a separate final stage.

The linker stage is responsible for:

* combining object files
* resolving symbols
* including required platform objects
* including explicitly required libraries
* applying the selected entry point
* producing the final binary or library

The compiler must not link unused libraries by default.

The compiler should avoid including unused Sec functions and data where possible.

Linker behavior must be controlled by the selected build target and profile.

## Compiler modes

Commands may stop the pipeline at different stages.

Expected run commands include:

sec init
sec lex
sec parse
sec check
sec sema
sec emit-ir
sec emit-mlir
sec emit-llvm
sec build
sec run
sec test

sec init creates a new Sec project structure and `.sec/sec.toml`.

sec lex stops after lexical analysis.

sec parse stops after parsing and syntax validation.

sec check performs all frontend validation without target code generation.

sec sema performs semantic, ownership, borrow and control-flow analysis.

The inspection commands report a final `summary: N errors, M warnings` on
stderr, so frontend failures and warnings can be counted without manually
counting diagnostic lines.

sec emit-ir emits Sec semantic IR.

sec emit-mlir emits MLIR.

sec emit-llvm emits LLVM IR.

sec build produces the requested binary, library or object.

sec run builds and executes a supported hosted target.

sec test builds and executes test declarations.

Exact command availability may be implemented incrementally.

Current MLIR implementation note:

* `sec emit-mlir <file.sec> -o <file.mlir|->` emits LLVM-dialect MLIR.
* `sec emit-mlir` supports `--target <os-arch>`, `--mlir-bin <path>` and
  `--verify`.
* For emit commands, `-o -` writes generated text to stdout. Other output
  filenames beginning with `-` are rejected.
* `sec build --pipeline mlir` orchestrates MLIR out-of-process:
  Sec source -> AST/sema -> MLIR text -> `mlir-opt` verification ->
  `mlir-translate --mlir-to-llvmir` -> LLVM IR -> `clang`.
* Without `-o`, build output uses the input file's base name in the current
  working directory. For example, building `testdata/ir/test_complex1.sec`
  produces `test_complex1`. With both keep flags, the retained intermediates
  are `test_complex1.mlir` and `test_complex1.ll` beside the executable.
* MLIR tools are resolved from `--mlir-bin`, then `SEC_MLIR_BIN`, then
  `~/mlir/llvm-project/build/bin`, then `PATH`.
* The first MLIR backend intentionally uses LLVM-dialect MLIR directly.
  A Sec-specific MLIR dialect is a later step.
* The current MLIR backend supports a small executable subset:
  `module main`, function declarations, `return`, `if`/`else`, `else if`,
  integer and float range `for` loops, infinite `for` loops, `while` loops, `break`,
  `continue`, local `let` declarations, local identifier assignments, identifier loads,
  direct function calls, bool/integer/unsigned integer/float literals and basic
  arithmetic/comparison/logical operators, and integer/bool subject switches
  with value cases and optional default. Concrete non-generic structs are
  supported for literals, local storage, parameters, returns, field reads and
  field assignment through stored local structs.
  Fieldless enums are supported for constants, local storage, assignment,
  parameters, returns, equality, inequality, explicit integer conversions and
  integer/bool-style value switches.
* A concrete struct lowers to an LLVM-dialect literal struct type whose elements
  follow declaration order. Sema materializes every omitted field before
  lowering. The current MLIR builder uses a transient `llvm.mlir.undef`
  aggregate followed by `llvm.insertvalue` for every field; that intermediate is
  never exposed or read as a Sec value. Field reads use `llvm.extractvalue`.
  Nested structs are represented inline and require no runtime support.
* Struct field assignment uses value semantics: nested aggregates are rebuilt
  inline with `llvm.insertvalue` from the changed leaf back to the stored root.
* Named primitive types erase to their underlying LLVM representation after
  semantic checking. This includes string-backed names such as
  `type TokenType string`.
* A stored or returned string lowers to
  `!llvm.struct<(!llvm.ptr, i64)>`. String parameters retain the existing
  split pointer/length ABI. Struct string fields and string return values are
  packed and unpacked inline with `llvm.insertvalue`/`llvm.extractvalue`, with
  no runtime dependency.
* Fixed-size array fields in structs lower recursively to
  `!llvm.array<N x element-type>`. This includes nested fixed-size arrays and
  requires no runtime support.
* Fixed-size arrays whose elements already have a direct LLVM representation
  support literals, local storage, parameters, returns, compile-time `.len`,
  indexed reads and indexed writes inline. Runtime indexes emit explicit
  signed/unsigned bounds checks and trap on failure before
  `llvm.getelementptr` addresses an element. Nested arrays use nested
  `!llvm.array` types. Arrays of strings and slice views remain separate
  lowering steps.
* Fixed-size array iteration evaluates its iterable once and lowers to an
  unsigned index loop over `0..<N`. One value binding and two index/value
  bindings are supported, including discard bindings, `break` and `continue`.
* The first struct lowering step does not yet support generic structs, struct
  spread, assignment through parameters or references, reference/slice
  fields, methods or properties.
* Enums lower directly to their underlying integer type while retaining enum
  identity as lowering metadata. Explicit values, automatic continuation,
  integer constant expressions, `iota`, aliases and nested enum namespaces are
  resolved at compile time and require no runtime support. Enum `match`
  lowering remains a later step.
* Hardware-mapped `enum Name: bit[N]` declarations lower to the exact `iN`
  integer representation with unsigned casts and no runtime support. Parser,
  AST and sema preserve the bit width, validate all values and conversions, and
  allow the enum to define the width and semantic type of a register field.
  Register load/store and mask/shift lowering remain part of the existing
  register-backend work.
* The first MLIR switch step evaluates its subject once and emits ordered test,
  case, default and continuation blocks. Comma-separated case values are joined
  with boolean OR. Subjectless switch, ranges, relational cases, fallthrough and
  non-integer/non-bool subjects remain later steps.
* `while` lowering emits condition, body and end blocks. `continue` branches to
  the condition block. `break` branches to the end block.
* Integer range `for` lowering supports explicit signed steps, including
  descending loops such as `for i in 3..-1 step -1`.
* Float range `for` lowering supports explicit float steps such as
  `for f in 0.0g..5.0g step 0.5g`.
* `in` with finite integer or float ranges lowers to lower-bound and
  upper-bound comparisons. Inclusive ranges use `<=` for the upper bound;
  exclusive ranges use `<`.
* Numeric literals are emitted using the surrounding expression context where
  possible, for example `uint_value > 15` emits `15` with the unsigned value's
  MLIR integer width.
* Immutable top-level integer and boolean bindings with compile-time constant
  initializers are folded into their use sites. They require neither global
  storage nor runtime initialization.
* Executable MLIR emission starts from functions in the main source file and
  follows resolved calls into imported modules. Unreferenced imported
  functions are not lowered into the executable module.
* Unsigned integer values keep signedness metadata during MLIR lowering. The
  backend emits unsigned integer predicates and operations where LLVM requires
  signedness-specific opcodes, for example `ugt`, `udiv`, `urem` and `lshr`.
* Logical `&&` and `||` lower to short-circuit control flow, not eager
  `llvm.and`/`llvm.or` operations.
  The temporary result slot is initialized with the left operand before
  branching, and only overwritten when the right operand is evaluated.
* Untyped integer literals in MLIR are emitted using the smallest currently
  supported integer width that can represent the value: signed literals prefer
  `i32`, then `i64`, then `i128`, then `i256`; unsigned literals prefer `i64`,
  then `i128`, then `i256`.
* The O0 MLIR backend hoists stack allocation (`llvm.alloca`) to the function
  prologue. Loop bodies must not allocate fresh stack slots per iteration.
* `decimal` lowers to `!llvm.struct<(i64, i32)>`; `decimal128` lowers to
  `!llvm.struct<(i128, i32)>`. Field zero is the signed base-10 coefficient and
  field one is the `i32` scale.
* Decimal literals, local storage, parameters, returns and explicit integer
  conversions lower fully inline. Aggregate construction and access use
  `llvm.insertvalue` and `llvm.extractvalue`. Decimal-to-integer conversion
  removes scale with an inline signed-division loop and truncates toward zero.
  These paths do not require a runtime library.
* `int128`, `int256`, `uint128` and `uint256` lower to `i128` and `i256`.
  Their MLIR path supports literals, storage, parameters, returns, casts,
  arithmetic, bitwise operations, shifts and signed/unsigned lowering.
* Decimal arithmetic and comparison lowering remain future work.
* String literals lower to immutable byte arrays plus a separate runtime
  length. The MLIR backend does not append an implicit C nul terminator.
  C-compatible nul-terminated strings must be produced by an explicit later
  conversion or FFI lowering rule.
* `RawPtr[T]` lowers to `!llvm.ptr`. The pointee type remains frontend-verified
  metadata at this lowering level, and explicit pointer-to-integer conversion
  uses `llvm.ptrtoint`.
* On `linux-amd64`, `fmt.Println(string)` resolves through `io.Println` and the
  target-specific `platform.linux.amd64._rawSyscall` overload. The MLIR backend
  lowers `string.ptr` to `!llvm.ptr`, `string.len` to `i64`, reference
  parameters to `!llvm.ptr`, and explicit pointer-to-`uint` conversion with
  `llvm.ptrtoint`.
* The Linux AMD64 platform dependency is imported as the directory package
  `platform/linux/amd64`. All `.sec` files directly in that package, including
  `raw_syscall.sec` and `syscall_numbers.sec`, participate in analysis and
  lowering. Source code uses the default short qualifier `amd64` or an explicit
  import alias; resolution rewrites it to the full module identity before
  semantic analysis and code generation.
* Raw syscall overloads are selected by source-level arity and receive distinct
  MLIR symbols. The inline assembly lowers to `llvm.inline_asm
  has_side_effects` with the Linux AMD64 register constraints. For `write`, the
  syscall number is supplied once in `rax`, followed by `rdi`, `rsi` and `rdx`;
  the result is returned from `rax`, while `rcx`, `r11` and `memory` are
  clobbered.
* The syscall and `Println` path is fully inline and does not call libc or a Sec
  runtime library. Target-specific syscall implementations for architectures
  other than Linux AMD64 require their own platform source and lowering tests.

## Diagnostics

The canonical diagnostic, severity, mentor-analysis and localization model is
defined in `rules/tooling/diagnostics.txt`.

Each pipeline stage must emit diagnostics using the shared diagnostic system.

Diagnostics must contain:

* severity
* message
* source file
* source range
* diagnostic code where defined
* related source locations where applicable
* explanatory notes where applicable

Later stages must not emit misleading diagnostics for errors caused by invalid earlier-stage input.

Current implementation status:

* parser, semantic, project and build diagnostics are still mostly emitted as
  English text without stable diagnostic IDs
* mandatory parser and semantic failures already stop lowering/build work
* several reachability checks already emit errors, matching the canonical
  diagnostics rule that proven unreachable/dead code is invalid
* the central diagnostic registry, localization, `sec explain`, diagnostic
  configuration and structured machine-readable diagnostic output remain future
  work

Compiler errors must be distinguished from user program errors.

An internal compiler error must report:

* pipeline stage
* current declaration or function
* source location when available
* compiler version
* target
* reproducible internal error information

## Error recovery

Frontend stages may recover from user errors to report additional independent diagnostics.

Recovery must not allow invalid nodes to reach semantic IR generation.

Lowering stages should assume validated input.

A lowering failure caused by semantically invalid input is a compiler defect.

## Pass invariants

Every pipeline pass must document its required input invariants and produced output invariants.

Passes must verify critical invariants in debug compiler builds.

Examples include:

* all identifiers resolved before semantic analysis completes
* all expressions typed before ownership analysis
* all ownership transfers explicit before semantic IR emission
* no unresolved generic parameters before monomorphized lowering
* no invalid control-flow edges before MLIR lowering
* no Sec-only types before final LLVM lowering
* no unsupported target operation before object generation

## Compiler architecture

Pipeline stages should be represented by separate packages or modules where practical.

Frontend stages must not import backend implementation details.

LLVM-specific code must not be used by:

* lexer
* parser
* symbol collection
* name resolution
* general semantic analysis
* ownership analysis
* borrow analysis
* control-flow analysis

Target-independent semantic code must be reusable across all supported targets.

Platform-specific behavior must be isolated behind explicit target and platform interfaces.

## Design rule

The frontend defines what a valid Sec program means.

Semantic IR records that meaning.

MLIR lowers and optimizes that meaning.

LLVM generates machine code for that meaning.

No backend stage may redefine the language.

## Test compilation mode

The pipeline represents compilation mode explicitly, with at least
`Production` and `Test`; test mode is not a late boolean source-inclusion hack.
A `TestCompilationPlan` retains selected `*_test.sec` and `tests/` provenance,
test-only dependency direction, compiler-known testing context, stable
`TestIdentity`, selected static harness roots, and execution metadata.

Test selection occurs early enough that constrained target artifacts need only
link selected tests and their reachable dependencies. Later stages must not
reconstruct test identity from generated function or linker names. `sec test`
uses the same pipeline and plan model as compiler/LSP test views defined by
`rules/tooling/testing.md`.
