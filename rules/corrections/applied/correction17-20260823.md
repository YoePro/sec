# Correction 17 — union constructor payload validation and ownership transfer are incomplete

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/declarations/unions.md`
- Document revision: **2**
- Created: `2026-08-13`
- Last updated: `2026-08-13`

## Classification

Implementation bugs.

These are not language-rule changes.

Revision 2 requires union payload construction to obey the ordinary
initialization, representability, copy, and move rules of the declared payload
type.

Current Sema performs basic payload arity and type compatibility checks, but two
important parts of the value semantics are missing:

1. integer literal representability/range checking is not applied to union
   payload construction; and
2. unnamed payload construction does not transfer ownership from move-only
   source values into the new union value.

Both occur in functionality currently described broadly as implemented in the
root governance ledger.

---

# Bug 1 — union payload integer literals bypass representability/range checks

## Normative requirement

`rules/declarations/unions.md` revision 2 states:

> A single-payload variant requires exactly one value assignable to its declared
> payload type.

For struct-like payloads:

> Field values must be assignable to their declared field types.

"Assignable" uses the ordinary type and value rules of the destination type. A
literal that is outside the representable range of its declared integer type is
not a valid payload merely because its broad numeric kind is compatible.

For example:

```sec
type Small union {
    Value(uint8)
}
```

must reject:

```sec
let value := Small.Value(300)
```

because `300` is not representable as `uint8`.

Likewise:

```sec
type Small union {
    Value {
        n: uint8
    }
}
```

must reject:

```sec
let value := Small.Value {
    n: 300
}
```

---

## Affected code — unnamed payload construction

`internal/sema/analyzer.go`

Both expected-type construction:

```go
payloadType := *variant.Payload
valueType, _ := a.inferExpressionWithExpected(
    expr.Arguments[0],
    payloadType,
)

if valueType.Kind != InvalidType &&
   !canInitialize(payloadType, valueType, expr.Arguments[0]) {
    ...
}
```

and qualified constructor analysis:

```go
payloadType := *concreteVariant.Payload
valueType, _ := a.inferExpressionWithExpected(
    expr.Arguments[0],
    payloadType,
)

if valueType.Kind != InvalidType &&
   !canInitialize(payloadType, valueType, expr.Arguments[0]) {
    ...
}
```

stop after `canInitialize()`.

For numeric literals, `canInitialize()` intentionally handles broad
initialization compatibility and may return true while a later representability
check is still required.

Ordinary typed bindings and struct fields separately call:

```go
checkIntegerExpressionRange(...)
```

after type compatibility.

Union payload constructors do not.

---

## Affected code — struct-like payload fields

`checkUnionPayloadFields()` performs:

```go
valueType, _ :=
    a.inferExpressionWithExpected(
        field.Value,
        expectedField.Type,
    )

if valueType.Kind != InvalidType &&
   !canInitialize(
        expectedField.Type,
        valueType,
        field.Value,
    ) {
    ...
}
```

but no:

```go
a.checkIntegerExpressionRange(
    expectedField.Type,
    field.Value,
)
```

or equivalent semantic range validation.

This is inconsistent with ordinary struct literal fields, where Sema explicitly
does:

```go
if valueType.Kind != InvalidType {
    a.checkIntegerExpressionRange(
        fieldType,
        field.Value,
    )
}
```

after the ordinary initialization check.

---

## Required correction for Bug 1

Union payload construction must use the same canonical destination-value
validation pipeline as every other typed initialization.

Do not duplicate ad hoc integer logic per feature.

At minimum, for every supplied union payload value:

1. infer with the declared payload type as expected type;
2. validate ordinary initialization compatibility;
3. validate integer representability/range when the target semantics require it;
4. validate constrained named-type requirements where applicable;
5. preserve the same compile-time diagnostic behavior as ordinary typed
   initialization.

Apply this consistently to:

- single unnamed payload constructors;
- struct-like payload fields;
- generic union payloads after concrete substitution;
- default-synthesized payload fields where relevant.

A future shared helper such as:

```text
validateTypedInitialization(target, expression)
```

would reduce drift between:

- let initialization;
- assignment;
- struct fields;
- union payloads;
- function arguments;
- defaults;
- property writes.

# Bug 2 — unnamed move-only payload construction does not consume the source

## Normative requirement

Revision 2 states:

> A union containing any non-copyable possible payload is not generally copyable
> as a value.

and:

> Assignment follows normal copy/move semantics.

Constructing a variant with a move-only payload creates ownership of that payload
inside the new union value.

For a move-only source:

```sec
@noCopy
type Session struct {
    id: int
}

type Choice union {
    Some(Session)
    None
}
```

construction:

```sec
let choice := Choice.Some(session)
```

cannot leave both:

```text
session
choice.Some payload
```

owning the same non-copyable value.

The construction must either:

- require the canonical explicit ownership-transfer form where Sec requires it;
  or
- consume the source according to the already-established constructor
  preparation rule.

It must not silently leave `session` usable after ownership was placed into the
union.

---

## Current ownership path

After a let initializer has been semantically accepted, Sema calls:

```go
a.applyLetOwnership(stmt)
```

which normally calls:

```go
a.markMoveSource(stmt.Value)
```

for ordinary inferred ownership.

`markMoveSource()` recursively handles:

- identifiers;
- struct literals;
- array literals;
- Ok/Err wrappers;
- spread expressions;
- conversions.

It does **not** handle ordinary `CallExpression`.

An unnamed union constructor such as:

```sec
Choice.Some(session)
```

is represented as an `ast.CallExpression`.

Therefore:

```go
markMoveSource(Choice.Some(session))
```

does not descend into `session`.

No ownership transfer is recorded for the payload source.

---

# Asymmetry with struct-like union payloads

Struct-like union construction:

```sec
Choice.Named {
    session: session
}
```

is represented as `ast.StructLiteral`.

`markMoveSource()` does recursively inspect struct-literal field values:

```go
case *ast.StructLiteral:
    for _, field := range expr.Fields {
        a.markMoveSource(field.Value)
    }
```

So named-field union payloads can transfer move-only field ownership through the
existing aggregate path, while unnamed payload constructors do not.

This is an accidental AST-shape dependency.

Union ownership semantics must not differ merely because one variant uses:

```text
Some(T)
```

and another uses:

```text
Some { value: T }
```

with semantically equivalent storage.

---

## Required correction for Bug 2

Do not solve this by making `markMoveSource()` recurse through **all**
`CallExpression` arguments. Ordinary function calls have their own parameter
ownership semantics and cannot be treated as aggregate constructors.

Instead, union construction should produce an explicit resolved construction
fact that records the ownership preparation of its payload.

For a single-payload variant, preserve at least:

```text
union type
variant identity
payload target type
payload expression
copy/move preparation
source place if ownership is transferred
resulting copy classification
```

For struct-like payloads, record the same facts per field.

The ownership analysis should then:

- copy implicitly copyable payload values;
- require/perform the canonical ownership transfer for non-copyable payload
  values;
- mark transferred source places unavailable;
- reject moves that conflict with active borrows or defer requirements;
- preserve exact source evaluation order;
- avoid applying function-call ownership semantics to union constructors.

The eventual Semantic IR construction operation should consume these immutable
resolved facts rather than rediscovering ownership from AST shape.

---

# Related borrow/reference provenance audit

Union payload types may themselves contain references.

While correcting constructor preparation, audit that:

- reference origins carried into payloads are preserved;
- branch-scoped match references cannot be stored into longer-lived unions;
- local-reference escape checks apply equally to unnamed and struct-like union
  payload construction;
- aggregate contained-origin metadata is updated for union construction.

This correction does not claim that every such reference case is currently
broken, but the constructor-specific semantic path must not omit provenance that
ordinary struct construction already tracks.

---

# Governance reconciliation

The current `frontend.unions` entry lists as implemented:

```text
nominal variant namespaces, duplicate and empty-union validation, and payload
construction arity and type checking
```

That should be narrowed.

Arity and broad type compatibility are implemented, but complete typed
initialization semantics are not because integer representability checks are
missing.

The same governance entry also describes union ownership support broadly through
payload copy/move classification and Place-based match ownership. That support
is substantial, but it does not currently include correct ownership transfer
from a reusable move-only source into an unnamed union constructor.

Add constructor ownership explicitly as partial/remaining.

Do not downgrade:

- union declaration parsing;
- variant namespace validation;
- explicit defaults;
- ordinary defaultability;
- match payload Place tracking;
- P11 union construction/match Semantic IR inside its documented implemented
  boundary;
- generic-union support already tracked separately.

The new issue is the frontend preparation of constructor payload values before
those later facts are emitted.

# Required regression tests

## Integer representability

1. `U.Value(uint8)` accepts `0`;
2. `U.Value(uint8)` accepts `255`;
3. `U.Value(uint8)` rejects `256`;
4. `U.Value(int8)` accepts `127`;
5. `U.Value(int8)` rejects `128`;
6. struct-like union payload `n: uint8` rejects `300`;
7. generic `U[T]` instantiated with `uint8` rejects an out-of-range literal;
8. ordinary struct field and equivalent union payload field produce equivalent
   representability diagnostics.

## Ownership transfer

9. copyable unnamed payload construction leaves the source usable;
10. move-only unnamed payload construction transfers ownership according to the
    canonical ownership rule;
11. source of transferred move-only unnamed payload cannot be used afterward;
12. borrowed move-only source cannot be transferred into unnamed payload;
13. defer-required source cannot be transferred into unnamed payload;
14. move-only struct-like payload field follows the same ownership semantics;
15. semantically equivalent unnamed and named-field payload variants do not
    differ because of AST representation;
16. temporary move-only payload construction remains valid where no reusable
    source place needs invalidation.

## Cross-layer

17. resolved union-construction facts record payload preparation and variant
    identity;
18. Semantic IR receives a prepared payload rather than inferring copy/move from
    AST call shape;
19. existing P11 union construction fixtures remain valid;
20. constructor validation failure does not publish a misleading successful
    resolved union-construction fact.

## Applied 2026-08-23

All union constructor forms now apply the ordinary destination integer
representability check after compatibility analysis. Aggregate move analysis
also recognizes resolved unnamed union constructors and transfers a move-only
payload into the union without treating ordinary function calls as constructors.
Focused tests cover unnamed and named overflow plus post-construction source use.
Explicit Semantic IR payload-preparation facts remain governed as later
integration work.
