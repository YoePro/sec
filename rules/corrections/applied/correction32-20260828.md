# Applied correction 32 — `sec build` bypasses the canonical LinkPlan/LinkEnvironment model

## Audit context

- Primary rulebook: `rules/compiler/linking.md`
- Status: Normative
- Created / last updated: 2026-08-23
- Document revision: 1
- Sec language version: 0.1
- Rulebook baseline reviewed: `c515862`
- Audited: 2026-08-28
- Primary implementation:
  - `cmd/compiler/main.go`
  - `cmd/compiler/target.go`
- Governance: `implementation-status.yaml`

## Classification

Software bug relative to the current canonical linking rulebook + governance omission.

The current `sec build` path performs concrete linking directly from CLI state and a coarse target definition. It does not construct or verify the canonical `LinkPlan` required by `linking.md`, and it selects the default linker driver through host `PATH` without first resolving a `LinkEnvironment`.

This correction does not change linking semantics. It replaces a legacy/transitional build path with the newly specified canonical linking model.

---

## 1. Canonical requirement

`rules/compiler/linking.md` requires every concrete `CompilationPlan` that needs binary linkage to have one canonical `LinkPlan`.

Conceptually:

```text
LinkPlan {
    CompilationPlan
    LinkEnvironment
    Output
    Inputs
    Symbols
    Roots
    NativeDependencies
    InitializationRequirements
    LinkOptions
    ToolchainRequirements
}
```

Concrete linker/toolchain invocation must be materialized from the verified `LinkPlan`.

The active `CompilationPlan.LinkEnvironment` is authoritative for linkage facts such as:

```text
object format
symbol model
entry convention
relocation model
platform linkage requirements
linker capabilities
startup/object conventions
dynamic-linking model
```

The rulebook explicitly rejects defining target linkage by finding the first linker in `PATH` and accepting its defaults.

---

## 2. Current build path

`cmd/compiler/main.go` currently does, after LLVM/MLIR generation:

```go
clangPath, err := exec.LookPath(options.Clang)
...
clangArgs := []string{
    "-target",
    targetDefinition.LLVMTriple,
    llvmPath,
    "-o",
    options.OutputFile,
}
cmd := exec.Command(clangPath, clangArgs...)
cmd.Run()
```

The default build option is:

```go
Clang: "clang"
```

so an ordinary build resolves `clang` from the compiler host's `PATH`.

An explicit `--clang` override changes the executable path, but it is still not selected or verified against a resolved `LinkEnvironment`.

---

## 3. Current target definition is not a LinkEnvironment

`cmd/compiler/target.go` currently models target linkage with coarse fields such as:

```text
OS
Arch
LLVMTriple
ABI
Profile
PointerWidthBits
Endianness
CanLink
```

`requireTargetCanLink()` verifies only that the target exists, can emit LLVM, and has `CanLink == true`.

There is no canonical resolved model here for:

```text
object format
entry convention
startup/runtime objects
default target libraries
relocation model
native dependency provenance
symbol resolution model
archive behavior
search paths
linker capability requirements
controlled environment
artifact verification
```

A boolean `CanLink` and LLVM target triple cannot substitute for the `LinkEnvironment` required by the rulebook.

---

## 4. Host tool discovery is occurring before target linkage semantics exist

Tool discovery itself may legitimately inspect the host.

The bug is that the current build path has no prior canonical target linkage contract against which the discovered tool is checked.

The effective logic is approximately:

```text
TargetDefinition.CanLink?
    yes
        -> find requested/default clang executable
        -> pass LLVM triple
        -> accept driver defaults
        -> accept successful exit as build success
```

The canonical flow is instead:

```text
CompilationPlan
    -> resolve authoritative LinkEnvironment
    -> build typed LinkPlan
    -> resolve symbols/dependencies/roots
    -> verify LinkPlan
    -> select compatible LinkToolchain
    -> deterministically materialize invocation
    -> execute controlled invocation
    -> verify produced artifact against LinkPlan
```

---

## 5. Target defaults are currently implicit external-tool behavior

The invocation passes only:

```text
-target <LLVMTriple>
<input .ll>
-o <output>
```

Consequently startup objects, runtime facilities, system/default libraries, entry conventions and many output-affecting choices may currently come from clang/linker defaults.

`linking.md` explicitly requires target defaults to remain visible as canonical `LinkPlan` requirements even when a linker driver materializes them implicitly.

The semantic model must not depend on undocumented external-tool defaults.

This matters especially for cross-compilation, where host startup objects/libraries/defaults must never silently become target inputs.

---

## 6. Link inputs are not typed or provenance-bearing

The current direct invocation gives the external driver one generated LLVM file and relies on driver behavior for everything else.

There is no represented typed `LinkInput` set distinguishing, for example:

```text
SecObject
GeneratedStartupObject
GeneratedRuntimeObject
NativeObject
StaticLibrary
SharedLibrary
ImportLibrary
Framework
PlatformLibrary
LTOUnit
```

There is consequently no canonical place to attach dependency provenance, archive selection rules, roots, retention requirements or deterministic materialization.

---

## 7. Successful external linker exit is treated as sufficient

Current `sec build` reports success if `cmd.Run()` succeeds.

`linking.md` explicitly states that successful external linker exit is not by itself proof that the Sec artifact contract is satisfied.

The compiler must verify the candidate artifact against the canonical `LinkPlan`, including as applicable:

```text
target architecture/object format
required entry
required retained roots
native dependency contract
ABI compatibility
forbidden unresolved imports
output artifact kind
```

No such post-link verification is present in the current build path.

---

## 8. Required implementation architecture

### 8.1 Resolve LinkEnvironment as part of CompilationPlan

Replace `CanLink` as the effective linkage semantic model with a resolved `LinkEnvironment` selected through the canonical platform model.

`CanLink` may remain as a compiler/toolchain support summary, but must not define target linkage semantics.

### 8.2 Build one typed LinkPlan

Before any external linker invocation, construct the canonical plan containing at least:

```text
output artifact contract
typed inputs
binary symbol identities
native/foreign requirements
roots/reachability
startup/runtime/shutdown requirements
resolved dependencies/search paths
link options
toolchain requirements
```

### 8.3 Select toolchain from plan compatibility

Host discovery may locate candidate clang/lld/system drivers.

The selected candidate must be verified as capable of materializing the active LinkEnvironment and LinkPlan.

An explicit `--clang` path is a toolchain override, not a substitute for semantic target resolution.

### 8.4 Deterministically materialize invocation

Concrete argv, response files, archive groups and search ordering must be derived from the canonical plan, not source traversal, map order, filesystem order or ambient host state.

### 8.5 Control or model environment

Output-affecting facts such as:

```text
working directory
toolchain path
SDK/sysroot
search paths
environment variables
```

must be explicit, controlled or proven irrelevant.

### 8.6 Verify candidate artifact

After the external tool returns success, verify the artifact against the LinkPlan before reporting build success.

## 9. Governance omission

Root `implementation-status.yaml` currently contains linking handoffs in other integrations, notably ABI, program initialization and platform model.

It has no canonical integration for `rules/compiler/linking.md` and no `LinkPlan` entry.

That is insufficient for a new normative compiler rulebook with explicit Sec 0.1 completion criteria.

Add a dedicated integration such as:

```text
compiler.linking
```

with status `partial` because a concrete legacy build/link execution path exists, but canonical planning/resolution/verification does not.

The governance entry should cross-link:

```text
compiler.program-initialization
platform.platform-model
platform.abi
modules / separate compilation
FFI/native dependency governance
Semantic IR / lowering
```

---

## 10. Existing implementation that can be retained

The following pieces are useful foundations and need not be discarded:

- target-specific LLVM triples;
- `CanLink` as a compiler-support capability flag;
- user-selectable `--clang` path as an explicit toolchain override;
- LLVM and MLIR production paths;
- external process invocation and diagnostic capture;
- output-path handling.

They must be placed downstream of canonical LinkPlan construction rather than serving as the linking semantics themselves.

## 12. Required tests

1. Every linkable CompilationPlan obtains exactly one canonical LinkPlan.
2. LinkEnvironment, not LLVM triple alone, determines linkage contract.
3. Default host PATH cannot silently define target linker semantics.
4. Explicit `--clang` override is compatibility-checked against LinkEnvironment.
5. Incompatible candidate toolchain is rejected before invocation.
6. Target default libraries/startup/runtime objects are represented as LinkPlan requirements.
7. Cross-build does not silently consume host startup objects/libraries/defaults.
8. Typed inputs retain dependency provenance.
9. Link input materialization is deterministic under map/filesystem/source-order changes.
10. Search paths are explicit/provenanced.
11. Archive selection follows canonical fixed-point semantics.
12. Link roots preserve required entry/startup/shutdown/runtime/callback surfaces.
13. Successful external linker exit with wrong artifact contract is rejected.
14. Correct target architecture/object format is verified.
15. Required entry and retained symbols are verified.
16. Link diagnostics map external evidence back to canonical Sec provenance where possible.
17. Multi-Variant builds construct independent LinkPlans.
18. Touched implementation functions contain rulebook/rule traceability comments.
