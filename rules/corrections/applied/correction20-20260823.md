# Correction 20 — `Err(_)` must be valid in match and try handlers

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Affected rulebooks:
  - `rules/control-flow/flowcontrol_match.md`
  - `rules/errors/errorhandling.txt`
- Current `flowcontrol_match.md` revision: **2.0**
- Current Sema behavior: rejects `Err(_)`
- Authoritative language decision: **`Err(_)` is valid**

## Classification

Normative rulebook correction **and** implementation bug.

The current revision-2 match rulebook contains a stale/wrong restriction that
requires an `Err` payload to be named. Sema implements that restriction directly.

The intended Sec 0.1 language rule is:

```sec
Err(_)
```

is a valid pattern when the error payload is intentionally ignored.

This is distinct from:

```sec
Err(error) => {
    discard error
}
```

which remains valid when the programmer wants a named binding and then explicitly
consumes it.

---

## Correct language rule

For `Result[T, E]` handling:

```sec
match result {
    Ok(value) => Use(value)
    Err(_) => Fallback()
}
```

is valid.

Likewise, in a `try` handler:

```sec
try Read() {
    Err(_) => Fallback()
}
```

is valid.

The `_` here is a **pattern discard position**.

It means:

- the `Err` variant is handled explicitly;
- the payload exists semantically;
- no local binding is introduced for the payload;
- the payload is intentionally ignored/consumed according to pattern semantics;
- no `discard error` statement is required because no named binding exists.

This does **not** make bare `_` a general expression.

Therefore:

```sec
discard _
```

remains invalid.

# Rulebook defect — `flowcontrol_match.md`

The current revision 2.0 text says:

```text
An Err payload must be named.
```

and marks this as invalid:

```sec
match result {
    Err(_) => Fallback()
    Ok(value) => Process(value)
}
```

That normative text is wrong and must be replaced.

## Required rulebook correction

Section 7 should preserve the important rule that a catch-all `_` may not
silently absorb an unhandled `Err`:

```sec
match result {
    Ok(value) => Process(value)
    _ => Ignore()
}
```

must remain invalid when `_` would hide the `Err` state.

But an explicit `Err(_)` arm does **not** hide the error variant. It handles the
variant explicitly and intentionally discards its payload.

The distinction is:

```text
_        catch-all pattern
         may not silently absorb an unhandled Result Err state

Err(_)   explicit Result-variant pattern
         valid explicit handling with discarded payload
```

Recommended normative examples:

```sec
match result {
    Ok(value) => Process(value)
    Err(_) => Fallback()
}
```

and:

```sec
match result {
    Ok(value) => Process(value)
    Err(error) => {
        Log(error)
        discard error
        Fallback()
    }
}
```

The second form is only needed when a named binding is useful.

The finalized rule is that `_` is valid in the explicit error payload discard
position:

```sec
Err(_)
```

The error-handling rulebook should be updated to state the same canonical rule as
the revised match/try books.

# Implementation bug — Result match rejects `Err(_)`

The generic match pattern analyzer contains:

```go
if binding.Value == "_" {
    if rejectDiscard {
        a.addErrorAtToken(
            binding.Token,
            "Err payload must be named; use discard name inside the handler",

```

For `Err`, the caller currently sets `rejectDiscard` so the otherwise already
implemented payload-discard machinery is disabled specifically for error payloads.

That restriction must be removed.

`Err(_)` should use the existing:

```text
PayloadDiscard = true
```

semantic path exactly as other valid payload-discard patterns do, while
preserving the special Result rule that a generic catch-all cannot hide an
unhandled error state.

# Semantic distinction that must remain

These three forms are intentionally different:

## 1. Explicit error-payload discard

```sec
Err(_) => Fallback()
```

Valid.

The error variant is explicitly handled; payload is discarded without a binding.

## 2. Named payload then explicit value discard

```sec
Err(error) => {
    discard error
    Fallback()
}
```

Valid.

Useful when a named binding is required by surrounding logic or style.

## 3. Catch-all that hides Err

```sec
match result {
    Ok(value) => Process(value)
    _ => Fallback()
}
```

Invalid when `_` would absorb an otherwise unhandled `Err`.

The compiler must not confuse #1 with #3.

---

# Ownership and destruction semantics

`Err(_)` must not mean "pretend the payload never existed".

The active `Err` payload is semantically discarded.

Therefore:

- trivially destructible payloads may lower to no machine operation;
- non-trivial discardable payloads receive their ordinary destruction;
- non-discardable payload obligations must follow the same discardability rules
  that apply to a payload discard pattern;
- no user-visible binding is created;
- no duplicate destruction may occur.

The resolved pattern should carry explicit payload-discard ownership/destruction
facts into Semantic IR.

Package 12 already has payload-discard support for Result matching; the frontend
must permit the canonical `Err(_)` source form to reach it.

# Required regression tests

## Match

1. `Err(_)` is accepted in a Result match;
2. `Ok(_)` remains accepted;
3. `Err(_)` contributes explicit Err coverage;
4. `Ok(value), Err(_)` is exhaustive for ordinary Result;
5. catch-all `_` after only Ok handling remains invalid when it would hide Err;
6. `Err(_)` creates no local binding named `_`;
7. non-trivial discardable Err payload is destroyed exactly once;
8. non-discardable Err payload follows canonical payload-discard legality.

## Try handlers

9. `try Call() { Err(_) => ... }` is accepted;
10. `Err(_)` creates no error binding;
11. `Err(error)` remains accepted;
12. `Err(error) => { discard error }` remains accepted;
13. exhaustive/handler-selection behavior is unchanged apart from allowing the
    payload discard form.

## Diagnostics

14. remove the diagnostic:
    `Err payload must be named; use discard name inside the handler`
    for canonical `Err(_)`;
15. retain diagnostics for malformed patterns that are neither a valid binding,
    variant, nor `_`;
16. retain the separate diagnostic that prevents catch-all `_` from silently
    hiding an unhandled Result error.

## Semantic IR / lowering

17. resolved match plan records `Err(_)` as explicit Err variant plus payload
    discard;
18. resolved try handler records the same payload-discard fact;
19. Package 12 Result payload-discard lowering accepts the frontend fact;
20. no unwrap/binding operation is required solely to implement `_`.
