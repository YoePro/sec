**§ 1(4)** Acceptance of a decision MUST be tracked separately from implementation, rulebook synchronization, testing, and governance status. Do not mark a compiler feature fully implemented merely because its intended behavior is specified here.

## § 2. MD-080 — Explicit reference creation outside call arguments

**§ 2(1)** A normal owned value or Place MUST NOT be implicitly converted to `ref T` or `ref mut T` in a variable initializer, module initializer, assignment, return expression, aggregate/struct field initializer, or other **non-call-argument** value context that requires a reference.

**§ 2(2)** A programmer MUST write `ref place` or `ref mut place` to create a reference in those contexts, subject to the ordinary reference-origin, mutability, borrowing, aliasing and lifetime rules. Explicit spelling does **not** permit a reference to escape its referent's lifetime.

**§ 2(3)** The established exception remains unchanged: `rules/memory/borrowing.md` § 15.2 permits a **call-bounded** implicit borrow for an argument passed to a parameter whose resolved mode is `ref T` or `ref mut T`. Do not extend that exception to storage, return values, or inferred reference construction. It does not waive the explicit `<-` marker for consuming transfers.

**§ 2(4)** The compiler MUST reject implicit reference creation outside the exception with the following stable diagnostic identity:

```text
ID:       S1169
Registry: borrowing.explicit-ref-required
Family:   borrowing
Severity: error
```

**§ 2(5)** The canonical help text is:

```text
Only call arguments may borrow implicitly.
Write `ref value` or `ref mut value` to create an explicit reference.
```

A diagnostic for an individual occurrence SHOULD also identify the required reference type and source Place and distinguish `ref` from `ref mut`. Reference-origin or lifetime errors remain independent diagnostics and must not be hidden by S1169.

**§ 2(6)** Required valid example:

```sec
let count: int := 10
let countView: ref int := ref count
```

Required invalid example:

```sec
let count: int := 10
let countView: ref int := count   // S1169
```

**§ 2(7)** Add tests for typed locals, module initializers, assignment, returns, struct fields, mutable Places, lifetimes and the allowed call-argument exception. Explicit reference creation must still fail if it would create a dangling reference or conflicting borrow.

**§ 2(8)** Update `rules/memory/references.md` and `rules/memory/borrowing.md` to cross-reference S1169, and register the diagnostic normatively in `rules/tooling/diagnostics.md` without changing its ID or inventing a second diagnostic.

## § 3. MD-082 — Decimal `Scale` property and migration spelling

**§ 3(1)** The canonical public intrinsic property on a **decimal value** is spelled `Scale` and has type `uint8`. It is read-only and belongs to the instance, **not** to the `decimal` type namespace as a static `int` property.

**§ 3(2)** In `rules/library/core-library.md` § 10.1, correct the canonical declaration **from**:

```sec
property scale: uint8 {
    get
}
```

**to**:

```sec
property Scale: uint8 {
    get
}
```

The use of `uint8` is unchanged. Do not rename the parameters of other APIs named `scale` solely as part of this property correction; local parameter names are a separate matter.

**§ 3(3)** `rules/compiler/compiler_known_members.md` MUST list `Scale` among the canonical compiler-known member names and list `.scale` among **temporary lowercase migration spellings**, alongside `.ptr` and `.len`. The lowercase spelling, where temporarily accepted, resolves to the **same stable semantic member ID** as `.Scale` and is not a second property or overload.

**§ 3(4)** All new canonical rulebook examples, generated declarations, hover documentation and final Sec 0.1 documentation MUST use `value.Scale`. When compatibility accepts `value.scale`, diagnostics SHOULD recommend `value.Scale`; the formatter may rewrite the spelling only under its existing opt-in semantic-correction policy and unambiguous resolution.

**§ 3(5)** This property is defined for `decimal`; it MUST NOT implicitly activate the corresponding member on `decimal128`. The latter remains subject to MD-068.

**§ 3(6)** Test instance lookup and type `uint8`, read-only behavior, rejection of the old static interpretation, same-ID legacy resolution, migration diagnostics, formatted output, documentation and the exclusion of `decimal128` until its own decision is applied.

## § 4. MD-096 — Atomic fence spelling in Semantic IR

**§ 4(1)** The normative Semantic IR printer spelling for a fence is:

```text
atomic.fence order=Acquire
atomic.fence order=Release
atomic.fence order=AcqRel
atomic.fence order=SeqCst
```

**§ 4(2)** The semantic operation is `OpAtomicFence` with a typed `AtomicOrder` field. It has **no input operands** and **no results**. `Relaxed` is not a legal order for an explicit fence. The order MUST remain explicit and preserved in IR verification, serialization and transformations.

**§ 4(3)** The operation is available as a **Semantic IR operation independent of the currently implemented numbered Sec MLIR package level**. This decision does *not* assign atomics to a new or existing numbered package, and does not silently expand the feature inventory of a numbered package.

**§ 4(4)** The operation's existence in Semantic IR does **not** imply that the active Sec MLIR dialect schema or lowering pipeline supports emitting it. Until that support is specified and implemented, the emitter MUST fail closed with an explicit unsupported-lowering diagnostic, never omit, replace, weaken or silently ignore a fence.

**§ 4(5)** The public language/API semantics of `MemoryOrder` and `atomic.Fence(order: MemoryOrder)` remain governed by `rules/concurrency/atomics.md`, including any more restrictive source-level validation. This correction controls the Semantic IR identity and available order set; it is not a substitute for platform atomic capability validation (MD-095).

**§ 4(6)** Update `rules/compiler/semantic_ir.md` to specify the operation and its verifier and reference `rules/concurrency/atomics.md`. The schema/lowering owner must explicitly schedule support later rather than treating the Semantic IR operation as already lowered.

**§ 4(7)** Test all four admitted orders, rejection of `Relaxed`, invalid/missing order, rejection of spurious operands/results, round-trip printing/serialization, preserved order through transformations, and fail-closed lowering when a target schema does not support the op.

## § 5. MD-098 — Project setting `max_alignment_padding`

**§ 5(1)** The canonical formatter project setting is:

```toml
[format]
max_alignment_padding = 32
```

It is measured in **spaces**, not indentation levels. Allowed explicit values are integers in the inclusive interval **1..1024**. Zero, negative values, out-of-range values and nonintegers MUST be rejected by project configuration validation, not interpreted as disabling alignment.

**§ 5(2)** If the key is absent, the effective value is **four times `indentation_width`**; for default indentation width `4`, that is **16 spaces**. Thus this addition does not change the result for a project that omits the key and does not require a new `format_version`.

**§ 5(3)** The setting is project-owned in the `[format]` table of `.sec/sec.toml`. It has **no separate `sec fmt` command-line override**. `sec init` SHOULD write it only as a commented example, not as an activated explicit default:

```toml
[format]
# max_alignment_padding = 16
```

**§ 5(4)** The setting limits candidate structural alignment columns as described by `rules/tooling/formatter.md` § 9(10), **except where that book explicitly mandates alignment independently of the limit**. In particular, `formatter.md` § 15(4) already requires homogeneous enum explicit-value groups to retain a common `=`/value column regardless of padding width (MD-100).

**§ 5(5)** Correct the stale explanatory example in `formatter.md` § 4(14): **wide enum member names are not a reason to increase this setting**, because enum explicit-value alignment is exempt. Describe ordinary non-exempt declaration groups (for example eligible struct fields or `let` declarations) instead. Preserve § 9(10)'s enum exemption.

**§ 5(6)** This correction does **not** decide MD-099 (whether the trailing-comment alignment column is independently subject to the padding cap) nor MD-100's remaining follow-up regarding potential mandatory alignment for other declaration categories. Those must remain open where currently open. Do not imply that the new setting settles them.

**§ 5(7)** Update `rules/tooling/formatter.md` §§ 4, 9 and 15 and the corresponding `[format]` manifest rules in `rules/projects/projects.md` without duplicating the default or changing canonical output for absent configuration.

**§ 5(8)** Test implicit default for indentation widths `2`, `4`, `6`, explicit values `1` and `1024`, invalid boundary and type values, no CLI override, `sec init` comment behavior, non-enum group behavior, mandatory enum alignment even when the configured cap is exceeded, and format idempotence.

## § 6. MD-104 — Exact integer conversion and plan-sensitive proof

### § 6.1 Conversion operation and authority

**§ 6.1(1)** Retain the accepted operation names:

```text
Semantic IR: numeric.convert-exact
Sec MLIR:    sec.numeric.convert_exact
```

The Semantic IR operation class may remain `NumericConvertExactOp`. The general name from P20 is intentionally reused for proven-exact built-in integer-to-integer conversion. No second integer-only operation is introduced.

**§ 6.1(2)** Until the later P20 scope is implemented, the **early dialect verifier admits this operation only when operand and result have valid integer-conversion representations**. This is an intentional temporary verifier restriction, not a change to P20's eventual numeric conversion scope. Updating schema/operation support must be explicit and version-compatible rather than silently interpreting an older schema as accepting unrelated float conversions.

**§ 6.1(3)** A conversion may be represented by `numeric.convert-exact` **only when Sema has established and retained proof** that every value permitted by the resolved source domain, or the particular compile-time-known source value, is representable in the destination domain under the active CompilationPlan. Merely finding a convenient `trunci`, `extsi`, `extui`, bitcast or identity instruction does **not** establish semantic exactness.

**§ 6.1(4)** Subject to proof, lowering may use signed/unsigned extension by source signedness, narrowing only when proven safe, or identity. No runtime error edge exists for `numeric.convert-exact`. The selected instruction must preserve the mathematical integer value and the resolved signedness/width semantics. In particular, truncating an arbitrary unsigned value into a too-small signed domain is not exact merely because the bit width is the same.

### § 6.2 Source-domain proofs and enum distinctions

**§ 6.2(1)** Proof from a **compile-time-known constant** is allowed if its exact value is validated as representable in the destination. A runtime expression cannot be treated as a constant based on an unrelated example or source literal elsewhere.

**§ 6.2(2)** For an ordinary **closed, integer-backed enum**, the semantic source domain is the set of unique declared underlying value classes, not the whole carrier integer range. Sema MAY prove exact conversion to an integer target from that closed domain, provided each declared value is representable in the target. Enum aliases with duplicate numeric values do not enlarge the domain.

**§ 6.2(3)** For an **open `bit[N]` enum**, the source domain is **every integer from `0` through `2^N - 1`**. Sema MUST NOT prove conversion safe from the values of just the named cases; unnamed hardware patterns remain valid values.

**§ 6.2(4)** For an external C enum or other ABI-defined **open** enum, the source domain is its complete ABI-defined representable raw-value domain for the active target, not the declared case list. If the ABI domain is unavailable or unresolved, Sema MUST NOT manufacture an exactness proof based on declared cases.

**§ 6.2(5)** Direct enum-to-carrier conversion may be an identity transformation only when its declared carrier representation and target semantics agree. Conversion to another integer width or signedness still requires an exactness proof, even when an underlying representation can physically be reinterpreted.

**§ 6.2(6)** The proof using a closed enum is valid only while the language's **closed-domain invariant** is upheld across construction, FFI, unsafe boundaries, IR transforms and lowering. A raw integer must not be silently accepted as an arbitrary closed-enum value. When raw foreign values could violate that invariant, validate or represent them via an appropriate open/raw type rather than treating an invalid closed-enum bit pattern as a legitimate Sec enum value.

**§ 6.2(7)** Example (the entire closed domain fits into `uint8`):

```sec
enum State int32 {
    Idle = 1
    Running = 2
    Failed = 200
}

fn StateCode(value: State) uint8 {
    return uint8(value)
}
```

**§ 6.2(8)** Counterexample (declared cases do not bound an open enum):

```sec
enum DeviceMode bit[8] {
    Off = 0
    Running = 1
}
```

A runtime `DeviceMode` can carry `255`. Conversion to `uint8`, `uint16` or `int16` is exact; conversion to `int8` is **not** proven exact from this enum type alone.

### § 6.3 Target-dependent proof — accepted option A

**§ 6.3(1)** The safety proof is made for the **selected CompilationPlan**, not for a synthetic intersection of all possible 32- and 64-bit targets. This is the owner's accepted **Option A**, 2026-10-18.

**§ 6.3(2)** Sema MUST first resolve the active plan's native widths and value ranges for `int`, `uint` and any other target-sized types. It MUST NOT use the host compiler's pointer size, an assumed universal `int64`, an unresolved layout, or an arbitrary default target.

**§ 6.3(3)** Example:

```sec
fn Convert(value: uint32) int {
    return int(value)
}
```

On a target where `int` is 64-bit signed, every `uint32` value is representable and this conversion is exact. On a target where `int` is 32-bit signed, the general `uint32` domain does not fit; this body cannot be treated as an exact conversion unless the actual operand has an independently proven narrower domain. A checked conversion with explicit `try` handling is required when failure remains possible.

**§ 6.3(4)** It is permitted for the same source program to compile on one target but be rejected, or require an explicit checked-conversion form, on a different target. This is **target-dependent portability**, not relaxed runtime safety.

**§ 6.3(5)** Exactness plans, Semantic IR records, incremental compilation reuse and persistent caches MUST carry or validate the **CompilationPlan compatibility** of every platform-sensitive proof. Reuse across different effective type widths, target ABI domains or other proof-relevant plan facts is forbidden unless the proof is independently re-established for the new plan. A stale, incompatible or unverified cached proof MUST fail closed or be recomputed from canonical semantic inputs.

**§ 6.3(6)** If the active CompilationPlan lacks the needed type-width or domain facts, the compiler MUST NOT emit an exact conversion on speculation. It may produce a proper diagnostic or defer the conversion until sufficient target facts are resolved, but the backend must not perform an unchecked conversion masquerading as exact.

### § 6.4 Checked conversions, error model and Sema/IR boundary

**§ 6.4(1)** A conversion that may not fit the destination is **not** `numeric.convert-exact`. It follows the language's checked explicit-conversion policy. When runtime checking is required, the canonical public failure family is **`ConversionError`**, including `ConversionError.OutOfRange` for integer-domain failure (MD-012). This correction does not introduce a competing public `NumericConversionError` type.

**§ 6.4(2)** P20's provisional references to `NumericConversionError` and `NumericConversionErrorFromReasonOp` MUST be reconciled with the already accepted `ConversionError` policy when the checked-conversion implementation is integrated. Internal operation names may be retained as implementation details only if they do not imply a new public error type.

**§ 6.4(3)** The fact that the active lowering track does not yet fully support `numeric.convert-checked`, `Result[_, ConversionError]` and `try` is an **implementation gap**. It does **not** authorize silent lossy integer conversion. The compiler must reject with an appropriate diagnostic or unsupported-lowering outcome until checked conversion is available. MD-056's remaining frontend consistency issue is not silently declared resolved here.

**§ 6.4(4)** Existing `ResolvedIntegerConversion` compiler data MAY be retained and eventually folded into P20's `ResolvedNumericConversionPlan`; no forced premature data-structure rewrite is required. Whatever representation is used MUST retain at least: resolved source/target semantic types, source/target integer domains and widths, signedness, active CompilationPlan compatibility, constant-vs-type-domain proof basis, whether exactness is proven, and whether checking/error behavior is required. This is an internal semantic data requirement, not a new Sec public type.

**§ 6.4(5)** Semantic IR builder and verifier MUST consume a Sema-resolved, plan-compatible conversion contract; they MUST NOT rediscover or guess enum domains or target width from lowered bits alone. The verifier MUST reject missing, incompatible, stale or contradictory proof information on `numeric.convert-exact`. A backend/MLIR lowering pass MUST NOT weaken or reinterpret the established proof.

**§ 6.4(6)** No direct-LLVM or parallel lowering track is authorized by this correction. This decision fits the established single pipeline; it does not prematurely claim that every conversion is supported by the current pipeline.

### § 6.5 Required tests and synchronization

**§ 6.5(1)** Required positive tests include exact signed and unsigned widening; exact identity; verified constant narrowing; negative/positive boundaries; `uint32 -> int` on a 64-bit plan; a closed enum whose *declared* domain fits a narrower integer; open `bit[8] -> uint8`/`uint16`/`int16`; and exact repeatable printer/lowering behavior.

**§ 6.5(2)** Required negative tests include unchecked `uint32 -> int` on a 32-bit plan with runtime-unknown value; open `bit[8] -> int8`; C/open enum where case-list-only proof would be unsound; a closed enum whose one declared case exceeds the target domain; a malformed exact-conversion IR op with no proof; a proof made for another plan; and a checked conversion not yet lowerable (must fail closed, never silently truncate).

**§ 6.5(3)** Test incremental and cold compilation parity under plan changes, including warming a cache on a 64-bit plan and compiling the same source on a 32-bit plan. No exactness proof may be inherited merely because the source file is unchanged. Include stale/malformed/incompatible cache states as negative test inputs.

**§ 6.5(4)** Synchronize `rules/types/types.md`, `rules/declarations/enums.md` (cross-reference only where its already canonical closed/open rules need no replacement), `rules/compiler/semantic_ir.md`, `rules/mlir/packages/sec-mlir-dialect_package20.md`, and the owning dialect schema/version documentation. Preserve existing package responsibilities and paragraph numbers.

## § 7. MD-105 — `char`/`rune` comparison through integer comparison IR

**§ 7(1)** Reuse the established Semantic IR `int.compare` operation and the corresponding Sec MLIR `sec.int.cmp` operation for comparison of **two `char` values** or **two `rune` values**. Do not add a separate character comparison IR/dialect operation.

**§ 7(2)** The supported comparison predicates are `==`, `!=`, `<`, `<=`, `>` and `>=`. Sema MUST require the operands of this character-specific comparison to have the **same** resolved character type. This decision does not add implicit conversion between `char` and `rune`, or between characters and integers.

**§ 7(3)** `char` compares by its **unsigned 8-bit** value. `rune` compares by its **Unicode scalar value**, using the existing unsigned 32-bit scalar representation. Signed comparison of either category is incorrect. Rune validity constraints remain governed by the core character type rules.

**§ 7(4)** Sema MAY record character-specific operator kinds for source typing and diagnostics. Semantic IR lowers those kinds to its existing `int.compare`, keeping `char`/`rune` operand types and provenance until the declared scalar-layout transition. The verifier MUST accept the respective character operands under this specific operation contract, while rejecting mismatched character types.

**§ 7(5)** The Sec dialect `sec.int.cmp` verifier likewise admits `!sec.char` and `!sec.rune` and lowering follows the established mappings `char -> ui8` and `rune -> ui32`, applying unsigned predicates for relational comparison. The result is `bool`.

**§ 7(6)** Update `rules/foundations/operators.md`, `rules/compiler/semantic_ir.md` and `rules/mlir/packages/sec-mlir-dialect_package7.md` (plus dialect-verifier documentation) **without claiming the whole of P7 has gained general character arithmetic**. The change is restricted to existing character comparisons.

**§ 7(7)** Test all six predicates, equality/ordering boundaries, `char` values with the top bit set, valid `rune` scalars above U+FFFF, mixed `char`/`rune` rejection, signedness correctness after lowering, and parity with source-level constant comparison.
