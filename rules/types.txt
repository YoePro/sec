Types, Variables and Decimal
============================

This file is the canonical rules document for:

- variable declarations
- type identity
- type defaultability and default initialization
- named-type contract integration
- explicit conversions
- decimal values

It replaces the older split documents:

- `variables.txt`
- `type_decimal.txt`
- the previous short `types.txt`


Implementation status
---------------------

Implemented:

- immutable-by-default variables
- `let` declarations with inferred or explicit type
- comma-separated `let` declarations
- type-first variable declarations
- parenthesized type-first declaration groups
- formatter indentation for parenthesized type-first declaration group entries
- mutable typed declarations without initializers
- semantic default initialization for defaultable mutable typed declarations
- explicit named-type `default` clauses
- rejection of immutable typed declarations without initializers
- redeclaration checks without overwriting the previous symbol
- named range types
- named unit types
- explicit conversions through `Type(value)`
- explicit numeric-to-bool conversion
- decimal literals as exact decimal values in sema
- `c` and `r` integer suffixes for explicit `char` and `rune` literals,
  including Unicode-scalar validation, contextual `char`-literal shaping for
  `rune` function parameters, and exact type comparisons
- `int128`, `int256`, `uint128` and `uint256` as active builtin types in lexer,
  parser, AST and semantic analysis
- `decimal128` as an active builtin type in lexer, parser, AST and semantic
  analysis
- decimal representation in LLVM as `{ i64, i8 }`
- decimal literal emission in LLVM
- explicit `decimal(int)` conversion in LLVM
- decimal function return values in LLVM
- MLIR decimal representation as `!llvm.struct<(i64, i32)>`
- MLIR decimal128 representation as `!llvm.struct<(i128, i32)>`
- decimal and decimal128 literals, storage, parameters and returns in MLIR
- inline integer-to-decimal and decimal-to-integer conversions in MLIR
- `int128`, `int256`, `uint128` and `uint256` lowering in MLIR
- bit-backed enum widths preserved through AST and semantic analysis and
  lowered as exact `iN` values in MLIR and LLVM
- bare `T[]` is accepted by semantic analysis as an owning dynamic
  array/sequence type; `ref T[]` and `ref mut T[]` remain slice references
- compiler-known types may carry non-copyable classification, which Sema
  enforces for ordinary named copies and consuming transfer contexts
- internal semantic types can represent explicit nominal non-copyability and
  preserve that reason for diagnostics; no source spelling is assigned

Partially implemented:

- decimal arithmetic is type-checked in sema, including unit algebra.
- decimal arithmetic in LLVM is recognized but not lowered yet.
- runtime contract checks for non-constant conversions are not generated yet.
- the direct LLVM backend does not yet lower the 128-bit and 256-bit integer
  families or `decimal128`; the MLIR pipeline does.

Not implemented yet:

- inline decimal arithmetic lowering.
- decimal overflow checks in generated lowering.
- decimal division precision policy.
- decimal comparison lowering in LLVM.
- runtime contract failure path for decimal overflow, division by zero or
  precision exhaustion.
- full formatter support for all declaration forms.
- source syntax requiring that a nominal type remain compiler-derivably
  copyable; Sec 0.1 intentionally defines no positive copy attribute.


1. Variable declarations
------------------------

Variables are immutable by default.

Supported `let` forms:

```sec
let a := 9
let mut a := 9
let a: int := 9
let mut a: int
let mut a: Type
```

Comma-separated `let` declarations are supported:

```sec
let a := 9, b := "hello", c := true
let mut a := 9, b := "hello", c := false
```

Each declarator is checked independently.

For inferred declarations, each variable gets the type of its own initializer.

Example:

```sec
let a := 9, b := "hello", c := true
```

This declares:

```sec
a: int
b: string
c: bool
```


2. Type-first variable declarations
-----------------------------------

Type-first mutable declarations may omit initializers when the declared type is
defaultable:

```sec
int mut: a, b, c
```

This declares three mutable `int` variables, each semantically initialized to
the `int` default zero.

Type-first immutable declarations must have initializers:

```sec
float: a := 5.4, pi := 3.14
```

Parenthesized type-first declaration groups are supported for many immutable
values of the same type:

```sec
TokenType (
    ILLEGAL := "ILLEGAL",
    EOF := "EOF",
    IDENT := "IDENT",
)
```

This is equivalent to ordinary immutable typed declarations where every
declarator inherits `TokenType`.

The form is intended for compact constant-like tables without introducing a
separate `const` declaration kind.

Each entry must have an initializer.

This is rejected:

```sec
int: a, b, c
```

Expected diagnostic shape:

```text
immutable typed declaration requires initializer for "a"
```

Reason:

An immutable declaration without an initializer is a useless unassigned
constant. Sec does not create implicit zero constants for immutable bindings.
This does not deny semantic default initialization of mutable storage or omitted
struct fields.


3. Declaration grammar
----------------------

Grammar sketch:

```text
LetDeclaration
    := "let" ["mut"] LetDeclarator { "," LetDeclarator }

TypedDeclaration
    := TypeReference ["mut"] ":" TypedDeclarator { "," TypedDeclarator }

TypedDeclarationGroup
    := TypeReference "(" TypedDeclarator { "," TypedDeclarator } [ "," ] ")"

LetDeclarator
    := Identifier [ ":" TypeReference ] [ ":=" Expression ]

TypedDeclarator
    := Identifier [ ":=" Expression ]

NamedTypeDeclaration
    := "type" Identifier TypeDefinition { Contract } [ DefaultClause ]

DefaultClause
    := "default" ConstantExpression
```

Rules:

- each declarator creates one symbol.
- redeclaration is checked per name.
- redeclaration must not overwrite the previous symbol.
- immutable declarations must have an initializer.
- parenthesized type-first declaration groups are immutable and every
  declarator must have an initializer.
- typed mutable declarations may omit an initializer only when their type is
  defaultable; omission performs semantic initialization.
- `let mut a: Type` is valid.
- `let a: Type` without initializer is invalid.
- explicit type applies to all declarators in a type-first statement.
- `let` declarations infer type per declarator when no explicit type exists.


4. Named type identity
----------------------

A user-defined type is distinct from its underlying type.

Example:

```sec
type Percent int range 0..100
type Age int range 0..130
```

`Percent`, `Age` and `int` are different types.


4.1 User-declared copy policy
-----------------------------

The compiler distinguishes trivial, semantic, conditional, move-only and
explicitly non-copyable classifications as defined by `copy_move.md` and
`ownership.md`.

A user-defined method named `Copy`, `Clone`, `Duplicate`, `Snapshot` or
`ToOwned` is an ordinary named operation. It does not implicitly opt the type
into assignment copy semantics.

The canonical explicit non-copyability declaration is:

```sec
@noCopy
type SessionID struct {
    value: uint64,
}
```

It is parser- and Sema-implemented for nominal structs, enums, unions,
registers, named underlying types, and generic nominal types.

The declaration syntax for this separate future policy is not defined:

- a verified requirement that a nominal type remain compiler-derivably
  copyable;

`attributes.md` intentionally excludes a positive copy attribute from the Sec
0.1 subset. Compiler-known core and standard-library types may carry the
internal non-copyable classification directly.

An aggregate's representation only permits copy derivation; it does not decide
the result by itself. All stored fields must permit copy, and ownership,
destruction, mutable-alias, resource, compiler-known, and nominal restrictions
may still forbid it. Wrapping a non-copyable field in another named aggregate
does not bypass the field restriction.

Sec 0.1 does not permit a user-defined hidden copy body. A positive future
declaration is a compiler-verified requirement on derived copyability, not an
implementation hook.


5. Type defaults and defaultability
-----------------------------------

Every type is either defaultable or non-defaultable. A defaultable type has one
deterministic valid value that the compiler can construct without hidden
allocation or resource acquisition.

Primitive defaults are:

| Type family | Default |
|---|---|
| signed integer | numeric zero |
| unsigned integer | numeric zero |
| binary float | numeric zero |
| decimal | numeric zero |
| `byte` | numeric zero |
| `bool` | `false` |
| `string` | `""` |
| `char` | zero character, written `0c` |
| `rune` | Unicode scalar zero, written `0r` |

A named type resolves its default in this order:

```text
explicit default clause
type-specific canonical rule
constraint-derived default
valid underlying-type default
no default
```

The explicit clause is canonical and follows all contracts:

```sec
type Port int range 1..65535 default 8080
type User string in ["Admin", "User", "Other"]

let mut port: Port
let mut user: User
```

`port` becomes `Port(8080)` and `user` becomes `User("Admin")`. Explicit
defaults are allocation-free compile-time constant expressions and must be
representable and satisfy every type contract. Range defaults use zero when
valid, otherwise the unique representable valid value nearest zero. An ordered
`in [...]` contract uses its first listed value.

An immutable binding still requires a source initializer. Complete default
selection, aggregate rules and non-defaultable families are defined in
`default_values.md`; contracts themselves are defined in `contracts.md`.

Invalid:

```sec
let age: Age := 20
let percent: Percent := age
```

Reason:

Variables already have a type. They are never implicitly converted into another
named type.


6. Builtin numeric types
------------------------

Sec has signed integers, unsigned integers, floating-point numbers and decimal.

Implemented integer types:

```text
int
int8
int16
int32
int64
int128
int256

uint
uint8
uint16
uint32
uint64
uint128
uint256
byte
```

`int128`, `int256`, `uint128` and `uint256` are active in lexer, parser, AST and
semantic analysis. Compile-time integer range metadata uses arbitrary precision
so boundary literals and overflow checks work for these widths.

The MLIR pipeline lowers these types to `i128` and `i256`, including literals,
storage, parameters, returns, casts, arithmetic, bitwise operations, shifts and
signed/unsigned operations. The legacy direct LLVM backend does not yet provide
the same coverage.

Floating-point types:

```text
float
float32
float64
```

Exact decimal type:

```text
decimal
decimal128
```

`decimal128` is active in lexer, parser, AST and semantic analysis as a distinct
concrete decimal type. Numeric literals may initialize it directly, and explicit
conversions such as `decimal128(value)` are accepted when the source is numeric.

The MLIR pipeline lowers `decimal128` to `!llvm.struct<(i128, i32)>`. The legacy
direct LLVM backend does not yet lower it.

Hardware bit widths are available only as enum backing and register layout
syntax:

```sec
enum ClockSource: bit[2] {
    Internal = 0,
    External = 1,
    Bypass = 2,
}
```

`bit` means `bit[1]`. A `bit[N]` enum is an unsigned nominal enum with the
range `0..(2^N - 1)` and lowers to the exact LLVM integer representation `iN`.

`bit` and `bit[N]` are not general-purpose variable types. Their scope is
hardware enum representation and register field layout.

Fixed in-memory byte buffers use the ordinary array type instead:

```sec
let mut buffer: byte[512]
```

The bootstrap string representation exposes `value.ptr[index]` as a `byte` for
low-level standard-library formatting code. Such indexing must remain within
`0..<value.len`; ordinary application code should prefer string iteration and
higher-level formatting operations.


7. Untyped literals
-------------------

Numeric literals are untyped until context gives them a type.

Literal suffixes may be used when the source should explicitly state the
literal family or scalar type:

```text
8i    int literal
8u    uint literal
8f    float literal
8d    decimal literal
65c   char literal
65r   rune literal
```

The suffix selects the numeric family, not a fixed width. Width is still chosen
by context or by explicit conversion/type annotation:

```sec
let a := 8i          // int
let b := 8u          // uint
let c := 8f          // float
let d := 8d          // decimal
let letter := 65c    // char
let nul := 0r        // rune

let small: int8 := 8i
let wide: int128 := 8i
let exact: decimal128 := 8d
```

`c` and `r` apply only to integer literals. They select the exact scalar type,
not a numeric width, and neither type implicitly converts to or from integer
types. Use the matching suffix when comparing against a `char` or `rune`:

```sec
if ch == 0r {
    // ...
}

if letter == 65c {
    // ...
}
```

Single-quoted character literals are context-shaped. A character literal such
as `'$'` is a `char` by default, but it becomes a `rune` where a `rune` is
expected, when it is compared directly to a `rune` value, or as a `rune`
`switch` case. No explicit `rune('$')` conversion is required:

```sec
let marker: rune := '$'

if ch == '$' {
    // ch is a rune
}
```

This does not make existing `char` and `rune` variables interchangeable.

The literal value must be a valid Unicode scalar value: it must be within
`0..U+10FFFF` and must not be in the surrogate range `U+D800..U+DFFF`.

For hexadecimal literals, `c` remains a hexadecimal digit. Consequently
`0x41c` is an unsuffixed hexadecimal integer; write the character value using
a decimal, binary, or octal `c` literal instead. `r` is unambiguous, so
`0x41r` is valid.

Base prefixes are supported for integer literals:

```text
0b1000    binary
0o10      octal
0x8       hexadecimal
```

Valid:

```sec
let i: int := 3
let u: uint := 3
let f: float64 := 3.14
let d: decimal := 3.14
let p: Percent := 90
```

Invalid:

```sec
let p: Percent := 101
let p: Percent := -1
```

The literal is checked against the target type before assignment.

This context shaping applies to declaration initialization. It does not mean
that variables are implicitly converted later.


8. Assignment
-------------

Assignment requires the assigned value to match the target variable type.
If the target has a constrained named type, conversion and assignment remain
fallible by type and must use `try` with a handler block; see
`rules/contracts.md`.

Valid:

```sec
let mut p: Percent := 10
try p = Percent(20) {
    Err(error) => {
        discard error
    }
}
```

Invalid:

```sec
let mut p: Percent := 10
p = 20
```

Rationale:

Declaration context may shape an untyped literal, but later assignment should
preserve strict type identity. Use an explicit conversion when assigning into a
named type.


9. Explicit conversions
-----------------------

Conversion syntax:

```sec
TargetType(value)
```

Examples:

```sec
let x := 90
let p: Percent := Percent(x)
let d: decimal := decimal(5)
let b: bool := bool(x)
```

If a conversion into a constrained type is compile-time known, sema checks the
contract at compile time.

If a conversion into a constrained type is not compile-time known, it must later
generate a runtime contract check.

Implicit conversion is not allowed.

Invalid:

```sec
let value: bool := true
let number: int := 1

if value == number {
}
```

Valid:

```sec
if value == bool(number) {
}
```


10. Boolean numeric conversion
-----------------------------

Explicit conversion from numeric values to bool is allowed.

Syntax:

```sec
bool(value)
```

Rules:

- `bool(int)` is valid.
- `bool(uint)` is valid.
- `bool(float)` is valid.
- `bool(decimal)` is valid.
- integer subtypes are valid.
- `int128` is valid.
- `int256` is valid.
- unsigned integer subtypes are valid.
- `uint128` is valid.
- `uint256` is valid.
- floating-point subtypes are valid.
- decimal is valid.
- decimal128 is valid.

The conversion result is:

- `false` when the numeric value is zero.
- `true` otherwise.

Examples:

```sec
bool(0)      // false
bool(1)      // true
bool(-1)     // true
bool(0.0)    // false
bool(0.1)    // true
```

This is explicit conversion only. Numeric values are still not accepted as
boolean conditions.

Invalid:

```sec
if 1 {
}
```

Expected:

```text
if condition must be bool, got int
```


11. Decimal model
----------------

`decimal` is Sec's exact base-10 numeric type.

It is represented conceptually as:

```go
type DecimalValue struct {
    Int64 int64
    Scale uint8
}
```

Examples:

```text
123.45  => Int64: 12345, Scale: 2
100     => Int64: 100,   Scale: 0
.1      => Int64: 1,     Scale: 1
```

Decimal literals must be interpreted from their source lexeme, not by first
converting through binary floating point.

This avoids errors such as:

```text
0.1 + 0.2 = 0.30000000000000004
```


12. Decimal inference
---------------------

Untyped decimal literals infer as `decimal` by default:

```sec
let x := 3.14
```

`x` has type `decimal`.

Float must be requested explicitly:

```sec
let f: float64 := 3.14
```

Numeric literals are still context-shaped:

```sec
let f: float64 := 3.14
let d: decimal := 3.14
let i: int := 3
```

But runtime values are not implicitly converted:

```sec
let f: float64 := 3.14
let d: decimal := f       // error
let e: decimal := decimal(f)
```

Current rule:

- decimal literals may initialize decimal targets.
- integer literals may initialize decimal targets.
- float variables do not implicitly initialize decimal targets.
- explicit conversion is required for runtime float-to-decimal conversion.
- explicit decimal-to-integer conversion discards fractional decimal digits by
  dividing the coefficient by ten once per scale step. Signed division therefore
  truncates toward zero.


13. Decimal arithmetic
----------------------

Semantic analysis type-checks decimal arithmetic.

Addition and subtraction require compatible numeric types and, when units are
present, compatible dimensions.

Multiplication and division participate in unit algebra.

Examples:

```sec
type Meter decimal<m>
type Second decimal<s>
type Speed decimal<m/s>

fn Calculate(distance: Meter, time: Second) Speed {
    return distance / time
}
```

When an expected named unit type exists and the derived dimension matches, sema
may use the expected named type.

For the full unit rules, see:

```text
rules/units.txt
```


14. Decimal lowering representation
-----------------------------------

The MLIR pipeline uses:

```mlir
decimal    => !llvm.struct<(i64, i32)>
decimal128 => !llvm.struct<(i128, i32)>
```

Field layout:

- field 0: signed integer value
- field 1: base-10 scale

The scale is `i32` on every target. This maps naturally to 32-bit registers on
amd64, ARM64, ARMv7, STM32 and ESP32-class targets and avoids byte-masking
operations associated with an `i8` scale.

Examples:

```sec
let d: decimal := 3.14
```

is emitted in the MLIR pipeline as an aggregate equivalent to:

```llvm
{ i64 314, i32 2 }
```

Implemented in MLIR code generation:

- decimal and decimal128 literal emission from the source lexeme
- local storage
- function parameters and return values
- integer literal to decimal when the target type is decimal or decimal128
- explicit integer-to-decimal conversion
- explicit decimal-to-integer conversion
- explicit conversion between decimal and decimal128
- fully inline aggregate construction with `llvm.insertvalue`
- fully inline component access with `llvm.extractvalue`
- inline scale removal loops for decimal-to-integer conversions

No runtime library call is used for these operations.

The legacy direct LLVM backend currently uses `%sec.decimal = type { i64, i8 }`.
That representation is retained only for the existing direct-backend subset and
must not define the canonical MLIR lowering.

Not implemented in decimal code generation:

- decimal arithmetic
- decimal comparison
- overflow checks
- precision/runtime contract failure paths


15. Inline decimal lowering strategy
------------------------------------

Decimal operations should be lowered inline so compiled programs do not require
a mandatory Sec runtime library. Generated lowering may use standalone MLIR
blocks, `llvm.extractvalue`, `llvm.insertvalue`, loops and LLVM overflow
intrinsics.

Addition and subtraction:

- align operands to the same scale.
- perform checked signed integer arithmetic.
- result scale is the aligned scale.

Multiplication:

- multiply integer values with overflow checking.
- result scale is `left.Scale + right.Scale`.

Division:

- reject division by zero.
- apply an explicit or default precision policy.
- scale numerator before integer division.
- normalize trailing zeroes when appropriate.

Overflow handling:

- generated lowering must use checked arithmetic.
- LLVM-dialect MLIR may use overflow intrinsics such as:

```llvm
@llvm.sadd.with.overflow.i64
@llvm.smul.with.overflow.i64
```

On overflow, division by zero or precision exhaustion, generated code must enter
the Sec contract failure path without requiring a general runtime library.
