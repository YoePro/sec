## Classification

1. an **implementation bug** in loop fixed-point analysis; and
2. a **general implementation-governance rule** requiring source-to-rulebook

# Part I — loop backedges do not carry arena generations

## Normative requirement

`rules/control-flow/flowcontrol_while.md` revision 2.0 requires Sema/flow
analysis to model:

```text
condition true
  -> body

body normal continuation
  -> condition

continue
  -> condition
```

and to preserve ordinary ownership, borrowing, lifetime, and destruction rules
through repeated iterations.

Arena references carry a generation/epoch. `Arena.Reset()` and
`Arena.Release()` advance that generation, making references created under an
older generation stale.

Therefore an arena-generation change on a loop backedge must be visible when
the next condition/body iteration is analyzed.

---

## Observable failure

Conceptually:

```sec
fn Run() Result[void, AllocationError] {
    let mut arena := new Arena()
    let value := try arena.New[int]()

    while true {
        Use(value)
        arena.Reset()
    }
}
```

Iteration 1:

```text
value generation = G
Use(value)        -> valid
arena.Reset()     -> arena generation becomes G+1
```

Iteration 2:

```text
Use(value)
```

must be rejected because `value` still refers to generation G.

Current fixed-point analysis can miss this completely.

The same defect applies to `for {}` because both loop families use the same
fixed-point helper.

---

# Bug 1 — arena generation is absent from fixed-point change detection

## Affected code

`internal/sema/analyzer.go`

`checkLoopBackedgeFixedPoint()` receives:

```go
headerMoved
headerReasons
headerClosedResources
headerBorrows
headerLocalRefContainers
```

but receives no header/backedge arena-generation state.

Its early-exit check is:

```go
if len(backedgePlaces) == 0 &&
   tokenStateKeysEqual(entry.closedResources, headerClosedResources) &&
   borrowStatesEqual(entry.borrows, headerBorrows) &&
   referenceOriginStatesEqual(
       entry.localRefContainers,
       headerLocalRefContainers,
   ) {
    return
}
```

Arena generation is not part of the test.

Therefore if a loop body changes only:

```text
arenaGenerations
```

for example by `arena.Reset()`, the compiler may conclude that no relevant
loop state changed and skip second-iteration verification entirely.

This is exactly the class of case where second-iteration analysis is required.

---

# Bug 2 — fixed-point replay resets arena state to loop entry, not backedge state

Even when another state change causes replay, the helper initializes:

```go
a.arenaGenerations =
    copyArenaGenerations(entry.arenaGenerations)
```

That is the state **before the first iteration**.

For correct second-iteration analysis, arena generation must come from the
merged reachable loop-header/backedge state:

```text
entry path
normal body backedge
continue backedges
```

Using the original entry generation makes a reset/release in the preceding
iteration invisible to stale-reference checks during the replayed condition/body.

---

# Bug 3 — `continue` edges do not record arena generations

`loopBreakFrame` records separate continuation state for:

```go
continueMoved
continueReasons
continueClosedResources
continueBorrows
continueLocalRefContainers
```

but has no:

```text
continueArenaGenerations
```

`recordLoopContinue()` therefore cannot capture the arena generation at the
`continue` edge.

For:

```sec
while condition {
    arena.Reset()
    continue
}
```

the next condition must observe the reset generation.

There is currently no dedicated edge-state field from which to construct that
header state.

---

# Why post-loop merging does not fix the bug

After loop analysis, Sema does:

```go
a.arenaGenerations =
    mergeLoopArenaGenerations(
        previousArenaGenerations,
        loopArenaGenerations,
        breakFrame.arenaGenerations,
    )
```

That may conservatively affect code **after** the loop.

It does not verify operations on the next iteration.

The bug occurs at the backedge:

```text
iteration N body
-> iteration N+1 condition/body
```

and must be fixed there.

---

# Required correction — loop arena state

## 1. Add arena generation to loop-header/backedge state

Construct a canonical backedge arena-generation state from all reachable
iteration-continuing edges:

- normal body fallthrough;
- every reachable `continue`;
- loop entry where appropriate for first-iteration joining.

Do not use only the original entry generation.

## 2. Record arena generation on `continue`

Extend loop edge facts with the equivalent of:

```go
continueArenaGenerations []map[string]int
```

or, preferably, a unified per-edge flow-state structure that already contains
all tracked domains.

`recordLoopContinue()` must snapshot the generation state exactly where the
continue occurs.

## 3. Include arena state in fixed-point change detection

A loop must be rechecked when the backedge generation differs from the entry/
previous header generation even if:

- no value moved;
- no resource changed;
- no borrow changed;
- no reference-origin map changed.

Arena generation alone is semantically sufficient to invalidate references.

## 4. Replay using the merged header generation

`checkLoopBackedgeFixedPoint()` must initialize the replay with the canonical
header/backedge generation, not `entry.arenaGenerations`.

Stale-reference checking of both:

- the next condition; and
- the next body

must therefore see prior-iteration reset/release operations.

## 5. Apply the correction to both loop families

The shared fixed-point helper is used by:

- `while`;
- `for`.

Regression coverage must include both.

## 6. Prefer one unified loop-edge state

The current design carries parallel collections:

```text
assignments
moved
moveReasons
closedResources
borrows
localRefContainers
arenaGenerations
continueMoved
continueClosedResources
...
```

This makes omission of one semantic domain easy.

Prefer a canonical:

```text
LoopEdgeState
```

containing every flow domain used by loop fixed-point analysis.

Then:

```text
break edge
continue edge
fallthrough backedge
loop exit
```

can all carry the same structured state.

# Required regression tests — arena generations

1. `while true` with `Use(ref); arena.Reset()` rejects the stale use reachable
   on iteration 2;
2. the equivalent `for {}` case is rejected;
3. reset before `continue` reaches the next while condition;
4. reset before `continue` reaches the next while body;
5. equivalent continue tests for `for`;
6. `Arena.Release()` has the same next-iteration invalidation behavior;
7. a loop with no arena generation change does not trigger false stale-reference
   diagnostics;
8. a reset only on a path that cannot reach the backedge does not contaminate
   the next iteration;
9. a reset on one of several reachable backedges is conservatively represented
   at the merged header;
10. break-only reset affects post-loop state as required but does not create a
    nonexistent next iteration;
11. nested loops keep arena-generation backedges associated with the correct
    loop;
12. condition-side arena/reference checks use the same header generation as the
    body.

# Part II — general implementation traceability rule

## New governance rule

Sec implementation code must be traceable back to the normative rulebooks it
implements.

### Main rule

**Where applicable, every source file and every function must contain a comment
identifying the normative rulebook or rulebooks, and the specific rule,
section, or group of rules, that the file/function implements, enforces,
analyzes, validates, or lowers.**

This is a source-governance requirement.

It does not make code comments normative. The rulebooks under `rules/` remain
the normative source.

---

## File-level comments

A source file that implements language/compiler behavior should contain a
file-level traceability comment identifying its principal normative owners.

Example:

```go
// Sec rulebooks:
// - rules/control-flow/flowcontrol_while.md §§28-29
//   Sema/flow analysis and while CFG.
// - rules/memory/ownership.md §...
//   Loop-carried ownership state.
```

A broad file such as `internal/sema/analyzer.go` may cite many books or may
describe its major rulebook domains at file level and place precise references
on individual functions.

The goal is not to place the entire rulebook index in every large file.

The goal is to make it possible to answer:

```text
Which normative rules justify this implementation?
```

without reverse-engineering the whole compiler.

---

## Function-level comments

Where a function exists to implement or enforce normative Sec behavior, its
comment should identify the most precise practical rule ownership.

Example:

```go
// Sec rules:
// - rules/control-flow/flowcontrol_while.md §28
//   Track the nearest active loop and merge reachable continuation state.
// - rules/memory/reference_model.md §...
//   Preserve arena-generation validity across the loop backedge.
func (a *Analyzer) analyzeWhileStatement(...) {
    ...
}
```

For very narrow functions, one rule/section may be enough.

For cross-cutting functions, several references are expected.

For very broad generic infrastructure where exact one-to-one mapping is not
practical, a higher-level rulebook section or grouped rule set is acceptable.

---

## What counts as "applicable"

This rule applies especially to code implementing:

- parser grammar decisions;
- Sema checks;
- ownership/borrowing/lifetime rules;
- control-flow semantics;
- type rules;
- diagnostics mandated by rulebooks;
- Semantic IR facts;
- lowering;
- ABI/FFI behavior;
- target-specific semantic behavior;
- formatter behavior required by normative syntax;
- compiler-known operations.

Pure infrastructure that has no direct normative semantic owner may state that
it is non-normative infrastructure or may omit a rule citation where no useful
mapping exists.

Examples may include some:

- generic container helpers;
- logging;
- test harness plumbing;
- build-system glue.

The exception must not become a reason to omit traceability from semantic code.

---

## Reference form

Prefer stable references in this order:

1. canonical rulebook path;
2. stable rule/section identifier if the book has one;
3. section number and heading;
4. concise quoted/paraphrased rule description when a stable identifier does not
   exist.

Do **not** use source line numbers as the primary reference because line numbers
drift during documentation edits.

Example:

```text
rules/control-flow/flowcontrol_while.md §29 "CFG requirements"
```

is better than:

```text
flowcontrol_while.md lines 470-490
```

---

## Multiple owning rulebooks

A function may implement several independent semantic obligations.

Example:

```text
analyzeWhileStatement
```

may need references to:

- `flowcontrol_while.md`;
- ownership;
- borrowing;
- lifetime/reference validity;
- defer/cleanup rules where relevant.

List all materially relevant normative owners.

Do not force a false single-owner classification.

---

## Comments must remain synchronized

When a code change alters which normative rule is implemented:

- update the implementation;
- update tests;
- update the rule-reference comment in the same change.

When a rulebook is replaced or moved:

- migrate the code references to the new canonical path.

A stale rule citation is a governance defect.

---

## Tests should carry traceability too where practical

Focused semantic regression tests should identify the rule/correction they
exercise.

Recommended forms include:

```go
// Sec rule: rules/control-flow/flowcontrol_while.md §29.
// Regression: correction25.md.
func TestWhileArenaGenerationBackedge(...) {
    ...
}
```

This is especially useful for bug-regression tests.

---

## Implementation-status relationship

`implementation-status.yaml` remains the machine-readable statement of what is
implemented, partial, or planned.

Source comments provide the opposite navigation direction:

```text
rulebook
  -> implementation-status.yaml
  -> source implementation

source implementation
  -> rulebook comment
```

Both are required for maintainable traceability.

---

## Required governance implementation

Add this rule to the canonical compiler implementation/governance documentation,
preferably in the successor/current home of implementation rules rather than
leaving it only in this correction document.

Candidate current documentation ownership includes:

```text

```

or its eventual Markdown replacement.

The canonical governance text should specify:

- file-level rulebook traceability;
- function-level rulebook/rule traceability;
- exceptions for genuinely non-normative infrastructure;
- update requirements when rulebooks change;
- preferred citation form;
- regression-test traceability.
