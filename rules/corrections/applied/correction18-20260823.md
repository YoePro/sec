# Correction 18 — deferred Arena.Reset/Release mutates arena generation during registration-time analysis

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/control-flow/defer.md`
- Document revision: **2.0**
- Created: `2026-08-16`
- Last updated: `2026-08-16`
- Reviewed rulebook baseline: `56be75d`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2.0 states that a defer body is not executed when the defer statement is
registered. Its statements and side effects occur later, when cleanup reaches
the registered defer entry.

Current Sema analyzes the defer body immediately in a copied analysis state, but
does not copy or restore `arenaGenerations`. Compiler-known `Arena.Reset()` and
`Arena.Release()` increment `arenaGenerations` during ordinary expression
analysis.

Therefore a reset/release that exists only inside a deferred cleanup mutates the
ordinary post-registration arena generation and can make references appear stale
before the deferred operation has executed.

---

## Normative requirements

`rules/control-flow/defer.md` revision 2.0 states:

> The defer block is not evaluated when it is registered.

and:

> Its statements execute later.

It also states:

> Side effects therefore occur at cleanup time, not registration time.

A defer may create **future-use/effect obligations** at registration time, but
those obligations are not equivalent to executing the cleanup operation.

For arena invalidation this means:

```text
register defer { arena.Reset() }
```

must record that cleanup will reset the arena at invocation exit.

It must not advance the arena's current generation while ordinary execution
continues before that exit.

---

# Bug — `analyzeDeferStatement()` omits arena generation from its temporary state snapshot

## Affected code

`internal/sema/analyzer.go`

`analyzeDeferStatement()` saves and copies:

```go
previousSymbols := a.symbols
previousConstInts := a.constInts
previousAssigned := a.assigned
previousMoved := a.moved
previousMoveReasons := a.moveReasons
previousBorrows := a.borrows
previousLocalRefContainers := a.localRefContainers
```

and later restores those domains.

It does **not** save/copy/restore:

```go
a.arenaGenerations
```

This differs from ordinary branch analysis, which explicitly snapshots:

```go
previousArenaGenerations := a.arenaGenerations
a.arenaGenerations = copyArenaGenerations(previousArenaGenerations)
...
a.arenaGenerations = previousArenaGenerations
```

The omission matters because defer-body expression analysis can mutate the arena
generation.

---

# Arena.Reset and Arena.Release mutate the live generation immediately

Compiler-known arena call analysis contains:

```go
case "Reset":
    ...
    a.arenaGenerations[receiver.Value]++
```

and:

```go
case "Release":
    ...
    a.arenaGenerations[receiver.Value]++
    a.moved[receiver.Value] = expr.Token
    a.moveReasons[receiver.Value] = "released"
```

The `moved` and `moveReasons` mutations happen inside defer's copied state and
are restored.

The `arenaGenerations` mutation does not.

Thus the two semantic effects of deferred `Release()` are already treated
inconsistently:

```text
moved/released state  -> temporary, restored
arena generation      -> leaks into ordinary execution
```

---

# Observable incorrect behavior

Consider conceptually:

```sec
fn Work() Result[void, AllocationError] {
    let mut arena := new Arena()

    let value := try arena.New[int]()

    defer {
        arena.Reset()
    }

    Use(value)

    return Ok()
}
```

At runtime according to defer revision 2.0:

1. `value` is allocated from generation G;
2. the defer is registered;
3. `Use(value)` executes while arena is still generation G;
4. function exit begins;
5. deferred `arena.Reset()` executes and changes the generation.

`Use(value)` is valid with respect to the deferred reset.

Current Sema instead analyzes the deferred `Reset()` at registration and
increments:

```text
arenaGenerations[arena]
```

immediately.

`value` still carries the generation recorded when it was allocated.

Later identifier use checks:

```go
current := a.arenaGenerations[symbol.Type.ReferenceOriginName]

if symbol.Type.ReferenceOriginGeneration != current {
    ...
    "cannot use %s after arena %s was reset"
}
```

Therefore the ordinary statement after the defer can receive the false
diagnostic:

```text
cannot use value after arena arena was reset
```

even though the reset has not executed yet.

---

# Deferred Release has the same generation leak

The equivalent pattern with:

```sec
defer {
    arena.Release()
}
```

also increments the arena generation during registration-time Sema.

Its temporary `moved["arena"] = ...` state is restored, but the generation
increment remains.

Any arena-derived references used between defer registration and function exit
can therefore be treated as stale because of an operation that has only been
scheduled for future cleanup.

---

# Required correction

## 1. Separate registration-time analysis state from cleanup-time state effects

When analyzing a defer body for:

- type correctness;
- definite assignment at registration;
- lexical name resolution;
- future reads/writes/borrows/moves;
- effect summaries;
- diagnostics;

the compiler must not commit execution-time state mutations to the ordinary
continuation after the defer statement.

At minimum, every mutable flow domain that can be changed by defer-body analysis
must either:

- be analyzed in an isolated snapshot and restored; or
- be represented as deferred cleanup effects without mutating current flow
  state.

## 2. Snapshot and restore arena generation state

As an immediate correctness fix, `analyzeDeferStatement()` must isolate:

```go
a.arenaGenerations
```

in the same manner as branch analysis.

Conceptually:

```go
previousArenaGenerations := a.arenaGenerations
a.arenaGenerations = copyArenaGenerations(previousArenaGenerations)

defer func() {
    ...
    a.arenaGenerations = previousArenaGenerations
}()
```

This prevents `Reset()`/`Release()` inside the analyzed defer body from
invalidating ordinary continuation references.

## 3. Preserve the deferred invalidation as a future cleanup effect

Simply restoring the generation is necessary but not sufficient for complete
defer semantics.

The compiler still needs to remember that when the defer **executes**:

```text
Arena.Reset  -> invalidates prior arena generation
Arena.Release -> invalidates generation and releases arena
```

That fact belongs in the registered cleanup/defer semantic representation and
must participate in exit cleanup ordering.

It must not be represented by mutating the current generation at registration.

## 4. Audit every mutable analysis domain used by defer-body analysis

The current defer snapshot manually enumerates mutable analyzer state.

Audit at least:

- assigned;
- moved;
- move reasons;
- closed/resource state;
- borrows;
- local-reference containers;
- arena generations;
- contained reference origins;
- resource lifecycle state;
- allocation-context state where relevant;
- loop/control-flow side state;
- future effect/cleanup summaries.

For each domain decide explicitly whether defer-body activity is:

```text
registration-time fact
```

or:

```text
cleanup-time execution effect
```

Do not rely on accidental inclusion/exclusion from a copied map list.

## 5. Prefer explicit deferred-effect facts

The durable architecture should represent a defer as something like:

```text
registration point
cleanup body / resolved cleanup operations
referenced places
future borrows/uses
future ownership actions
future arena invalidations
future resource closes
source order
invocation owner
```

Ordinary flow after registration then sees only the restrictions that are true
before cleanup, such as:

- a pending read preventing an incompatible move;
- a required lifetime extension.

Cleanup-time mutations are applied only on cleanup edges.

This also matches the rulebook's Semantic IR requirements.

---

# Resource-state note

`analyzeDeferStatement()` also does not isolate `closedResources`.

A deferred `File.Close()` can therefore update that domain during defer-body
analysis.

That may currently be intentionally exploited to prove that a resource will be
closed by scope exit, because `closedResources` is used primarily by the
scope-exit leak check rather than as a strict "closed right now" state.

Do **not** blindly fix that map by copying it without first separating:

```text
resource is currently closed
```

from:

```text
resource has a registered future close before invocation exit
```

The arena-generation bug demonstrates why those concepts need separate semantic
facts.

This correction proves the arena case. The resource-state model should be
audited as part of the same architectural cleanup.

# Governance reconciliation

The current `frontend.defer-v2` entry correctly records major remaining work for:

- unified defer/destruction ordering;
- Semantic IR cleanup regions;
- dynamic loop registration;
- callable contexts;
- complete backend lowering.

It also marks as implemented:

```text
registration represented when execution reaches the defer statement
```

and:

```text
deferred reads analyzed against ordinary values at cleanup time
```

Those statements should be qualified because registration-time defer-body
analysis currently leaks at least arena generation invalidation into the
ordinary continuation.

Add explicit remaining work for:

```text
isolating cleanup-time state mutations from registration-time flow state
```

including arena reset/release generation invalidation.

Do not downgrade the already implemented:

- block-form parser;
- nested-defer rejection;
- control-transfer diagnostics;
- pending deferred read/move/discard conflict support;
- static MLIR reverse defer ordering within its documented scope.
