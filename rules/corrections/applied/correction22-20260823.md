# Correction 22 — short-circuited boolean RHS commits runtime flow effects during Sema

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/control-flow/flowcontrol_if.md`
- Document revision: **2.0**
- Created: `2026-08-16`
- Last updated: `2026-08-16`
- Reviewed rulebook baseline: `0f92cf4`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2.0 guarantees left-to-right short-circuit semantics for `&&` and `||`.
The right operand is evaluated only when the left operand selects it.

Current Sema's infix-expression analysis always calls `inferExpression()` on the
right operand before it checks whether the operator is logical. That call is not
a pure type query: it can commit ownership, resource, arena, borrow, call-graph,
and other execution-flow effects.

Therefore an RHS that is provably not executed can still mutate the semantic
state as though it had executed.

The maintained backends may lower `&&` and `||` lazily, but correct lowering
does not repair already-corrupted frontend flow facts.

---

## Normative requirements

`rules/control-flow/flowcontrol_if.md` revision 2.0 states:

For:

```sec
left && right
```

`right` is evaluated only when `left` is `true`.

For:

```sec
left || right
```

`right` is evaluated only when `left` is `false`.

The rulebook explicitly says this guarantee may be relied upon for:

- safety;
- side-effect control;
- source-ordered evaluation.

This creates an important compiler distinction:

```text
statically validate RHS
```

is not the same operation as:

```text
commit RHS runtime effects to the current flow path
```

Even if unreachable/short-circuited source is still type-checked, its
execution-time state changes must not be applied to a path on which runtime
evaluation cannot occur.

# Bug — `inferInfixExpression()` evaluates both operands in the same live Sema state

## Affected code

`internal/sema/analyzer.go`

Current structure:

```go
leftType, _ := a.inferExpression(expr.Left)
if leftType.Kind == InvalidType {
    return ...
}

...

rightType, _ := a.inferExpression(expr.Right)
if rightType.Kind == InvalidType {
    return ...
}

...

if isLogicalOperator(expr.Operator) {
    if leftType.Kind != BoolType || rightType.Kind != BoolType {
        ...
    }

    return Type{Name: "bool", Kind: BoolType}, ...
}
```

The right operand is inferred unconditionally before logical-operator semantics
are applied.

`inferExpression()` is stateful. A call expression can select a consuming
parameter and execute:

```go
a.markMovedCallArguments(...)
```

which in turn may do:

```go
a.markExplicitMoveSource(arg)
```

and mark the caller's source unavailable.

Other expression paths can also update:

- resource-close state;
- arena generations;
- borrow state;
- resolved call/effect facts;
- call graph reachability/effects;
- reference-origin facts.

No short-circuit branch state is created around the RHS.

---

# Observable ownership bug — `false && ...`

Conceptually:

```sec
@noCopy
type Token struct {
    id: int
}

fn Consume(-> token: Token) bool {
    return true
}

fn Test() void {
    let token := Token { id: 1 }

    if false && Consume(token) {
    }

    Use(token)
}
```

Runtime semantics:

1. evaluate `false`;
2. short-circuit;
3. do not call `Consume`;
4. `token` remains owned by the caller;
5. `Use(token)` is valid.

Current Sema:

1. infers the left operand;
2. unconditionally infers `Consume(token)`;
3. selected consuming parameter calls `markMovedCallArguments()`;
4. `token` is marked consumed;
5. later `Use(token)` can be rejected.

That is a direct violation of the guaranteed short-circuit semantics.

---

# Symmetric bug — `true || ...`

The same defect occurs for:

```sec
if true || Consume(token) {
}

Use(token)
```

The RHS must never execute.

Current Sema still analyzes it in the live runtime state and can consume
`token`.

---

# Call-graph/effect reachability is also incorrect for proven short-circuit RHS

Ordinary branch analysis has a dedicated reachability mechanism:

```go
a.callGraphPathReachable = previous && reachable
```

before analyzing a statically unreachable branch.

Logical RHS inference does not use equivalent reachability.

A resolved call records itself when:

```go
!a.summaryPass &&
a.callGraphPathReachable &&
recordCall
```

Since `callGraphPathReachable` remains true while an impossible logical RHS is
inferred, a call in:

```sec
false && ExpensiveOrEffectfulCall()
```

can be registered as reachable call-graph/effect activity even though runtime
semantics guarantee it cannot execute.

This can contaminate:

- effect summaries;
- arena-effect summaries;
- concurrency analyses;
- escape/call-graph consumers;
- optimization facts;
- diagnostics built from reachable call sites.

# Required correction

## 1. Give logical operators their own flow-analysis path

Handle `&&` and `||` before ordinary eager binary RHS inference.

Conceptually:

```text
analyze left
validate left is bool

derive RHS reachability:
    left == false for && -> unreachable
    left == true  for || -> unreachable
    otherwise          -> conditionally reachable

analyze/type-check RHS in appropriate isolated/path state
validate RHS is bool

merge execution-flow facts according to short-circuit CFG
```

Do not route logical operators through a generic eager infix path.

## 2. Preserve static type checking without committing impossible runtime effects

For a proven unreachable RHS, the compiler may still perform ordinary static
validation according to Sec's unreachable-code policy.

But it must analyze that expression using a state where execution effects do not
escape into the continuing runtime path.

At minimum isolate/restore:

- moved values and move reasons;
- definite assignment mutations;
- borrows/reference-holder state;
- resource close state;
- arena generations;
- local/contained reference-origin state;
- execution-effect/call-graph reachability.

Diagnostics caused by the source itself may still be retained where canonical
policy requires them.

## 3. Represent conditional RHS execution for non-constant left operands

For:

```sec
left && right
```

the RHS executes only on the `left == true` edge.

For:

```sec
left || right
```

the RHS executes only on the `left == false` edge.

A robust frontend should model this as real control flow, not as eager
expression evaluation.

The resolved condition should expose branch-specific state so later `if`,
`while`, match/guards if added, ownership, and lifetime consumers need not guess.

## 4. Use compile-time boolean facts, not only syntax literals

`analyzeIfStatement()` currently recognizes constant reachability using
`isBoolLiteral()`, which only handles literal `true`/`false`.

Revision 2.0 also refers to compile-time constant boolean conditions.

Where the compiler has a proven compile-time boolean value, the same
short-circuit reachability rule should apply even when the source is not a
literal token.

Do not duplicate constant evaluation inside each control-flow feature; consume a
canonical resolved constant fact.

## 5. Preserve exactly-once and source-order semantics

The fix must keep:

```text
left evaluated exactly once
RHS evaluated at most once
left before RHS
RHS only on its selected edge
```

It must not re-infer an effectful expression multiple times merely to obtain
types and branch state.

Prefer one resolved expression analysis producing immutable type/effect/CFG
facts.

## 6. Feed resolved short-circuit CFG into Semantic IR

Semantic IR should receive explicit control flow for logical operators, e.g.
branch/merge facts or equivalent operations.

Backends should not have to rediscover from raw AST that `&&`/`||` are
short-circuiting.

Frontend ownership and effect facts must agree with that CFG before lowering.

---

# Scope beyond `if`

Although found while auditing `flowcontrol_if.md`, `&&` and `||` are ordinary
expressions.

The same correction applies when logical expressions occur in:

- `while` conditions;
- returned boolean expressions;
- let/assignment RHS;
- function arguments;
- property/accessor expressions;
- match expressions/guards if guards are later introduced;
- any other expression context.

The bug must therefore be fixed in logical-expression analysis, not patched only
inside `analyzeIfStatement()`.

---

# Governance reconciliation

The current `frontend.if-statements-v2` entry lists as implemented:

```text
logical !, &&, and || expressions with left-to-right short-circuit lowering
```

That is accurate only for the backend/control-flow lowering slice.

It is too broad as an end-to-end semantic statement because frontend Sema still
commits RHS execution effects eagerly.

The same governance entry leaves:

```text
focused tests for short-circuit side effects
```

as remaining, but the issue is not merely missing tests: a concrete frontend
state bug exists.

Record separately:

```text
short-circuit backend lowering implemented;
short-circuit-aware frontend ownership/effect/flow-state analysis partial.
```

Do not downgrade ordinary bool operand type checking or existing lazy backend
branch generation.

# Required regression tests

> **Applied 2026-08-23:** Logical operators now use a dedicated Sema flow path.
> Proven-skipped RHS expressions are checked with execution effects isolated;
> conditional RHS state is merged with the bypass path, and unreachable calls
> are excluded from reachable call-graph recording.

## Proven short-circuit ownership

1. `false && Consume(moveOnly)` leaves the source available;
2. `true || Consume(moveOnly)` leaves the source available;
3. `true && Consume(moveOnly)` consumes the source;
4. `false || Consume(moveOnly)` consumes the source when the RHS is evaluated;
5. source is never consumed twice by analysis/lowering.

## Other execution-time state

6. proven short-circuited RHS cannot close a resource in current flow state;
7. proven short-circuited RHS cannot advance an arena generation;
8. proven short-circuited RHS cannot create a live borrow in the continuation;
9. proven short-circuited RHS does not register a reachable call/effect site;
10. actually reachable RHS retains all ordinary ownership/effect behavior.

## Type checking

11. RHS still must have type `bool`;
12. invalid RHS source diagnostics follow canonical unreachable-source policy;
13. left operand must be bool;
14. right operand must be bool when structurally present.

## Conditional/non-literal left side

15. RHS of `left && right` is represented on the true edge only;
16. RHS of `left || right` is represented on the false edge only;
17. branch/continuation ownership merges conservatively across both possible
    short-circuit paths;
18. compile-time constant boolean facts trigger the same reachability as literal
    true/false.

## Cross-context

19. same semantics apply in `while`;
20. same semantics apply in returned/logically nested expressions;
21. nested `a && (b || c)` preserves left-to-right conditional evaluation;
22. Semantic IR and maintained backends consume the same resolved
    short-circuit CFG.
