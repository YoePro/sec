## 2. MD-079 — Direct `unsafe` call form is canonical best practice

2.1. Sec 0.1 accepts **both** a direct single-operation `unsafe` form and an `unsafe` block. The direct form is **recommended best practice when exactly one unsafe call needs authorization**; a block remains appropriate for a sequence of related unsafe operations or a deliberately scoped unsafe expression.

2.2. The canonical direct forms are:

```sec
let value := unsafe pointer.Read()
unsafe pointer.Write(value)
let buffer := unsafe Buffer.FromRawParts(pointer, length)
```

2.3. The direct form authorizes only the immediately prefixed *complete call*. It does not silently make the enclosing statement, its neighboring operations, its surrounding scope, or unrelated calls inside arguments unsafe. Nested unsafe operations require their own explicit authorization unless already inside an explicit unsafe block.

2.4. `rules/foundations/grammar.md` must accept an `unsafe`-prefixed call as an expression and, by the ordinary expression-statement rule, as a statement. The grammar must distinguish this form from the declaration modifier `unsafe fn` and the existing `unsafe { ... }` block. The prefix binds to the following call, not to an arbitrary following binary expression.

2.5. `rules/memory/unsafe.md` § 4 already recognizes the single-operation syntax; retain its safety and caller-obligation semantics. `unsafe` is not an exemption from ordinary type, borrow, ownership, error, visibility, or lifetime checking.

2.6. The formatter must use a single space between `unsafe` and the call, preserve the call's ordinary member/argument formatting, and **must not** rewrite a single-operation form into a block or vice versa solely as a stylistic preference.

2.7. Example scope distinction:

```sec
let value := unsafe pointer.Read() + SafeAdjustment()
```

Only `pointer.Read()` is authorized by the marker. `SafeAdjustment()` remains subject to its own call contract.

2.8. Required tests cover expression, statement, method and indirect callable calls; precedence; nested unsafe requirements; invalid `unsafe` without a call; preservation through formatting; Semantic IR source provenance; and ordinary semantic validation inside the authorized call.

## 3. MD-083 — `TemporalArithmeticError` is the temporal module error type

3.1. `TemporalArithmeticError` is the canonical public error type for `stdlib/temporal/arithmetic` in Sec 0.1. Do not define another module-local type named `ArithmeticError`.

3.2. The compiler-known core `ArithmeticError` retains its own identity and purpose. It must not be redeclared, shadowed as a competing public type, or repurposed to express temporal-library domain failures.

3.3. The temporal type's public definition may be **extended later** as the implementation of `stdlib/temporal` grows, through normal revision of the temporal rulebooks and exact source declarations. ## 4. MD-089 — Slice Place rendering in diagnostics

4.1. The diagnostic rendering of a slice projection must distinguish a **runtime-unknown bound** from a **compile-time-known bound**. This is display/provenance information; it does not change slicing semantics.

4.2. Canonical presentation rules for an exclusive-upper-bound slice are:

| Known fact | Diagnostic rendering |
| --- | --- |
| Unknown start | `*` in the start position |
| Known start of zero | Omit the start |
| Unknown end | Open-ended `..` form |
| Known exclusive end | `..<N` with exact `N` |

4.3. Examples of the critical distinction:

```text
values[*..<3]   runtime-unknown start, known exclusive end 3
values[..<3]    constant start 0, known exclusive end 3
```

4.4. Diagnostic printing must not show `values[..<3]` for an unknown start; doing so falsely implies proof that the start equals zero. Known bounds are printed exactly; unknown bounds must not be guessed.

4.5. Apply the same rendering rule consistently wherever a projected Place is presented in diagnostics, notes, traces, or related compiler tooling that uses that diagnostic renderer.

4.6. Synchronize `rules/memory/borrowing.md` and `rules/tooling/diagnostics.md`. Tests must distinguish zero, positive constant, unknown start, known end, unknown end, and combined symbolic bounds without changing the underlying Place identity.

## 5. MD-091 — Byte-to-string decoding belongs to `stdlib/str`

### 5.1 Normative library boundary

5.1.1. **Public conversion from a `byte[]` sequence to a `string` is owned by `stdlib/str`, not by core and not by the compiler-known-member registry.** The reason is that materializing a string from a byte sequence allocates or otherwise requires explicit result storage. This is a standard-library text-decoding operation.

5.1.2. Remove `string.FromByteArray(...)` from the public core surface and compiler-known associated-function registry. It must not remain as a second public core entry point, even as an alias of the stdlib function.

5.1.3. The public standard-library APIs already supplied by the owner are:

```sec
// Decode a borrowed byte sequence as strictly validated UTF-8.
fn FromByteArray(value: ref byte[]) Result[string, StringError]

// Decode a borrowed byte sequence while replacing malformed UTF-8.
fn FromByteArrayLossy(value: ref byte[]) Result[string, CollectionError]
```

These declarations belong to `sec/stdlib/str/collect.sec` (logical import/module: `str`). Preserve these exact signatures unless a subsequent explicit API revision changes them.

5.1.4. `FromByteArray` validates UTF-8 and returns `Err(StringError.InvalidUtf8(index))` for malformed input. The owner's supplied validation loop rejects invalid lead bytes, malformed continuation bytes, overlong sequences, surrogate code points, values beyond U+10FFFF, and incomplete sequences. No partial or invalid `string` may be returned.

5.1.5. `FromByteArrayLossy` uses the stdlib's defined replacement policy for malformed sequences rather than exposing invalid UTF-8. Its declared `CollectionError` continues to govern its fallible result-storage contract; this correction does not invent a new error type or change its signature.

5.1.6. Both functions borrow the input and must preserve its contents and ownership. The resulting `string` must satisfy the canonical valid-UTF-8 invariant and the active ownership/allocation rules.

### 5.2 `byte[].ToString()` is not UTF-8 decoding

5.2.1. `byte[].ToString()` must **not** interpret arbitrary byte contents as string text. `ToString()` remains a general representational/formatting operation, distinct from explicit decoding.

5.2.2. For the ordinary dynamic `byte[]` type, the canonical type-summary representation is the text `byte[]`, as proposed by the owner. Where the universal `ToString()` signature applies, the call therefore produces:

```sec
// The content is not UTF-8-decoded by ToString().
let description := try bytes.ToString() // "byte[]"
```

5.2.3. Byte fixed arrays and borrowed byte-sequence views must also **not** UTF-8-decode merely because their element type is `byte`. Their existing collection/fallback formatting contracts remain applicable where not specifically replaced here. No such `ToString()` overload may advertise itself as a byte-to-text decoder.

5.2.4. Preserve the already-decided universal `ToString()` signature:

```sec
fn ToString() Result[string, StringError]
```

Producing even the type-summary string may use the normal `ToString` storage/error contract. This correction does **not** make `ToString()` infallible or establish a second result type.

5.2.5. `rune` and `char` scalar/sequence conversion semantics are not changed by this **byte-specific** correction. Do not silently delete or rewrite their independently specified members while implementing MD-091. Audit related allocating associated constructors separately against the established core/stdlib allocation boundary.

### 5.3 Required `FromByteArray` implementation change

5.3.1. The owner's current `FromByteArray` source ends with:

```sec
// The complete array is now known to contain valid UTF-8.
return value.ToString()
```

This must be replaced. After § 5.2, that expression means formatting the `byte[]` type, **not** constructing a string containing the decoded UTF-8 bytes.

5.3.2. The stdlib implementation must construct a valid `string` **after successful validation**, using a valid string-materialization path available to the standard library. It may use a rune-based encoding strategy if appropriate, but **must not be required** to allocate an intermediate `rune[]` solely to satisfy this correction. Nor may it introduce an unchecked public byte-to-string cast or an alternate public core constructor.

5.3.3. If the existing implementation cannot materialize a string from validated bytes using already supported language/runtime facilities, compiler/stdlib integration must supply the **narrow implementation capability** required for that operation. Its concrete internal spelling must be grounded in the existing allocation and string-representation contracts before it is committed. Do not fabricate a new public `core` API as a workaround.

5.3.4. Validation and materialization must not create a second *publicly callable* decode path in core. The stdlib API owns the caller-visible validity, allocation, ownership and error guarantees.

5.3.5. The public API also must not be bypassed with `string(bytes)`, a legacy `string.FromByteArray(bytes)`, or a new implicit `byte[]` → `string` conversion.

### 5.4 Synchronization and test obligations

5.4.1. Synchronize `rules/library/core-library.md` § 1.3, § 2 examples, § 3 examples, § 5.2 and any further references to `string.FromByteArray` or UTF-8-decoding `byte[].ToString()`.

5.4.2. Synchronize `rules/compiler/compiler_known_members.md`: remove public compiler-known association/registry references to `string.FromByteArray`; amend its byte-sequence `ToString` semantics, byte round-trip examples, and any compiler-known/IR/diagnostics contracts that currently equate `ToString` with UTF-8 decoding. Preserve unrelated `ToString` and string-conversion contracts.

5.4.3. Synchronize `sec/stdlib/str/stdlib_str.md` and `sec/stdlib/str/collect.sec` with the stdlib-owned APIs and the actual string-materialization path, using the standard structured LSP documentation contract. Do not claim the source implementation updated until it has been changed and tested.

5.4.4. Required regression tests include:

- Strict decoding: empty input; ASCII; valid 2-, 3-, and 4-byte UTF-8; embedded U+0000; invalid lead byte; invalid continuation; truncated sequence; overlong encoding; surrogate encoding; >U+10FFFF; exact error byte offset.
- Lossy decoding: malformed input produces valid UTF-8 according to the existing replacement policy; successful input is unchanged; storage failure remains in its declared error family.
- `byte[].ToString()`: valid-looking UTF-8 and malformed bytes both follow the type-summary contract and never act as a decoder.
- Type checking: no public core `string.FromByteArray`, no implicit byte-array-to-string conversion, and no accidental compiler-known alias of the stdlib function.
- Ownership: neither conversion mutates, adopts, or consumes the borrowed input; output remains valid independently.
- Round-trip: `str.FromByteArray(ref text.ToByteArray())` (with correct temporary/borrowing and error handling in executable tests) reconstructs equivalent content; round-trip does **not** use `byte[].ToString()`.

5.4.5. Do not silently assume that a compiler-known string-materialization path exists. Verify its real implementation while integrating this correction. A passing source-level UTF-8 validator alone does not demonstrate that the new conversion path is implemented.

## 6. MD-094 — One primary diagnostic for a constant-invalid slice range

6.1. Compile-time-provable invalid slice bounds follow the same ordered classification as runtime `RangeError`:

1. Negative or otherwise invalid endpoint.
2. Start after end.
3. Endpoint beyond the source bound.

6.2. For one invalid range expression, the compiler issues **one primary diagnostic** for the first provable failure in that precedence order. It does not issue several independent primary diagnostics for lower-priority failures of the same range.

6.3. For example, with a fixed four-element array, `fixed[9..<7]` has a descending range and out-of-bounds endpoints. The primary diagnostic is **start after end**, not an additional independent bounds-overflow error.

6.4. A constant start-after-end condition remains diagnosable at compile time even when the collection's length is unknown at compile time. A missing length proof does not suppress a contradiction between two known range endpoints.

6.5. The compiler may add contextual diagnostic **notes** identifying related facts, but those notes are not additional primary errors and must not change the fixed precedence.

6.6. Synchronize `rules/collections/collections.md` and `rules/mlir/packages/sec-mlir-dialect_package16.md` §§ 18–19. Test all three precedence tiers, known/unknown source lengths, and deterministic diagnostic counts/order.

## 7. MD-097 — Trailing single-line block comments align like `//`

7.1. A one-line `/* ... */` appearing **after code on the same source line, ending that line**, is a trailing comment for formatter purposes, exactly like a trailing `// ...` comment.

7.2. Both comment spellings share the same structural trailing-comment column and the same alignment-group behavior. A trailing block comment does **not** terminate the compatible declaration or enum explicit-value group.

7.3. Example of the intended column treatment:

```sec
enum Example {
    Short     = 1  /* first */
    LongerKey = 20 // second
    End       = 3  /* third */
}
```

7.4. A block comment followed by more code on that line is an **inline comment**, not a trailing comment. A block comment beginning after a line break is a **standalone comment**. Their existing handling remains unchanged.

7.5. Existing width limits, column-padding policy, group boundaries, and enum-specific exceptions continue to apply. This decision does not override separate open questions about maximum trailing-comment padding.

7.6. Amend `rules/tooling/formatter.md` § 9(8)/§ 9(8b), § 12(4)–§ 12(9), and the relevant enum declaration notes. Test groups mixing `//` and `/* ... */`, groups that would otherwise be split, inline-vs-trailing classification, standalone boundaries, limit handling, and formatter idempotence.

7.7. MD-097 is a clarification of the **already chosen structural alignment rule**, not a justification for a second independent comment-alignment model.
