# Correction 28 — Arena Reset/Release dependency legality is not enforced, and allocation storage-origin taxonomy is stale

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-20`
- Primary rulebook: `rules/memory/allocation.txt`
- Arena-specific authority: `rules/memory/arena.md`
- Rulebook generation: older/living allocation book with later synchronization
- `allocation.txt` explicitly delegates current Arena semantics to the canonical Arena rulebook where applicable
- `arena.md` status: canonical Arena rulebook for Sec 0.1

## Classification

This correction contains:

1. a **software bug**: `Arena.Reset()` and `Arena.Release()` do not validate
   whether validity-preserving dependencies cross the operation point;
2. a **governance bug**: generation tracking/stale-use diagnostics are described
   without recording the missing operation-point legality proof;
3. a **rulebook consistency correction**: `allocation.txt` still contains an
   obsolete `StorageOrigin` taxonomy superseded by `storage.md` and the later
   fixed-address rules.

This correction does not change intended Sec semantics.

---

# Authority

`allocation.txt` remains normative for general allocation semantics.

`rules/memory/arena.md` explicitly states that it is the canonical Arena
rulebook for Sec 0.1 and that all normative Arena-specific semantics belong
there.

Therefore, for Reset/Release dependency rules, `arena.md` is authoritative.

---

# Bug 1 — `Arena.Reset()` does not prove that validity-preserving dependencies are dead

## Normative requirement

`arena.md` states:

```text
Reset is valid only when no validity-preserving dependency crosses the reset
point.
```

This includes, as applicable:

```text
owned values stored in the Arena;
shared references;
mutable references;
slices;
nested Arenas;
containers using Arena backing;
closure captures;
task captures;
thread arguments;
deferred operations;
foreign-retained dependencies;
strong handles;
returned values that remain live.
```

The rulebook explicitly requires **non-lexical lifetime analysis**.

Therefore this is valid:

```sec
let values := try arena.Alloc[int](100)
Process(values)

// Last use has passed.
arena.Reset()
```

while this is invalid:

```sec
let values := try arena.Alloc[int](100)
arena.Reset()
Process(values)
```

The important semantic question is not whether the binding remains lexically in
scope.

It is whether its validity-preserving dependency remains live across the Reset
point.

---

## Current implementation

In `internal/sema/analyzer.go`, `Arena.Reset()` currently performs:

```go
case "Reset":
    ...
    if !a.canWriteThroughSymbol(symbol) {
        ...
    }

    a.arenaGenerations[receiver.Value]++
    a.recordArenaEffect(
        ArenaEffectReset,
        receiver.Value,
        member.Property.Token,
        false,
    )

    return Type{Name: "void", Kind: VoidType}, ...
```

The implementation checks:

- no generic arguments;
- no runtime arguments;
- mutable Arena access.

It does **not** check whether any live validity-preserving dependency crosses the
Reset point.

It simply advances the generation.

---

## Why stale-generation diagnostics are not enough

Current Sema can later reject:

```sec
let values := try arena.Alloc[int](100)
arena.Reset()
Process(values)
```

because `values` still carries the old Arena generation.

That is useful, but it is not equivalent to validating Reset.

The canonical rule says the Reset operation itself is legal only if no
validity-preserving dependency crosses it.

A compiler that merely waits for a later stale use has incomplete semantics.

For example, a dependency may remain semantically live because of:

- a deferred use;
- a captured reference;
- a nested Arena;
- a retained container;
- a task/thread dependency;
- a strong handle;
- another dependency tracked outside an immediate later identifier use.

Even in a simpler local case, the Reset legality should be proved at the reset
point using NLL/dependency information, not inferred retrospectively from
whether a stale reference is eventually mentioned again.

# Bug 2 — `Arena.Release()` has the same missing dependency proof

## Normative requirement

`arena.md` states:

```text
Ordinary safe dependencies may not cross Release.
```

Example:

```sec
let values := try arena.Alloc[int](100)
arena.Release()
Process(values)
```

is invalid.

`Release()` is stronger than Reset:

```text
it consumes the Arena owner;
terminates the ArenaDomain;
invalidates validity-preserving dependencies;
ends borrowed backing access;
permits no later Arena use.
```

Weak stale-capable handles are a distinct exception because their contract does
not require continued storage validity.

---

## Current implementation

Current Sema performs:

```go
case "Release":
    ...
    if !a.canWriteThroughSymbol(symbol) {
        ...
    }

    a.arenaGenerations[receiver.Value]++
    a.moved[receiver.Value] = expr.Token
    a.moveReasons[receiver.Value] = "released"

    a.recordArenaEffect(
        ArenaEffectRelease,
        receiver.Value,
        member.Property.Token,
        false,
    )
```

Again, no validity-preserving dependency check occurs before termination of the
ArenaDomain.

The Arena owner itself is marked consumed correctly, but dependent safe values
are not used as a precondition for Release legality.

---

# Required software correction

## 1. Add canonical Arena dependency-liveness validation

Before committing Reset or Release, Sema must determine whether any
validity-preserving dependency is live across that operation.

Conceptually:

```text
validate Arena mutation authority
resolve ArenaDomain
collect validity-preserving dependencies
apply non-lexical last-use information
reject operation if any blocking dependency crosses the point
only then commit epoch/domain mutation
```

Do not use lexical scope alone.

---

## 2. Distinguish blocking dependencies from stale-capable identities

A dependency blocks Reset/Release when its contract requires the underlying
Arena allocation/domain to remain valid.

Examples include ordinary safe refs, slices, nested Arenas, and strong handles.

Weak or explicitly stale-capable handles do not block merely because the handle
identity remains live.

The dependency checker must consume the reference/handle contract, not just ask
whether a symbol exists.

---

## 3. Integrate deferred use

A deferred operation that will access Arena-backed storage after the proposed
Reset/Release is a blocking dependency unless cleanup ordering proves that the
dependent use happens first.

This must compose with the defer ordering rules rather than only with ordinary
lexical liveness.

Do not duplicate the separate registration-time arena-generation bug already
tracked by `correction18.md`.

---

## 4. Integrate control-flow fixed points

Dependency liveness must use the corrected control-flow state across:

- if;
- switch;
- match;
- for;
- while;
- break;
- continue;
- defer cleanup edges.

Do not duplicate the separate loop arena-generation backedge defect already
tracked by `correction25.md` or switch CFG defect tracked by
`correction24.md`.

Those corrections improve the state that this Reset/Release legality check must
eventually consume.

---

## 5. Preserve the existing epoch mechanism

The current generation/epoch mechanism remains useful.

After a valid Reset:

```text
old ordinary references are invalid;
new allocations receive the new epoch.
```

After Release:

```text
the Arena owner is consumed;
the ArenaDomain terminates.
```

The correction adds the missing legality proof **before** committing those state
changes.

It does not replace generation tracking.

---

# Governance bug — `analysis.arena-allocation` overstates the Reset boundary

The current governance entry marks as implemented:

```text
semantic validation of mutable Arena.Reset calls
```

and:

```text
rejection of arena-backed references and slices after a reset advances their
generation
```

The second statement is substantially true in the represented local-generation
subset.

The first is too broad.

Current Reset validation covers syntax/arity/mutability and generation
advancement, but not the canonical requirement that no validity-preserving
dependency crosses the Reset point.

Similarly, Release ownership consumption exists but dependency legality is not
documented as missing.

## Required governance wording

Record separately:

```text
implemented:
    Arena Reset/Release syntax, receiver mutability, generation/domain mutation,
    stale-generation checking in represented paths

partial:
    operation-point proof that no validity-preserving dependency crosses Reset
    or Release
```

Also qualify:

```text
conservative generation-state merging across if, switch, match, for, while,
and break
```

because already-audited defects affect that broad claim:

- `correction18.md` — deferred Reset/Release generation leaks into registration
  flow;
- `correction24.md` — switch case/fallthrough state is not canonical;
- `correction25.md` — loop backedge/continue arena generations are omitted.

Do not duplicate those bugs here; only reconcile the governance statement.

# Existing `Arena.Alloc[T]` omissions are already documented

`allocation.txt` requires safe `Arena.Alloc[T]` to validate:

```text
T is sized;
T is trivially destructible;
T has a compiler-defined default;
count * sizeof(T) overflow;
alignment.
```

Current `Arena.Alloc[T]` Sema does not implement that complete set.

However root governance already lists:

```text
sized, trivially-destructible, default-value, overflow, and alignment checks
required by the safe allocation contract
```

under remaining work.

Therefore these are **not new correction28 software findings**.

They remain valid known implementation gaps.

# Rulebook defect — `allocation.txt` contains a stale StorageOrigin taxonomy

## Current text in `allocation.txt`

The book currently says minimum storage origins are:

```text
Inline
Static
Arena
External
Foreign
FixedAddress
```

That taxonomy is obsolete.

---

## Later canonical storage model

`rules/memory/storage.md` defines independent storage properties and canonical
`StorageOrigin` values:

```text
Automatic
Static
ThreadLocal
Arena
AllocatorBacked
Unknown
```

It explicitly states that these are **not** storage origins:

```text
Inline
Stack
External
CallerProvided
CompilerTemporary
Mapped
Foreign
FixedAddress
Device
SharedMemory
Volatile
Atomic
Pinned
```

Those concepts belong to other storage properties/contracts.

The newer storage model is semantically stronger because it deliberately avoids
collapsing:

```text
origin
backing relation
reclamation authority
address stability
memory space
invalidation domain
validity epoch
```

into one enum.

---

## Fixed-address rule confirms the newer model

`rules/platform/fixed-address-bindings.md` explicitly says an addressed binding:

```text
uses AddressStability.Fixed;
does not introduce a new storage origin.
```

Its storage origin remains independently classified.

Therefore `FixedAddress` in the old `allocation.txt` origin list directly
conflicts with the later rule.

---

# Required rulebook correction

Replace the `allocation.txt` storage-origin subsection with a delegation to the
canonical storage rulebook.

Recommended shape:

```text
Allocation and Arena analysis must preserve the canonical storage metadata
defined by rules/memory/storage.md.

Arena-allocated storage has StorageOrigin.Arena.

Other properties such as external backing, foreign provenance, fixed address,
reclamation authority, or address stability are represented by their
corresponding independent storage properties and must not be encoded as
StorageOrigin values.
```

Do not duplicate the complete canonical enum in `allocation.txt` unless there is
a strong reason; delegation reduces future drift.

# Required regression tests

## Reset

1. Arena-backed ref used after Reset is rejected;
2. Arena-backed slice used after Reset is rejected;
3. Reset after the last use of an Arena-backed reference is valid;
4. a lexically in-scope but NLL-dead reference does not block Reset;
5. a reference whose next use occurs after Reset blocks Reset at the reset point;
6. mutable and shared dependencies both block while live;
7. nested Arena dependency blocks parent Reset;
8. Arena-backed container dependency blocks Reset;
9. deferred future use blocks Reset unless cleanup order proves the use precedes
   Reset;
10. strong handle blocks Reset;
11. weak stale-capable handle does not block Reset.

## Release

12. Release with no crossing safe dependencies is valid;
13. live Arena-backed ref blocks Release;
14. live Arena-backed slice blocks Release;
15. nested Arena blocks parent Release;
16. NLL-dead dependency does not block Release;
17. weak stale-capable handle may survive Release as a non-resolving identity;
18. after valid Release the Arena owner is consumed;
19. double Release remains invalid.

## Control flow

21. unreachable dependency path does not block;
22. loop-carried dependency is represented at the operation point;
