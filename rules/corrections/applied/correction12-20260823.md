# Correction 12 — write-only properties are readable and can participate in compound assignment

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/declarations/properties.md`
- Document revision: **2.0**
- Created: `2026-08-13`
- Last updated: `2026-08-13`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2.0 explicitly allows write-only properties, but states that a property
without a getter is not readable. It also requires both a getter and a setter
for compound assignment.

Current Sema records `HasGetter` correctly, but ordinary property-expression
inference returns the property type without checking that flag. The same
unchecked read path is then reused by compound assignment.

Consequently a write-only property can be:

1. read as an ordinary expression; and
2. used as the read side of `+=`, `-=`, and other compound assignment even
   though no getter exists.

---

## Normative requirements

`rules/declarations/properties.md` revision 2.0 states:

> A property without a getter is not readable.

It separately states:

> A property without `get` is write-only.

For compound assignment:

> Compound assignment to a property uses the property's getter and setter
> semantics.

and requires both:

- a readable property value; and
- an assignable setter.

It further states:

> A write-only property cannot be the target of compound assignment because no
> getter exists.

These are direct frontend semantic requirements and do not depend on property
lowering being implemented.

---

# Bug 1 — ordinary member read ignores `HasGetter`

## Affected code

`internal/sema/analyzer.go`

Properties are registered with the correct semantic flag:

```go
target.Properties = append(target.Properties, Property{
    Name:      property.Name.Value,
    Type:      propertyType,
    Token:     property.Name.Token,
    Fallible:  property.Setter != nil && property.Setter.Fallible,
    Error:     errorType,
    HasGetter: property.Getter != nil,
    HasSetter: property.Setter != nil,
})
```

However ordinary member inference later performs:

```go
if property, ok := lookupProperty(objectType, expr.Property.Value); ok {
    return property.Type, true
}
```

There is no:

```text
property.HasGetter
```

check.

Therefore the semantic fact that the property is write-only is discarded at
the use site.

---

## Example

```sec
type Sink struct {
    _value: int,
}

impl Sink {
    property Value: int {
        set next {
            self._value = next
        }
    }
}

fn Read(sink: Sink) int {
    return sink.Value
}
```

`Value` has no getter.

Revision 2.0 requires the read to be rejected.

Current member inference can type `sink.Value` as `int`.

---

# Bug 2 — unqualified property reads inside the defining `impl` have the same problem

Identifier inference inside an implementation contains the equivalent path:

```go
if a.currentImplTarget != "" {
    if target, ok := a.types[a.currentImplTarget]; ok {
        if property, ok := lookupProperty(target, expr.Value); ok {
            a.bindDefinition(expr.Token, property.Token)
            return property.Type, ...
        }
    }
}
```

Again, `HasGetter` is not checked.

Thus a write-only property can also be read by unqualified member syntax inside
its implementation.

For example:

```sec
impl Sink {
    property Value: int {
        set next {
            self._value = next
        }
    }

    fn CopyValue() int {
        return Value
    }
}
```

must be rejected because `Value` has no getter.

---

# Bug 3 — compound assignment checks only the setter

## Affected code

`analyzeMemberAssignmentStatement()` begins by inferring the member expression:

```go
targetType, ok := a.inferMemberExpression(member)
```

which currently succeeds for a write-only property.

It then checks:

```go
property, propertyOK := a.lookupPropertyOnMember(member)

if propertyOK && !property.HasSetter {
    a.addErrorAtToken(..., "property %s has no setter", ...)
    return
}
```

but never checks:

```text
stmt.Operator != "=" && !property.HasGetter
```

The compound-assignment path later calls:

```go
assignmentType, valid =
    a.inferCompoundAssignmentType(
        stmt.Operator,
        targetType,
        valueType,
        stmt.Value,
    )
```

Therefore the compiler can conceptually treat:

```sec
sink.Value += 1
```

as if it had read an `int` from `Value`, even though no getter exists.

That directly contradicts revision 2.0.

---

# Required correction

## 1. Distinguish property read from property lookup

`lookupProperty()` should remain capable of returning metadata for write,
conformance, diagnostics, and tooling.

The semantic expression-read path must separately validate readable access.

For example, introduce a helper conceptually equivalent to:

```text
resolveReadableProperty(receiverType, name)
```

which:

1. finds the property;
2. binds definition metadata;
3. rejects the access if `HasGetter == false`;
4. returns the property type only when readable.

Do not make `lookupProperty()` itself reject write-only properties because
assignment analysis still needs to find them.

## 2. Apply the read check to every property-expression form

At minimum:

- `object.Property`;
- unqualified property use inside the defining implementation;
- property access through supported wrapper/guard forwarding paths;
- future static property reads;
- interface-value property reads once interface runtime access is implemented.

Any expression that semantically reads the property must require a getter.

## 3. Make compound assignment require both accessors

For a property target and:

```text
+= -= *= /= %= &= |= ^= <<= >>= ...
```

require:

```text
HasGetter == true
AND
HasSetter == true
```

before operator/type analysis proceeds.

A missing getter should receive a focused diagnostic such as:

```text
property Value has no getter and cannot be used with +=
```

or the canonical equivalent.

The exact wording is diagnostic policy; the semantic requirement is mandatory.

## 4. Preserve ordinary simple assignment

Simple assignment:

```sec
sink.Value = newValue
```

must continue to require only a setter.

A write-only property is specifically useful because this operation is valid.

Do not accidentally require a getter for `=`.

## 5. Preserve fallible setter behavior

For:

```sec
property Value: int {
    try set next {
        ...
    }
}
```

simple assignment still requires `try`.

Compound assignment requires:

1. getter;
2. fallible setter handling;
3. exact-once getter/setter behavior.

The existing governance item for **complete fallible compound assignment**
remains separate and partial.

## 6. Record explicit resolved property access facts

When property lowering is implemented, Semantic IR should receive the resolved
access kind rather than rediscovering it:

```text
PropertyRead
PropertyWrite
FalliblePropertyWrite
PropertyCompoundUpdate
```

Frontend Sema must not emit a `PropertyRead` fact for a property without a
getter.

---

# Governance reconciliation

The current `frontend.properties` entry lists as implemented:

```text
property member access type inference and self-member resolution
```

That statement is too broad.

Member lookup/type resolution exists, but read-access validation is incomplete
because write-only properties are still inferable as readable expressions.

The entry also lists:

```text
complete getter and setter body analysis using ordinary function-body rules
```

which is not implicated by this correction.

Keep the existing remaining item:

```text
complete fallible compound-assignment behavior
```

but add the more basic missing getter requirement separately, because it applies
even to infallible properties and is already a revision-2.0 frontend rule.

---

# Required regression tests

Add tests covering at least:

## Ordinary reads

1. read-write property can be read;
2. getter-only property can be read;
3. write-only property member read is rejected;
4. write-only property unqualified read inside its implementation is rejected;
5. getter side-effect semantics remain represented as a property read, not field
   access.

## Simple assignment

6. write-only property with infallible setter accepts `=`;
7. read-only property rejects `=`;
8. write-only fallible property accepts `try ... = ...`;
9. write-only fallible property rejects ordinary `=` without `try`.

## Compound assignment

10. read-write infallible property may use `+=` when the operator/types are
    otherwise valid;
11. getter-only property rejects `+=` because there is no setter;
12. write-only property rejects `+=` because there is no getter;
13. write-only property rejects every other supported compound assignment for
    the same reason;
14. fallible read-write property requires `try` for compound assignment;
15. compound assignment does not evaluate the receiver, getter, or RHS merely
    to diagnose an absent accessor in lowering.

## Interface/tooling boundary

16. interface conformance still distinguishes required getter from required
    setter;
17. hover/completion may show a write-only property but expression validation
    still rejects reading it;
18. future resolved Semantic IR never contains PropertyRead for a property whose
    semantic metadata has `HasGetter == false`.

## Applied

Applied on 2026-08-23 to `internal/sema/analyzer.go`, focused property tests,
and `implementation-status.yaml`. Read authorization is separate from raw
property lookup, represented member and unqualified reads require a getter, and
compound assignment requires both accessors while simple assignment remains
setter-only. Future static/interface runtime access and explicit IR access-kind
facts remain tracked as broader property implementation work.
