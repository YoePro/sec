# Correction 23 — statement-match termination analysis duplicates and contradicts canonical match coverage

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/control-flow/flowcontrol_match.md`
- Document revision: **2.0**
- Created: `2026-08-17`
- Last updated: `2026-08-17`
- Reviewed rulebook baseline: `56be75d`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2.0 states that an exhaustive match whose every reachable arm
terminates is itself non-continuing.

The main match analyzer already has a substantially complete canonical coverage
implementation for:

- Result;
- union and Option variants;
- closed enum numeric value classes;
- open bit-backed enum domains;
- guarded versus unguarded coverage;
- catch-all.

However function-return and block-termination analysis does not consume that
resolved coverage result. Instead `matchStatementDefinitelyReturns()` performs a
second, older coverage analysis with materially different semantics.

That duplicate analysis:

1. has no union/Option exhaustiveness case at all; and
2. checks enum member **spellings** rather than normalized numeric value classes.

As a result, a statement match can be accepted as exhaustive by the canonical
match analyzer but still be treated as fallthrough-capable by function return
analysis.

---

# Normative requirement

`rules/control-flow/flowcontrol_match.md` revision 2.0 states:

> An exhaustive match whose every arm terminates is itself non-continuing.

It also states that enum exhaustiveness is based on:

> distinct reachable declared values, not merely member spellings.

and:

> The compiler must normalize enum aliases before coverage analysis.

The rule applies to every supported match subject, including:

- ordinary unions;
- Option;
- Result;
- ordinary enums;
- open bit-backed enums when the complete domain is covered.

There must be one semantic answer to:

```text
Is this match exhaustive and non-continuing?
```

Return analysis, reachability, Semantic IR, and lowering must not recompute
different answers from raw AST spelling.

# Bug 1 — exhaustive union/Option statement matches are never recognized as terminating without catch-all

## Affected code

`internal/sema/analyzer.go`

Function return checking uses:

```go
if !function.Initializer &&
   !a.blockDefinitelyReturns(fn.Body) &&
   function.ReturnType.Kind != VoidType &&
   function.ReturnType.Kind != NeverType {
    a.addErrorAtToken(
        fn.Name.Token,
        "function %s must return %s",
        fn.Name.Value,
        typeDisplayName(function.ReturnType),
    )
}
```

For a `MatchStatement`, the analyzer-specific return helper calls:

```go
a.matchStatementDefinitelyReturns(matchStmt)
```

That helper accumulates unguarded pattern kinds and variants, then handles only:

```go
if catchAll {
    return true
}

if subjectType.Kind == ResultType && len(subjectType.TypeArgs) == 2 {
    return seenKinds["Ok"] && seenKinds["Err"]
}

if enumValues, ok := a.enumValuesForType(subjectType); ok {
    ...
    return true
}

return false
```

There is **no `UnionType` case**.

But `Option[T]` is represented as a compiler-known union, and ordinary tagged
unions are also `UnionType`.

Therefore:

```sec
fn Read(option: Option[int]) int {
    match option {
        Some(value) => return value
        None => return 0
    }
}
```

is semantically exhaustive and every arm returns.

The canonical match analyzer knows this because `matchCoverageComplete()` does:

```go
if subjectType.Kind == UnionType {
    for _, variant := range subjectType.UnionVariants {
        if !seenVariants[variant.Name] {
            return false
        }
    }
    return true
}
```

But `matchStatementDefinitelyReturns()` does not use it and falls through to:

```go
return false
```

The enclosing non-void function can therefore receive a false
`function ... must return ...` diagnostic.

The same defect applies to ordinary user unions.

# Bug 2 — enum alias normalization is lost in statement-match return analysis

## Canonical match coverage

The main analyzer stores enum coverage by numeric value:

```go
key := info.EnumNumericValue.String()
seenEnumValues[key] = info.EnumCaseName
```

and `enumNumericDomainCovered()` checks the set of distinct numeric value
classes.

That correctly implements revision 2.0.

There is already a regression test proving this behavior for a bit-backed enum
with aliases:

```sec
enum Alias: bit[1] {
    Off = 0,
    Disabled = 0,
    On = 1,
}

return match value {
    Alias.Off => 0
    Alias.On => 1
}
```

The match is exhaustive even though `Disabled` is not written, because it is an
alias of numeric value 0.

## Return helper uses member names instead

`matchStatementDefinitelyReturns()` does not retain `EnumNumericValue`.

It records:

```go
seenVariants[info.Variant] = true
```

then calls:

```go
enumValues, ok := a.enumValuesForType(subjectType)
```

and requires every returned string to occur in `seenVariants`.

`enumValuesForType()` returns `typ.EnumValues`.

Enum construction populates that slice with every declared member spelling:

```go
typ.EnumValues = append(
    typ.EnumValues,
    value.Name.Value,
)
```

Thus the alias enum above yields conceptually:

```text
Off
Disabled
On
```

A statement match containing only:

```text
Alias.Off
Alias.On
```

is correctly exhaustive by numeric-domain semantics but the return helper asks
whether `Disabled` also appeared.

That is impossible to satisfy cleanly because the canonical match analyzer
rightly treats a separate `Alias.Disabled` arm as duplicate/unreachable numeric
coverage.

So for aliased enums the secondary return analysis can require a source shape
that the primary match analysis rejects.

# Bug 3 — nested terminating match statements are also invisible to generic block fallthrough helpers

The duplication extends one level further.

`matchArmDefinitelyReturns()` uses the package-level helper:

```go
return blockDefinitelyReturns(arm.BlockBody)
```

rather than the analyzer-aware:

```go
a.blockDefinitelyReturns(...)
```

The package-level `statementDefinitelyReturns()` explicitly has:

```go
case *ast.MatchStatement:
    return false
```

Similarly `blockCanFallThrough()` eventually routes a nested MatchStatement
through that non-aware helper.

Consequently an arm block whose terminating operation is itself an exhaustive
terminating match can be classified as continuing.

Example:

```sec
match outer {
    A => {
        match inner {
            X => return 1
            Y => return 2
        }
    }

    B => return 3
}
```

If the nested match is exhaustive, the `A` arm is non-continuing.

The structural helpers can nevertheless report that the arm block falls
through.

This can affect:

- outer match termination;
- function return analysis;
- unreachable code after the match;
- `ResolvedMatchArm.Flow`;
- expression-match all-terminating reasoning when block arms are involved.

# Architectural cause

The repository already contains the correct direction:

```go
ResolvedMatchPlan
matchCoverageComplete(...)
enumNumericDomainCovered(...)
ResolvedMatchArm.Flow
```

Yet later control-flow helpers reconstruct semantics from:

- AST pattern spellings;
- raw type kind checks;
- package-level structural recursion.

That creates two semantic authorities.

The rulebook explicitly requires Sema to resolve before lowering:

- normalized pattern identity;
- enum numeric value class;
- exhaustive residual coverage;
- arm flow classification.

Once those facts exist, no later return/fallthrough consumer should reconstruct
them from source syntax.

# Required correction

## 1. Use the canonical resolved match result for termination

After `analyzeMatch()` completes successfully, statement termination should be
derived from the same resolved facts used by Semantic IR.

Conceptually:

```text
plan.Exhaustive
AND
every reachable arm.Flow is non-continuing
```

should determine whether a statement match is non-continuing.

Do not run a separate pattern-coverage algorithm.

## 2. Cover all canonical subject kinds automatically

By consuming `ResolvedMatchPlan`, termination analysis automatically follows the
same support boundary for:

- Result;
- Option;
- ordinary union;
- ordinary enum;
- open bit-backed enum;
- future compiler-known empty state.

There should be no separate type-kind switch to keep synchronized.

## 3. Preserve enum numeric value classes

Termination/reachability must consume canonical normalized enum coverage.

Never use `EnumValues` member spellings to decide match exhaustiveness.

Alias names are declarations, not distinct runtime states.

## 4. Make nested control flow analyzer-aware

Replace package-level structural queries in analyzed match flow with resolved or
analyzer-aware flow facts.

In particular:

```text
matchArmDefinitelyReturns
blockCanFallThrough
resolvedMatchArmFromAnalysis
```

must not treat a nested already-resolved MatchStatement as inherently
fallthrough-capable.

Prefer one general resolved statement-flow fact rather than special-casing match
recursively.

## 5. Avoid post-analysis syntax reconstruction

The durable model should provide something equivalent to:

```text
StatementFlow {
    CanContinue
    Returns
    Terminates
    BreakTarget
    ContinueTarget
}
```

with MatchStatement consuming its `ResolvedMatchPlan`.

Then:

- function return checking;
- unreachable code detection;
- block fallthrough;
- outer match arm flow;
- cleanup edge planning;
- Semantic IR;

all consume the same result.

# Governance reconciliation

The current `frontend.match-v2` entry says the frontend and IR path cover:

- statement and expression matches;
- union and Option;
- enum aliases normalized to numeric value classes;
- open bit-backed enum exhaustiveness;
- source-order CFG;
- statement continuation/all-terminating control flow.

Those claims are accurate for the primary match analysis and much of Package 12,
but too broad for frontend function/block termination analysis.

Add an explicit partial item:

```text
statement-match return/fallthrough analysis still re-computes coverage
independently and does not recognize exhaustive union/Option matches or enum
alias-normalized coverage.
```

The current remaining list does not document this mismatch.

Do not downgrade:

- canonical `analyzeMatch()` coverage;
- Result statement return handling;
- expression-match `never` handling in the currently tested cases;
- enum numeric coverage in the main match analyzer;
- Package 12 ResolvedMatchPlan-based CFG lowering.

The defect is specifically the secondary structural termination consumers.

# Required regression tests

## Union / Option statement matches

1. non-void function ending in exhaustive Option statement match where every arm
   returns is accepted;
2. equivalent ordinary user-union match is accepted;
3. code after such an exhaustive all-returning match is diagnosed unreachable;
4. one continuing union arm correctly restores post-match continuation;
5. guarded union arm does not count as complete coverage unless fallback exists.

## Enum aliases

6. closed enum statement match with aliases uses numeric value classes for
   return analysis;
7. bit-backed enum statement match covering the complete numeric domain is
   non-continuing when all arms return;
8. omitted alias spelling does not create false fallthrough;
9. adding a duplicate alias arm remains rejected as unreachable/duplicate;
10. return analysis never requires all alias names.

## Nested match flow

11. match arm block ending in exhaustive all-returning nested Result match is
    non-continuing;
12. same with nested Option/union match;
13. same with nested enum-alias match;
14. outer match `ResolvedMatchArm.Flow` reflects the nested match termination;
15. code after a nested terminating match inside an arm is diagnosed unreachable.

## Consistency

16. canonical match exhaustiveness and function-return analysis always agree;
17. `ResolvedMatchPlan.Exhaustive` is the sole match coverage source for later
    consumers;
18. open bit-backed enum complete-domain match uses the same numeric proof in
    return analysis;
19. catch-all handling remains final/reachable according to normal match rules;
20. Package 12 lowering consumes the same flow facts as frontend return analysis.

## Applied 2026-08-23

Statement-match return and nested block-flow analysis now consume the analyzer's
resolved match plans. Exhaustiveness, enum value-class normalization, and arm
continuation therefore use the same frontend facts instead of a duplicate AST
coverage implementation. Downstream Semantic IR/lowering consumption remains
tracked in `implementation-status.yaml`.
