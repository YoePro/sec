# Applied correction 31 — volatile raw-pointer operations are missing from the canonical compiler-known registry

## Audit context

- Primary rulebook: `rules/platform/volatile.md`
- Status: Normative
- Created / last updated: 2026-08-26
- Document revision: 1
- Sec language version: 0.1
- Rulebook baseline reviewed: `fc8d632`
- Related canonical rulebook: `rules/compiler/compiler_known_members.md`
- Audited: 2026-08-28

## Classification

Software bug + canonical-rulebook synchronization bug + governance bug.

`volatile.md` normatively introduces:

```sec
RawPtr[T].VolatileRead() T
RawPtr[T].VolatileWrite(value: T) void
```

but the canonical compiler-known registry, its Sema implementation, and root implementation governance do not contain those operations.

This correction does not change the intended volatile semantics.

---

## 1. Canonical source API

`rules/platform/volatile.md` defines `VolatileRead` and `VolatileWrite` as compiler-known RawPtr methods.

They are explicit observable physical-storage operations and are semantically distinct from ordinary:

```sec
RawPtr[T].Read()
RawPtr[T].Write(value)
```

Ordinary RawPtr use remains subject to the canonical unsafe rules.

The volatile operations must preserve, as applicable:

- volatile occurrence identity;
- access width;
- alignment;
- address space / memory domain;
- representation validity;
- target permissions;
- byte-order requirements;
- physical ordering requirements;
- observable read/write effects.

They must survive Semantic IR and lowering as explicit volatile operations rather than ordinary memory accesses.

---

## 2. Canonical registry is unsynchronized

`rules/compiler/compiler_known_members.md` declares itself the single canonical registry for compiler-known members and requires other rulebooks to synchronize with it rather than create parallel registries.

Its RawPtr registry currently contains the equivalent of:

```text
Read
Write
Offset
AddBytes
Difference
```

but omits:

```text
VolatileRead
VolatileWrite
```

The omission occurs in the RawPtr member inventory and the minimum registry summary, and `rules/platform/volatile.md` is not listed among required synchronization inputs.

### Required documentation correction

Add canonical entries equivalent to:

```text
RawPtr[T].VolatileRead() T
RawPtr[T].VolatileWrite(value: T) void
```

and delegate their physical semantics to `rules/platform/volatile.md`.

Add `rules/platform/volatile.md` to the compiler-known registry synchronization list.

---

## 3. Sema registry has the same omission

`internal/sema/compiler_known_members.go` registers RawPtr compiler-known members for:

```text
Read
Write
Offset
AddBytes
Difference
```

but no volatile pair.

Therefore ordinary compiler-known-member resolution cannot currently satisfy the source API required by `volatile.md`.

### Required implementation

Add stable compiler-owned identities, for example:

```text
CKM-RAWPTR-VOLATILE-READ
CKM-RAWPTR-VOLATILE-WRITE
```

with:

```text
receiver: RawPtr[T]
unsafe: required
VolatileRead result: T
VolatileWrite parameter: T
VolatileWrite result: void
```

Both operations are effectful.

---

## 4. Physical eligibility is separate from ordinary RawPtr typing

The existence of `RawPtr[T]` does not prove that direct volatile materialization of `T` is legal for the active `CompilationPlan`.

Sema must reject facts already known invalid, including as applicable:

- `RawPtr[void].VolatileRead()`;
- `RawPtr[void].VolatileWrite(...)`;
- unsupported physical representation;
- unsupported access width;
- statically invalid alignment;
- invalid address space;
- forbidden target operation;
- known permission violation.

Dynamic facts that the unsafe contract deliberately leaves to the programmer may remain programmer obligations, but `unsafe` must not waive facts the compiler already knows are invalid.

---

## 5. Do not lower through ordinary Read/Write semantics

`VolatileRead` must not be implemented merely as an alias for `Read`, nor `VolatileWrite` as an alias for `Write`.

The semantic operation must preserve:

```text
observable occurrence
volatile read/write effect
no elimination
no duplication
no speculation
no invalid merging/deduplication
required ordering
physical access contract
```

through optimizer and backend stages.

---

## 6. Governance correction

Root `implementation-status.yaml` has a dedicated fixed-address integration, but no complete integration for the new `volatile.md` rulebook.

`frontend.fixed-address-bindings` should remain the `@address`-specific slice.

Add a separate integration such as:

```text
frontend.volatile-access
```

covering at minimum:

- compiler-known RawPtr volatile methods;
- registry synchronization;
- unsafe-context enforcement;
- physical read/write eligibility;
- target access-contract resolution;
- address-space, width, alignment and representation checks;
- explicit volatile effects;
- Semantic IR representation;
- optimizer invariants;
- Sec MLIR / LLVM lowering;
- target-required hardware ordering/barriers;
- diagnostics;
- LSP presentation;
- complete volatile test families.

The existing `Symbol.Volatile` marker for accepted fixed-address bindings is useful, but is not end-to-end volatile support.

## 8. Required tests

1. `RawPtr[int].VolatileRead` resolves as compiler-known.
2. `RawPtr[int].VolatileWrite` resolves as compiler-known.
3. Both are rejected outside required unsafe context.
4. Both resolve inside unsafe when otherwise legal.
5. `RawPtr[void]` direct volatile access is rejected.
6. Ordinary RawPtr `Read` / `Write` remain distinct operations.
7. Two volatile reads remain two observable reads.
8. A discarded volatile read is retained.
9. Equal volatile writes remain two writes.
10. Conditional volatile accesses are not speculated.
11. Loop volatile reads are not hoisted illegally.
12. Known-invalid access width/alignment/address-space use is rejected.
13. Volatile effects reach Semantic IR/effect analysis.
14. Target-required ordering reaches lowering.
15. LSP completion derives the members from the canonical registry.
16. Touched semantic functions contain rulebook/rule traceability comments.
