# Correction 27 — shaped static extent products are unchecked and active `x` semantics enforce an obsolete same-element restriction

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-20`
- Primary rulebook: `rules/collections/shaped-types.md`
- Rulebook generation: **v2**
- Document revision: **2.0**
- Created: `2026-08-13`
- Last updated: `2026-08-13`
- Replaces: previous `shaped-types.md` revision 1

## Classification

This correction contains two software bugs and related governance corrections:

1. static shaped extent products are not checked for overflow;
2. the already-active contextual `x` implementation and its regression test
   enforce a same-element-type rule that contradicts shaped-types v2.

These are not intended language changes.

---

# Bug 1 — static shaped extents are validated individually but their total element count is never overflow-checked

## Normative requirements

`rules/collections/shaped-types.md` §4 states:

```text
Zero extents are valid.
Negative extents are invalid.
The product of all extents must be checked for overflow whenever it is not
proven safe at compile time.
```

§5 defines:

```text
Len = product of all extents in Shape
```

with canonical result type:

```text
uint
```

§29 requires Sema to prove or check:

```text
static and runtime extents
element-count overflow
```

For a fully static vector/matrix/tensor, the complete product is known at
compile time. The compiler must therefore prove representability and reject a
type whose logical element count cannot be represented by the canonical shaped
length/index/storage arithmetic required for the target.

This is a type-validation obligation, not something that may be deferred until
`.Len` is first read.

---

## Current implementation

`validateCompilerKnownGenericType()` sends:

```go
vector -> validateCompilerKnownTypeArity(..., 1, 1, 1)
matrix -> validateCompilerKnownTypeArity(..., 1, 2, 2)
tensor -> validateCompilerKnownTypeArity(..., 1, 1, -1)
```

`validateCompilerKnownTypeArity()` validates:

- number of type arguments;
- number of compile-time integer arguments;
- each dimension is non-negative.

Its dimension loop is only:

```go
for _, arg := range typ.ConstArgs {
    if arg < 0 {
        a.addErrorAtToken(
            token,
            "%s arguments must be non-negative",
            typ.Name,
        )
        return false
    }
}
```

There is no multiplication of shaped extents and no overflow proof.

The generic argument resolver itself additionally requires each single
compile-time dimension to fit `int64`, but that does not imply that the product
fits any supported length/storage representation.

---

## Observable example

Both dimensions below individually fit signed 64-bit:

```sec
matrix[byte, 5000000000, 5000000000]
```

but:

```text
5,000,000,000 * 5,000,000,000
= 25,000,000,000,000,000,000
```

which exceeds even `uint64`.

Current shaped arity/dimension validation can accept the type because it checks
only each individual non-negative `int64` dimension.

The type then semantically claims a `.Len` that cannot be represented even on a
64-bit target.

The same defect applies to a tensor where several individually modest
dimensions overflow only when multiplied.

---

## Zero-extent requirement

Overflow analysis must respect the rule:

```text
any zero extent => Len == 0
```

For example:

```sec
tensor[byte, 0, 9000000000, 9000000000]
```

has logical `Len == 0`.

A naïve left-to-right multiplication using a fixed-width temporary could
overflow before noticing a later zero dimension.

The compiler should therefore reason in arbitrary precision or first establish
the zero-extent result.

---

## Required correction for static extent products

### 1. Introduce canonical shaped-product validation

After shaped arity and individual extent validation, compute the static logical
element count using arbitrary-precision arithmetic.

Conceptually:

```text
if any extent == 0:
    Len = 0
else:
    Len = product(extents) using big.Int
```

Then validate that the result is representable under the canonical semantic
length/index/storage contract.

### 2. Use the target scalar/layout plan

Because shaped `.Len` returns target-sized `uint`, final representability is
target dependent.

The frontend/CompilationPlan must therefore use the selected target's canonical
`uint` width.

This cross-references the broader target-sized `int`/`uint` issue already tracked
by `correction5.md`; do not duplicate that architecture. Once target scalar
facts are available, shaped validation must consume them.

Even before that integration exists, values greater than `uint64` are invalid
for every currently intended target and must not be silently accepted.

### 3. Preserve the proven product

The compiler should retain the proven static element count as a canonical shaped
fact.

Consumers include:

- `Len`;
- `SizeOf`;
- dense stride derivation;
- storage eligibility;
- materialization planning;
- indexing bounds;
- Semantic IR;
- layout/lowering.

Do not recompute the product independently in every subsystem.

### 4. Runtime-shaped tensors remain checked at runtime

For:

```sec
tensor[T, Shape[Rank]]
```

runtime extents require checked product computation and appropriate
`ShapeError`/storage failure semantics according to the shaped rulebook.

This correction's concrete bug is the already-recognized static shaped forms.

# Bug 2 — active `x` implementation requires identical element types contrary to v2 algebra

## Normative requirements

`shaped-types.md` §22.1 defines:

```sec
matrix[L, Rows, Inner] x matrix[R, Inner, Columns]
```

as:

```sec
matrix[ProductElement[L, R], Rows, Columns]
```

where the result element type is derived from ordinary scalar multiplication and
the product terms support compatible addition.

§22.2 analogously defines:

```sec
matrix[L, Rows, Columns] x vector[R, Columns]
```

as:

```sec
vector[ProductElement[L, R], Rows]
```

The rule deliberately uses separate type variables `L` and `R`.

There is no requirement:

```text
L == R
```

Instead the compiler must ask whether:

1. ordinary scalar `L * R` is valid;
2. the resulting product type is known;
3. products can be accumulated with compatible addition.

Units and other scalar algebra participate through the ordinary operator rules.

---

## Current implementation

`inferMatrixMultiplyExpression()` is active in ordinary infix inference.

Before shape checking it does:

```go
if !sameConcreteType(
    leftType.TypeArgs[0],
    rightType.TypeArgs[0],
) {
    return invalid(
        "matrix multiplication element types differ: %s and %s",
        ...
    )
}
```

For matrix × matrix it then clones the **left** matrix type:

```go
result := leftType
result.ConstArgs = []int64{
    leftType.ConstArgs[0],
    rightType.ConstArgs[1],
}
```

For matrix × vector it clones the **right** vector type:

```go
result := rightType
result.ConstArgs = []int64{
    leftType.ConstArgs[0],
}
```

Thus no scalar multiplication result type is ever derived.

The current implementation only works accidentally for the restricted case
where both operand element types are already exactly identical and the desired
product/accumulation element type is also assumed to remain that type.

---

## The obsolete behavior is locked in tests

`internal/sema/analyzer_test.go` contains
`TestContextualMatrixMultiplyTypesAndShapes`.

Its invalid cases explicitly expect:

```text
matrix multiplication element types differ: int and float32
```

for:

```sec
matrix[int, 4, 3] x vector[float32, 3]
```

That regression expectation contradicts shaped-types v2.

This is therefore not merely dormant code or an untested scaffold. The compiler
and test suite actively preserve the stale same-element rule.

---

## Required correction for `x`

### 1. Resolve scalar product type through ordinary operator semantics

Given element types:

```text
L
R
```

resolve the semantic result of:

```sec
L * R
```

using the same scalar/unit/operator rules as an ordinary scalar multiplication.

Call that result:

```text
ProductElement[L, R]
```

The notation need not be a public generic type; it is the rulebook's name for
the resolved scalar multiplication result type.

### 2. Validate accumulation

Matrix multiplication forms sums of scalar products.

The compiler must prove that two product terms can participate in the canonical
addition/accumulation operation and that the accumulator/result type is stable
under that operation.

Do not infer validity from `sameConcreteType(L, R)`.

### 3. Construct the result from the derived element type

For matrix × matrix:

```text
matrix[ResolvedProductElement, Rows, Columns]
```

For matrix × vector:

```text
vector[ResolvedProductElement, Rows]
```

subject to the canonical accumulation result rules.

Do not clone the left/right shaped operand and merely replace dimensions.

### 4. Preserve shape proof behavior

The current static inner-dimension checks are useful and should remain:

```text
left.Columns == right.Rows
left.Columns == vector.Length
```

When runtime-shaped canonical `x` forms are implemented, use `ShapeError` and
`try` exactly as §22.4 requires.

### 5. Units and named scalar types

The `x` implementation must consume ordinary scalar operator/unit semantics,
not create a separate numeric universe for shaped algebra.

Examples needing deliberate validation include:

```text
matrix[Length, ...] x vector[Force, ...]
matrix[int, ...] x vector[decimal, ...]
```

where ordinary scalar multiplication determines whether the operation is legal
and what product element type results.

- multiplicative precedence;
- Sema dispatch to `inferMatrixMultiplyExpression()`;
- static matrix × matrix support;

- static inner-dimension validation;

The accurate status is **partial**, not wholly absent.

The current partial implementation must be documented together with its stale

# Secondary rulebook clarity observation — `ProductElement[L, R]`

This audit does **not** classify the shaped-v2 rule as logically contradictory:
§22 explains that `ProductElement[L,R]` means the result type derived from
ordinary scalar multiplication.

However the spelling looks syntactically like a compiler-known generic type even
though the book does not state that such a public type exists.

During the next rulebook edit, consider making the notation explicit, e.g.:

```text
ProductElement[L, R] is specification notation for the compiler-resolved result
type of ordinary scalar L * R; it is not a source-visible generic type unless a
separate rulebook defines one.
```

That would prevent an implementer from inventing an unnecessary runtime/core
type.

This is a documentation clarification, not a software correction.

# Required regression tests

## Static shaped extent product

1. ordinary small vector extent accepted;
2. ordinary small matrix product accepted;
3. ordinary small static tensor product accepted;
4. any zero extent yields static Len 0 without false overflow;
5. matrix with individually valid extents whose product exceeds `uint64` is
   rejected;
6. tensor whose extent product exceeds `uint64` is rejected;
7. product exactly at the target `uint` maximum is handled according to storage
   eligibility and target rules;
8. first value above target `uint` maximum is rejected;
9. static Len fact is retained rather than recomputed inconsistently;
10. SizeOf multiplication performs its separately required checked byte-count
    arithmetic after Len validation.

## `x` algebra

11. existing same-element matrix × matrix valid case remains valid;
12. existing same-element matrix × vector valid case remains valid;
13. mismatched static inner dimensions remain rejected;
14. different element types are accepted when ordinary `L * R` and product
    accumulation are valid;
15. different element types are rejected only when the scalar algebra is
    actually invalid;
16. result matrix element type is the resolved scalar product/accumulation type;
17. result vector element type is the resolved scalar product/accumulation type;
18. unit-bearing element multiplication follows ordinary unit algebra;
19. matrix × unsupported right-family remains rejected;
20. unsupported `vector x vector` remains without hidden `x` meaning;
21. contextual identifier `x` remains usable as an ordinary identifier outside
    operator position;
22. operator `x` remains multiplicative-precedence and left-associative.

## Governance/traceability

23. `frontend.shaped-types` records static `x` Sema as partial rather than wholly
    remaining;
24. stale lexical “built-in shaped type parser integration” remaining item is
    removed or narrowed;
25. touched semantic/parser functions cite canonical shaped rulebook sections;
26. focused tests cite the governing rule/correction where practical.

## Applied 2026-08-23

Static shaped extents now produce one arbitrary-precision element-count fact,
including zero short-circuiting and selected-target `uint` validation. Static
contextual `x` derives its element through ordinary scalar multiplication and
checks stable accumulation through ordinary addition. Runtime-shaped behavior
and downstream fact consumption remain tracked in `implementation-status.yaml`.
