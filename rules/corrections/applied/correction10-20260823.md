# Correction 10 — interface method overload sets are collapsed by method name

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/declarations/interfaces.md`
- Document revision: **2.0**
- Created: `2026-08-13`
- Last updated: `2026-08-14`
- Related later/equal-generation rulebook: `rules/declarations/functions.md`, revision **2.0**, `2026-08-14`

## Classification

Implementation bug.

This is not a language-rule change.

Sec methods participate in ordinary overload rules. Interface method requirements
are bodyless method signatures, and interface conformance explicitly compares
parameter signatures while stating that return type is not an overload
discriminator.

Current Sema nevertheless treats an interface method **name** as unique inside an
interface and inside an inherited requirement set. Two legal overload
requirements with the same name but different parameter signatures are therefore
rejected or collapsed.

---

## Normative requirements

`rules/declarations/functions.md` revision 2.0 states:

- functions **and methods** may be overloaded when their overload parameter
  signatures differ;
- return type alone never distinguishes overloads;
- named types retain identity during overload resolution;
- ownership mode is part of callable compatibility but does not permit otherwise
  identical overload declarations.

`rules/declarations/interfaces.md` revision 2.0 states that conformance checks
include:

- member name;
- parameter count and parameter types;
- parameter borrow/consuming/variadic modes;
- generic constraints;
- result type;
- receiver capability;
- static versus instance category;

and explicitly says:

> Return type is not an overload discriminator.

Therefore an interface requirement set must preserve overload identity by the
same canonical parameter-signature rules used for methods generally.

---

# Bug 1 — direct interface declarations reject every repeated method name

## Affected code

`internal/sema/analyzer.go`

`analyzeInterfaceDeclarationBody()` uses:

```go
seenMethods := map[string]lexer.Token{}

for _, method := range stmt.Methods {
    ...
    if previous, exists := seenMethods[method.Name.Value]; exists {
        _ = previous
        a.addErrorAtToken(
            method.Name.Token,
            "duplicate interface method %q in %s",
            method.Name.Value,
            stmt.Name.Value,
        )
        continue
    }

    seenMethods[method.Name.Value] = method.Name.Token
    iface.InterfaceMethods = append(
        iface.InterfaceMethods,
        a.interfaceMethodRequirement(stmt.Name.Value, method),
    )
}
```

The key is only:

```text
method.Name
```

No parameter-signature comparison is performed before the duplicate diagnostic.

---

## Example

This should form two requirements in one overload set:

```sec
interface Formatter {
    fn Format(value: int) string
    fn Format(value: string) string
}
```

The parameter signatures differ:

```text
Format(int)
Format(string)
```

Under the canonical method-overload rule these are distinct overloads.

Current Sema reports the second declaration as:

```text
duplicate interface method "Format" in Formatter
```

and discards it.

# Bug 2 — inherited interface overloads are also collapsed by method name

## Affected code

`internal/sema/analyzer.go`

`mergeInheritedInterfaceRequirements()` initializes:

```go
methods := map[string]Function{}
```

and indexes every requirement by:

```go
methods[method.Name]
```

For each inherited parent requirement:

```go
if existing, exists := methods[method.Name]; exists {
    if !sameInterfaceRequirementSignature(existing, method) ||
       !sameConcreteType(existing.ReturnType, method.ReturnType) {
        a.addErrorAtToken(
            method.Token,
            "inherited interface method %s conflicts in %s",
            method.Name,
            iface.Name,
        )
    }
    continue
}
```

Thus any two inherited methods with the same name are interpreted as either:

- identical duplicate requirement; or
- conflict.

A valid overload pair is never retained.

---

## Example

```sec
interface IntFormatter {
    fn Format(value: int) string
}

interface StringFormatter {
    fn Format(value: string) string
}

interface Formatter implements IntFormatter, StringFormatter {
}
```

The inherited requirements are compatible as an overload set:

```text
Format(int) -> string
Format(string) -> string
```

They do not conflict.

Current inheritance merging sees only the shared name `Format` and diagnoses a
conflict because the parameter signatures differ.

# Bug 3 — same-signature different-return inherited requirements need a
# different decision from distinct overloads

The current name-only map accidentally mixes two different cases:

### Valid distinct overloads

```text
F(int)    -> string
F(string) -> string
```

### Invalid same-overload return conflict

```text
F(int) -> string
F(int) -> bool
```

The second pair is invalid because return type is not an overload discriminator.

The implementation must preserve this distinction.

A canonical overload key must first determine whether two requirements are the
**same overload parameter signature**.

Only then should callable-contract compatibility — including return type,
receiver capability, static/instance category, parameter ownership modes, and
other interface requirements — decide whether duplicate inherited requirements
are semantically identical or conflicting.

---

# Required correction

## 1. Represent interface methods as overload groups

Do not use:

```text
map[methodName]singleRequirement
```

for declaration duplicate checks or inherited merge.

Use either:

```text
map[methodName][]requirements
```

with canonical signature comparison, or an equivalent canonical overload-key
structure.

The semantic `InterfaceMethods` representation may remain a flat list if all
lookup/merge operations preserve every distinct overload.

## 2. Apply the canonical method overload identity

Two interface method requirements with the same name are distinct overloads when
their canonical overload parameter signatures differ.

The overload key must follow the functions rulebook, including the exact
decisions for:

- parameter types;
- generic/concrete signature dimensions that participate in method identity;
- variadic shape once native variadics are supported for interface
  requirements;
- ownership modes that are callable-contract properties but explicitly do not
  create otherwise-identical overloads where the function rule forbids that.

Return type must not create a distinct overload.

Receiver capability must not be used to create an otherwise identical overload
unless a later rulebook explicitly makes it part of overload identity. It is a
conformance/callable-contract requirement.

## 3. Diagnose exact duplicate requirements

Within one interface:

```sec
interface Bad {
    fn Read(value: int) string
    fn Read(value: int) string
}
```

should receive a duplicate-requirement diagnostic.

The diagnostic should point to both declarations where practical.

## 4. Diagnose same-overload incompatible requirements

Within inheritance:

```sec
interface A {
    fn Read(value: int) string
}

interface B {
    fn Read(value: int) bool
}

interface C implements A, B {
}
```

must remain invalid.

The requirements have the same overload identity but incompatible return
contracts.

Likewise incompatible receiver/static/ownership/property-of-callable contract
facts must remain conflicts according to the owning rules.

## 5. Preserve distinct inherited overloads

This must be valid:

```sec
interface A {
    fn Read(value: int) string
}

interface B {
    fn Read(value: string) string
}

interface C implements A, B {
}
```

`C` must contain both requirements.

## 6. Conformance must check every overload requirement

`validateTypeImplementsInterface()` already iterates `iface.InterfaceMethods` and
searches the concrete overload group:

```go
methods := a.functions[typ.Name+"."+required.Name]
```

This architecture can support overloaded interface requirements once the
interface requirement list stops dropping them.

Verify that every distinct requirement is checked independently and that one
concrete overload cannot incorrectly satisfy two incompatible requirements.

## 7. Interface member calls must retain overload resolution

When interface values gain complete Semantic IR/dynamic dispatch support, a call
such as:

```sec
formatter.Format(value)
```

must resolve a concrete interface requirement overload before runtime dispatch.

Runtime interface dispatch must not become runtime overload resolution.

The selected overload identity must be part of the immutable resolved call fact.

---

# Governance reconciliation

The root `frontend.interfaces` entry currently lists as implemented:

```text
exact method parameter/result/static compatibility
```

but does not state that interface overload sets are unsupported.

The implementation is partial:

- concrete conformance can search ordinary concrete overload groups;
- interface declaration/inheritance representation itself currently permits only
  one requirement per method name.

Add this limitation explicitly.

Do not downgrade:

- basic interface declarations;
- explicit primary-impl conformance placement;
- receiver borrow-call restrictions;
- inheritance cycle detection;
- ordinary concrete method overload resolution.

The defect is specifically the interface requirement overload-set model.

---

# Required regression tests

Add tests covering at least:

## Direct interface declarations

1. same method name with different parameter types is accepted as overloads;
2. same method name with different parameter counts is accepted;
3. exact duplicate parameter signature is rejected;
4. same parameter signature differing only by return type is rejected;
5. otherwise-identical requirements differing only by consuming parameter mode
   follow the canonical function-overload prohibition;
6. static versus instance contract is checked according to canonical overload
   identity and interface compatibility rules.

## Inheritance

7. two parents contributing distinct overloads with the same name are accepted;
8. three or more parents can contribute one overload set;
9. identical inherited requirement is merged without duplication;
10. same overload identity with different return type is rejected;
11. same overload identity with incompatible receiver requirement is rejected;
12. inherited overload source order does not affect the result.

## Conformance

13. a concrete type must implement every required overload;
14. implementing only one of two required overloads is rejected;
15. two concrete overloads satisfy their corresponding requirements;
16. one concrete method cannot accidentally satisfy a different parameter
    overload;
17. return type remains a compatibility requirement but never an overload
    discriminator.

## Future lowering boundary

18. resolved interface calls identify one exact overload before dynamic dispatch;
19. interface dispatch never performs runtime overload selection.

## Applied 2026-08-23

Direct and inherited interface requirements now retain overload groups keyed by
canonical parameter signatures. Distinct same-name overloads are accepted,
identical requirements are merged where appropriate, and incompatible duplicate
contracts are diagnosed with their prior declaration. Conformance continues to
check every retained requirement independently.
