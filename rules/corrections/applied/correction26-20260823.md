# Correction 26 — owning dynamic arrays inherit fixed-array value semantics through the shared `ArrayType`

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-20`
- Primary rulebook: `rules/collections/collections.md`
- Document revision: **1**
- Created: `2026-08-11`
- Last updated: `2026-08-11`

## Classification

Implementation bug.

This is not a language-rule change.

The collections rulebook defines `T[N]` and owning `T[]` as semantically
different value types.

Current Sema represents both with the same `ArrayType` kind:

```text
T[N] -> ArrayType, ArrayLength = N
T[]  -> ArrayType, ArrayLength = -1
```

Several generic type-trait functions inspect only `Kind == ArrayType` and do not
distinguish the dynamic-array sentinel.

That causes owning `T[]` to inherit fixed-array semantics in four important
areas:

1. copy/move classification;
2. destruction classification;
3. ordinary equality;
4. initialization/conversion compatibility.

The shared representation is therefore not merely an implementation detail: it
currently leaks incorrect source semantics.

---

# Normative distinction

`rules/collections/collections.md` §5 defines:

```sec
T[N]
```

as a fixed-size owning inline array whose length is part of type identity.

§6 defines:

```sec
T[]
```

as a distinct first-class dynamically sized owning array.

Every `T[]` is explicitly:

```text
MoveOnly
non-trivially destructible
owning its live logical elements
```

regardless of whether `T` itself is copyable.

§10 grants ordinary `==` / `!=` content equality to fixed arrays when their
element type supports equality.

It does not grant that operation to owning dynamic arrays. Dynamic-array content
equality must be separately and explicitly defined.

§11 states that by-value `T[]` transfers the owning dynamic array by move.

---

# Representation cause

## Affected code

`internal/sema/analyzer.go`

The type resolver creates fixed arrays as:

```go
Type{
    Kind:        ArrayType,
    Element:     &element,
    ArrayLength: length,
}
```

and owning dynamic arrays as:

```go
Type{
    Name:        typeDisplayName(element) + "[]",
    Kind:        ArrayType,
    Element:     &element,
    ArrayLength: dynamicArrayLength,
}
```

with:

```go
const dynamicArrayLength int64 = -1
```

The frontend therefore relies on every consumer remembering that
`ArrayLength == -1` means a fundamentally different owning collection kind.

Several consumers do not.

---

# Bug 1 — `T[]` can be classified as copyable

## Affected code

`internal/sema/types.go`

`copyClassificationOf()` handles every `ArrayType` identically:

```go
case ArrayType:
    if typ.Element == nil {
        return CopyTrivial
    }
    return aggregateCopyClassification(
        []Type{*typ.Element},
        visiting,
    )
```

For:

```sec
int[]
```

the element is trivially copyable, so the owning dynamic array itself becomes
`CopyTrivial`.

For a semantically copyable struct element it can similarly become copyable.

This directly contradicts §6.1:

```text
Every T[] is MoveOnly regardless of whether T itself is copyable.
```

## Consequences

Any ownership consumer that trusts `CopyClassificationOf()` may permit implicit
duplication rather than ownership transfer.

That includes, depending on the surrounding path:

- let initialization;
- assignment;
- by-value argument passing;
- return;
- aggregate embedding;
- generic copyability constraints;
- diagnostics and LSP ownership facts.

A dynamic owner must never become copyable merely because its element type is
copyable.

---

# Bug 2 — `T[]` can be classified as trivially destructible

## Affected code

`triviallyDestructible()` also handles all `ArrayType` values as fixed arrays:

```go
case ArrayType:
    if typ.Element == nil {
        return true
    }
    return triviallyDestructible(
        *typ.Element,
        visiting,
    )
```

Thus:

```sec
int[]
```

is classified as trivially destructible.

But §6.1 explicitly says every `T[]` is non-trivially destructible, and §12.2
requires dynamic-array destruction to:

1. destroy live logical elements in reverse order;
2. end the active backing invalidation domain;
3. reclaim backing according to the resolved reclamation authority.

Even an empty dynamic array is still an owning collection value with this
destruction model.

Its element type being trivial does not make the owner type a fixed inline
aggregate.

---

# Bug 3 — ordinary `==` / `!=` is enabled for `T[]`

## Affected code

`equalityComparable()` says:

```go
case ArrayType:
    return typ.Element != nil &&
        equalityComparable(*typ.Element, visiting)
```

Then `canCompareEquality()` treats all arrays through:

```go
if left.Kind == ArrayType || right.Kind == ArrayType {
    return sameComparableArrayType(left, right)
}
```

`sameComparableArrayType()` requires equal `ArrayLength`.

Two dynamic arrays both have:

```text
ArrayLength = -1
```

so two values of `int[]` are accepted as comparable when `int` supports
equality.

This imports the fixed-array §10 equality rule into the owning dynamic-array
type.

The rulebook explicitly does not define ordinary dynamic-array content equality
this way.

Therefore:

```sec
let same := left == right
```

for two `int[]` values must not become legal simply because both use the
internal `ArrayType` representation.

If Sec later adds a public dynamic-array equality operation, that operation must
be defined deliberately by its owning rulebook/core API.

# Bug 4 — fixed and dynamic arrays are implicitly initialization-compatible

## Affected code

`canInitialize()` contains:

```go
if target.Kind == ArrayType ||
   value.Kind == ArrayType ||
   target.Kind == SliceType ||
   value.Kind == SliceType {

    if target.Kind == ArrayType &&
       value.Kind == ArrayType &&
       target.Element != nil &&
       value.Element != nil &&
       (target.ArrayLength == dynamicArrayLength ||
        value.ArrayLength == dynamicArrayLength) {

        return canInitialize(
            *target.Element,
            *value.Element,
            expr,
        )
    }

    return sameConcreteType(target, value)
}
```

If either side is dynamic, array length and owning representation cease to be
part of compatibility.

This can make:

```text
T[N] -> T[]
T[]  -> T[N]
```

appear initialization-compatible based only on element compatibility.

That contradicts the rulebook's explicit statement that `T[]` is distinct from
`T[N]`.

Creating an owning dynamic array from a fixed array would require a separately
defined operation with explicit storage/allocation/element-transfer semantics.
Likewise a dynamic owner cannot simply initialize an inline `T[N]` without a
defined length proof and transfer/copy operation.

No such implicit conversion is defined by `collections.md`.

## Required behavior

At minimum:

```text
T[N] <- T[N]
    requires exact fixed-array type compatibility

T[] <- T[]
    requires compatible exact dynamic-array element identity
    and owning move semantics

T[] <- T[N]
    no implicit owner conversion

T[N] <- T[]
    no implicit owner conversion

slice formation
    follows explicit ref/ref mut slice rules
```

# Required correction

## 1. Give owning dynamic arrays a robust semantic identity

Preferred fix:

```text
ArrayType        -> fixed T[N]
DynamicArrayType -> owning T[]
SliceType        -> borrowed slice/view
```

A distinct semantic kind makes invalid fixed-array trait reuse structurally
harder.

If the implementation temporarily retains the `ArrayLength == -1` sentinel,
then every semantic trait must route through a single canonical helper such as:

```text
isFixedArray(type)
isOwningDynamicArray(type)
```

and direct generic `case ArrayType:` logic must be audited.

The long-term representation should reflect the rulebook's explicit source-level
identity distinction.

## 2. Lock dynamic-array copy classification

For every valid:

```sec
T[]
```

return:

```text
CopyMoveOnly
```

independently of `T`.

Element copyability still matters for operations such as iteration by plain
value or `Fill`, but it does not change ownership of the dynamic-array container.

## 3. Lock dynamic-array destruction classification

Every `T[]` must be:

```text
TriviallyDestructible == false
```

even for primitive `T`.

The destruction plan may optimize empty/no-backing cases later, but semantic
destruction responsibility remains non-trivial.

## 4. Separate fixed-array equality from dynamic-array equality

Only fixed arrays receive §10 ordinary `==` / `!=` through elementwise
comparison.

Do not route `T[]` through `sameComparableArrayType()`.

Dynamic-array equality remains unavailable until a canonical explicit operation
is defined.

## 5. Remove implicit fixed/dynamic owner initialization

`canInitialize()` must distinguish:

- fixed array identity;
- dynamic array ownership identity;
- slice borrowing identity.

Do not use "either side has dynamic length" as permission to erase collection
identity.

## 6. Audit all `ArrayType` consumers

Search every frontend, Semantic IR, LSP, formatter, lowering, and backend use of:

```text
Kind == ArrayType
```

and classify whether that code intends:

- fixed arrays only;
- dynamic arrays only;
- both sequence categories with deliberately shared behavior.

Pay particular attention to:

- copy/move;
- destruction;
- equality;
- defaultability;
- initialization;
- literal typing;
- parameter preparation;
- return preparation;
- aggregate ownership;
- indexing/slicing;
- layout;
- FFI;
- Semantic IR;
- lowering.

## 7. Apply source-rulebook traceability comments

Under the project-wide traceability rule introduced by `correction25.md`, every
touched semantic function should gain comments identifying its normative owners.

At minimum, comments on the relevant functions should reference:

```text
rules/collections/collections.md §5
    fixed arrays

rules/collections/collections.md §6
    owning dynamic arrays

rules/collections/collections.md §10
    equality

rules/collections/collections.md §11
    parameters and return values

rules/collections/collections.md §12
    destruction
```

and the relevant ownership/copy-move/destruction rulebooks where those functions
implement cross-cutting semantics.

Examples of functions requiring traceability when modified include:

```text
type resolution for T[N] / T[]
copyClassificationOf
triviallyDestructible
equalityComparable
canCompareEquality
sameComparableArrayType
canInitialize
```

The comments are traceability metadata and do not replace the normative
rulebooks.

# Governance reconciliation

## `frontend.collections`

The current entry correctly says overall collection support is partial and
already lists:

```text
array ... equality and ownership validation
```

as remaining.

However it also says Sema recognizes the collection identities.

That statement should be qualified: syntax/type recognition exists, but fixed
and owning dynamic arrays currently share `ArrayType` with a sentinel and this
identity is not preserved by core semantic traits.

Add an explicit partial item for:

```text
owning dynamic-array semantic identity across copyability, destruction,
equality, initialization, and ownership transfer
```

## `frontend.copy-move`

This entry currently describes recursive **array** classification as
implemented.

That is too broad.

Fixed-array classification follows the element type as intended.

Owning `T[]` must be explicitly marked partial/incorrect until it is always
MoveOnly independently of its element type.

## `frontend.dynamic-array-public-api`

The compiler-known member surface can remain implemented within its documented
scope.

This correction concerns value semantics of the owner type, not the existence
or signatures of `Len`, `Append`, `Clear`, `RemoveAt`, etc.

## `frontend.default-values`

The canonical allocation-free empty mutable `T[]` default can remain
implemented.

Its default construction is valid; the resulting value's copy/destruction
traits are what need correction.

# Required regression tests

## Semantic identity

1. fixed `int[3]` and owning `int[]` have distinct semantic collection identity;
2. fixed arrays of different lengths remain distinct;
3. dynamic-array runtime length is not part of type identity;
4. slices remain distinct borrowed types.

## Copy/move

5. `CopyClassificationOf(int[]) == CopyMoveOnly`;
6. `CopyClassificationOf(CopyableStruct[]) == CopyMoveOnly`;
7. `CopyClassificationOf(NoCopyType[]) == CopyMoveOnly`;
8. copyable fixed arrays retain copy classification derived from their element;
9. by-value `T[]` parameter transfer consumes the owner;
10. return/assignment/aggregate transfer of `T[]` follows owning move semantics;
11. implicit second use after owner transfer is rejected.

## Destruction

12. `TriviallyDestructible(int[]) == false`;
13. empty `int[]` still carries dynamic-owner destruction semantics;
14. fixed `int[N]` with trivial element remains trivially destructible where
    otherwise valid;
15. dynamic array with non-trivial elements destroys live elements then backing
    according to §12.2.

## Equality

16. `int[3] == int[3]` remains valid;
17. fixed arrays of unequal lengths remain incomparable;
18. `int[] == int[]` is rejected unless a future explicit rule introduces it;
19. dynamic-array inequality `!=` follows the same restriction;
20. element equality support does not implicitly enable container equality.

## Initialization/conversion

21. exact fixed-array initialization remains valid;
22. exact dynamic-array owner transfer remains valid with move semantics;
23. fixed `T[N]` cannot implicitly initialize owning `T[]`;
24. owning `T[]` cannot implicitly initialize fixed `T[N]`;
25. explicit slice formation remains governed by `ref` / `ref mut`, not owner
    conversion;
26. contextual literals do not silently blur fixed and dynamic owner identity.

## Cross-layer and governance

27. Semantic IR preserves fixed-array versus dynamic-owner identity;
28. maintained lowering paths cannot infer ownership from `ArrayLength == -1`
    without an explicit semantic category;
29. touched semantic functions contain canonical rulebook/rule traceability
    comments under correction25 governance;
30. copy/move and destruction governance tests explicitly cover owning `T[]`.

## Applied 2026-08-23

The dynamic-array sentinel is now treated as a distinct owning semantic category
by frontend traits: every `T[]` is move-only and non-trivially destructible,
ordinary fixed-array equality excludes it, and fixed/dynamic owner initialization
does not implicitly cross the type boundary. Broader downstream representation
audits remain in `implementation-status.yaml`.
