# Correction 11 — lambda capture resolution confuses module bindings with enclosing locals

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/declarations/lambda-functions.md`
- Document revision: **2.0**
- Created: `2026-08-14`
- Last updated: `2026-08-14`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2.0 draws a hard distinction between:

- enclosing local bindings, which require explicit capture; and
- normal non-local declarations such as module-level declarations, imported
  declarations, types, and named functions, which are not captures and remain
  directly visible according to ordinary scope rules.

Current Sema does not preserve that distinction when entering a lambda. It
classifies the complete enclosing symbol table as lambda outer state and then
uses that same table both to reject implicit access and to validate explicit
captures.

Consequently:

1. module-level variables can be incorrectly rejected as implicit captures; and
2. `capture(moduleVariable)` can be incorrectly accepted even though a capture
   entry must name an enclosing local binding.

---

## Normative requirements

`rules/declarations/lambda-functions.md` revision 2.0 states:

> Enclosing local bindings are never captured implicitly.

It also states:

> Capture entries identify visible local bindings.

and:

> A captured name must resolve to a visible local binding in an enclosing
> scope.

Critically:

> Module-level declarations, imported declarations, types, and named functions
> are not local captures and may be referenced normally according to scope
> rules.

The scope section repeats that lambda bodies may access normal non-local
declarations and may not implicitly access enclosing local bindings.

Therefore the compiler must classify the binding being referenced before
applying capture rules.

---

# Bug 1 — module-level variables are placed in `lambdaOuterSymbols`

## Affected code

`internal/sema/analyzer.go`

Before ordinary function bodies are analyzed, module-level statements are
analyzed and their variable symbols remain in the analyzer's symbol table.

Ordinary function-body analysis then starts from:

```go
previousSymbols := a.symbols
...
a.symbols = copySymbols(previousSymbols)
```

so the function's symbol environment contains module-level values plus the
function's locals/parameters as analysis proceeds.

When a lambda is entered, `inferLambdaExpression()` does:

```go
previousSymbols := a.symbols
...
a.symbols = map[string]Symbol{}
...
a.inLambda = true
a.lambdaOuterSymbols = previousSymbols
```

The complete enclosing symbol map therefore becomes the lambda's
`lambdaOuterSymbols`.

Identifier resolution later does:

```go
if a.inLambda {
    if _, outer := a.lambdaOuterSymbols[expr.Value]; outer {
        a.addErrorAtToken(
            expr.Token,
            "lambda cannot access outer variable %s without explicit capture",
            expr.Value,
        )
        return Type{Kind: InvalidType}, ...
    }
}
```

No binding-class check is performed.

Thus a module-level variable present in the outer symbol table is treated exactly
like an enclosing function local.

---

## Example — legal module access is rejected

Conceptually:

```sec
module app

let answer: int := 42

fn MakeReader() int {
    let read := fn() int {
        return answer
    }

    return read()
}
```

`answer` is a module-level declaration.

Revision 2.0 says it is not a capture and may be referenced normally.

Current Sema enters the function with `answer` in `a.symbols`, then places that
same symbol in `lambdaOuterSymbols`, clears the lambda-local symbol map, and
diagnoses use of `answer` as:

```text
lambda cannot access outer variable answer without explicit capture
```

That diagnostic is incorrect.

# Bug 2 — explicit capture of a module-level variable is accepted

`defineLambdaCaptures()` validates captures against the same unfiltered outer
symbol table:

```go
symbol, ok := outerSymbols[name]
if !ok {
    a.addErrorAtToken(..., "undefined capture %s", name)
    continue
}
```

It checks:

- duplicate name;
- symbol existence;
- definite assignment.

It does **not** check that the resolved symbol is a local binding belonging to an
enclosing function/lambda scope.

Therefore:

```sec
module app

let answer: int := 42

fn MakeReader() int {
    let read := capture(answer) fn() int {
        return answer
    }

    return read()
}
```

can be accepted as a capture even though revision 2.0 explicitly says
module-level declarations are not local captures.

This is semantically significant because a capture creates closure-environment
ownership/copy/move/borrow semantics, while ordinary module access does not.

A compiler must not silently turn a non-local declaration into closure state.

---

# Bug 3 — the existing `Symbol.Local` flag is not sufficient by itself

`defineSymbol()` records:

```go
Local: a.inFunctionBody
```

for ordinary declarations.

That means ordinary module-level variables receive `Local == false`, which can
help distinguish them from function-body locals.

However ordinary function parameters are currently constructed separately with:

```go
Local: false
```

even though parameters are valid enclosing local bindings for lambda capture.

Likewise compiler-provided contextual bindings and implicit instance members
have their own construction paths.

Therefore the correction must not simply implement:

```go
if !symbol.Local {
    reject capture
}
```

without first defining the canonical capture-eligible binding categories.

The analyzer already has compiler-owned binding facts (`BindingID`,
`ResolvedBinding`, binding kinds) and should use a coherent semantic binding
classification instead of guessing from symbol-table residency.

---

# Nested-lambda consequence

A nested lambda compounds the same architectural problem.

The outer lambda replaces `a.symbols` with only its captures, parameters, and
locals. Normal module-level value bindings are not retained in that local symbol
map.

A nested lambda may therefore lose ordinary non-local value visibility entirely
or classify only the immediately enclosing lambda symbols as capturable.

The fix must preserve non-local lexical/module lookup independently from the
closure-environment symbol set at every lambda nesting depth.

---

# Required correction

## 1. Separate ordinary lexical lookup from capture candidates

Entering a lambda must create two conceptually distinct environments:

### Lambda-local/captured environment

Contains:

- lambda parameters;
- explicit captures;
- lambda-local declarations.

### Normal non-local lookup environment

Retains access according to ordinary scope/module/import rules to:

- module-level declarations;
- imported declarations;
- types;
- named functions;
- compiler-known symbols;
- other non-local declarations allowed by their owning rulebooks.

Do not model both through one untyped `map[string]Symbol`.

## 2. Build capture candidates only from capture-eligible enclosing bindings

The explicit capture resolver must accept only bindings whose semantic binding
kind is valid for closure capture.

At minimum this includes ordinary enclosing:

- local variables/constants where capture is permitted;
- function/lambda parameters;
- loop and pattern bindings while they are in scope;
- enclosing lambda owned/borrowed captures where re-capture semantics permit it.

It must exclude ordinary:

- module-level variables/constants;
- imported declarations;
- named functions;
- types;
- compiler-known declarations.

Contextual bindings such as `self` and implicit members must be classified by
their owning rulebooks rather than inferred from table membership.

## 3. Resolve identifier use in the correct order

For an identifier inside a lambda:

1. resolve lambda parameter/capture/local binding;
2. resolve legal normal non-local declarations;
3. if the name resolves only to a capture-eligible enclosing local binding,
   diagnose missing explicit capture;
4. otherwise emit the ordinary unresolved-name diagnostic.

A non-local declaration must never trigger the "without explicit capture"
diagnostic.

## 4. Reject invalid explicit captures

If:

```sec
capture(name)
```

resolves to a module/import/type/function/compiler-known binding rather than a
capture-eligible enclosing local binding, emit a focused capture diagnostic.

Do not represent the name as a closure environment field.

## 5. Preserve semantic definition binding

Uses of a module-level declaration inside a lambda must bind definition/LSP
metadata to the original module declaration exactly as ordinary function-body
use does.

Capture references must instead bind to the outer local declaration plus the
compiler-owned capture record.

## 6. Fix nested lambda lookup composition

Nested lambdas must retain:

- normal non-local lookup;
- explicit access to their own captures/parameters/locals;
- capture eligibility for appropriate bindings in enclosing lambda/function
  scopes.

They must not require an unnecessary intermediate capture merely to access a
module declaration.

# Governance reconciliation

The current `frontend.lambda-functions-v2` entry lists as implemented:

```text
explicit plain-name capture lists with duplicate, undefined-name,
parameter-conflict, and implicit-capture diagnostics
```

and:

```text
exactly-once plain capture analysis
```

Those statements are too broad with respect to capture **resolution class**.

The implementation supports the listed syntax and basic diagnostics, but it
does not yet distinguish capture-eligible enclosing locals from normal non-local
bindings.

Add this limitation explicitly.

The large existing remaining items for capture modes, callable capability,
escaping environments, and closure lowering are separate and remain valid.

# Required regression tests

> **Applied 2026-08-23:** Sema now maintains separate normal non-local lookup
> and capture-candidate environments, classifies function parameters as local
> capture candidates, rejects explicit module captures, and retains module
> definition lookup inside lambdas. Focused regressions cover both forms.

Add tests covering at least:

## Module-level declarations

1. lambda reads module-level immutable value without `capture`;
2. lambda reads module-level mutable value according to ordinary module access
   rules without `capture`;
3. `capture(moduleValue)` is rejected as a non-local capture;
4. module-level value definition binding remains attached to the module
   declaration inside the lambda.

## Enclosing locals

5. enclosing ordinary local used without capture remains rejected;
6. enclosing function parameter used without capture remains rejected;
7. enclosing function parameter is accepted by plain explicit capture;
8. enclosing loop binding is accepted by capture while in scope;
9. out-of-scope local cannot be captured.

## Non-value declarations

10. named function remains directly usable inside lambda without capture;
11. `capture(namedFunction)` is rejected;
12. visible type remains usable inside lambda type positions without capture;
13. imported non-local declaration follows ordinary import lookup rather than
    capture rules.

## Nested lambdas

14. nested lambda can access module-level declaration without either lambda
    capturing it;
15. nested lambda must explicitly capture an eligible local from an enclosing
    lambda/function when required;
16. capturing an outer lambda capture follows the canonical capture ownership
    rules;
17. module-level access is never converted into closure environment state merely
    because the lambda is nested.

## Diagnostics

18. missing explicit local capture uses the dedicated lambda diagnostic;
19. invalid explicit non-local capture uses a distinct focused diagnostic;
20. genuinely undefined capture remains diagnosed as undefined.
