Generics

Generics allow types and functions to be written once and instantiated with concrete types during compilation.

type Stack[T] struct {
    items: Vec[T],
}

fn Identity[T](value: T) T {
    return value
}

Generic parameters exist only during compilation. Every concrete use becomes an ordinary concrete type or function.

Rule: Generics introduce no runtime type erasure, implicit boxing or runtime generic dispatch.

Generic Parameters

Generic parameters are declared in square brackets after a type or function name:

type Holder[T] struct {
    value: T,
}

type Pair[A, B] struct {
    first: A,
    second: B,
}

fn Convert[From, To](value: From) To {
    return To(value)
}

A generic parameter is a type symbol and may be used anywhere a type reference is allowed inside its declaration.

fn First[T](values: []T) T {
    return values[0]
}

A generic parameter cannot be used as a runtime value:

fn Invalid[T]() void {
    let value := T
}
Invalid: A generic type parameter is a type, not a value.

Parameter names must be unique within the same declaration:

type Invalid[T, T] struct {
}

Generic Arguments

Concrete types are supplied using square brackets:

Stack[int]
Pair[string, int]
Option[User]
Result[Data, IOError]

Generic arguments must be types:

Stack[10]
Stack[value]
Invalid: Runtime values cannot be used as generic type arguments.

The number of arguments must match the generic declaration:

type Pair[A, B] struct {
}

let value: Pair[int]

Generic arguments on non-generic types are invalid:

User[int]
int[string]

Concrete Type Identity

Different generic argument lists produce different concrete types:

Stack[int]
Stack[uint]

Pair[int, string]
Pair[string, int]

Identical instantiations refer to the same concrete type:

Stack[int]
Stack[int]

Named type identity is preserved:

type CustomerID int
type ProductID int

let customers: Stack[CustomerID]
let products: Stack[ProductID]

Stack[CustomerID] and Stack[ProductID] are different types.

Rule: Generic substitution never erases named types, units, enums or other semantic type identity.

Generic Parameter Scope

A generic parameter is visible only inside the declaration that introduces it:

type Container[T] struct {
    value: T,
}

type Other[T] struct {
    value: T,
}

The two parameters named T are different symbols.

type T struct {
}

fn Identity[T](value: T) T {
    return value
}

Inside Identity, T refers to the generic parameter.

Generic Structs

A generic struct is a type template:

type Pair[A, B] struct {
    first: A,
    second: B,
}

A concrete struct type is created when all arguments are supplied:

let pair := Pair[int, string] {
    first: 10,
    second: "ten",
}

Nested generic types are supported:

type Cache[K, V] struct {
    values: Map[K, Option[V]],
}

Size, alignment, copyability and defaultability are calculated for each concrete instantiation.

Generic Unions

type Option[T] union {
    Some(T)
    None
}

type Result[T, E] union {
    Ok(T)
    Err(E)
}

Concrete instantiations substitute the payload types:

Option[int]
Result[string, IOError]
let value: Option[int] := Option.Some(10)
let result: Result[string, IOError] := Result.Ok("ready")

Construction may use the expected target type or payload type to infer concrete arguments when the result is unambiguous.

Generic Functions

fn Identity[T](value: T) T {
    return value
}

Multiple generic parameters are allowed:

fn MakePair[A, B](first: A, second: B) Pair[A, B] {
    return Pair[A, B] {
        first: first,
        second: second,
    }
}

Function generic parameters are visible in parameter types, return types and the function body.

Generic Impl Blocks

type Stack[T] struct {
    items: Vec[T],
}

impl Stack[T] {
    fn Push(value: T) void {
        items.Add(value)
    }

    fn Pop() Option[T] {
        return items.Pop()
    }
}

The parameters in the impl target correspond to the parameters of the generic type.

Additional method-level generic parameters are not part of the initial implementation:

impl Stack[T] {
    fn Map[U](mapper: fn(T) U) Stack[U] {
    }
}

Constraints

Generic constraints use interfaces:

fn Save[T: Serializable](value: T) Result[void, IOError] {
    return value.Serialize()
}

The concrete type used for T must explicitly implement Serializable.

type Serializable interface {
    fn Serialize() bytes
}

type User struct {
}

impl Serializable for User {
    fn Serialize() bytes {
        return EncodeUser(self)
    }
}

Inside generic code, an unconstrained parameter cannot assume that methods or operators exist.

fn Invalid[T](value: T) bytes {
    return value.Serialize()
}
Invalid: Members may only be used when a constraint guarantees that they exist.

The initial constraint model supports one interface constraint per generic parameter.

Inferred Generic Function Calls

fn Identity[T](value: T) T {
    return value
}

let number := Identity(10)
let text := Identity("hello")

The compiler infers T = int and T = string for the two calls.

fn MakePair[A, B](first: A, second: B) Pair[A, B] {
}

let pair := MakePair(10, "ten")

The compiler infers A = int and B = string.

Explicit Generic Function Calls

let value := Identity[int](10)

The explicit argument fixes T before normal argument checking.

Identity[int]("hello")

This is invalid because the argument does not match the selected concrete signature.

Partial explicit argument lists are not supported:

fn Convert[From, To](value: From) To {
}

Convert[int](value)

Nested Inference

fn First[T](values: []T) T {
    return values[0]
}

let names: []string := LoadNames()
let first := First(names)

The compiler recursively matches the slice type and infers T = string.

fn GetOr[T](value: Option[T], fallback: T) T {
}

let result := GetOr(optionalName, "unknown")

All occurrences of the same generic parameter must resolve to one consistent type.

Expected Result Inference

fn Empty[T]() Option[T] {
    return Option.None
}

let value: Option[int] := Empty()

The expected result type supplies T = int.

Expected-result inference may complete information in typed declarations, assignments and returns, but cannot override contradictory argument inference.

Inference Errors

Inconsistent inference

fn Equal[T](left: T, right: T) bool {
    return left == right
}

Equal(10, "ten")

One generic parameter cannot resolve to both int and string.

Insufficient information

fn Empty[T]() Option[T] {
    return Option.None
}

let value := Empty()

Use an explicit argument or a typed expected result.

Wrong arity

Pair[int]
Pair[int, string, bool]

Argument is not a type

Stack[10]

Monomorphization

Sec specializes generic code for each concrete argument list used by the program.

fn Identity[T](value: T) T {
    return value
}

let number := Identity(10)
let text := Identity("hello")

Conceptually, the compiler produces concrete functions equivalent to:

fn Identity_int(value: int) int {
    return value
}

fn Identity_string(value: string) string {
    return value
}

Generated names are internal. Identical instantiations are reused.

Rule: Code generation receives only fully resolved concrete types and functions.

Ownership and Copying

A generic parameter does not automatically imply copyability.

fn Duplicate[T](value: T) Pair[T, T] {
    return Pair[T, T] {
        first: value,
        second: value,
    }
}

This is invalid for a non-copyable concrete T. Generic code follows the normal copy, move, borrow and lifetime rules.

Rule: Generics introduce no hidden copying, cloning, allocation or ownership transfer.

Default Values

An unconstrained generic parameter has no assumed default value:

fn Make[T]() T {
    let mut value: T
    return value
}

This is invalid because T is not known to support default construction.

type Holder[T] struct {
    value: T,
}

Defaultability is calculated for each concrete instantiation.

Recursive Generic Types

Direct recursive storage is invalid:

type Node[T] struct {
    next: Node[T],
}

Recursion must pass through a defined indirection:

type Node[T] struct {
    next: Option[Box[Node[T]]],
}

Changing generic arguments may create non-converging recursion:

type Infinite[T] struct {
    next: Infinite[Option[T]],
}

The compiler rejects instantiation chains that cannot converge to a finite concrete layout.

Current Limitations

  • const generics
  • default generic arguments
  • partial explicit generic argument lists
  • variadic generic parameter lists
  • generic enums
  • generic lifetime parameters
  • higher-kinded types
  • specialization
  • operator constraints
  • multiple constraints on one parameter
  • automatic interface implementation
  • runtime generic dispatch
  • type erasure
  • implicit boxing
  • additional method-level generic parameters

Summary of Rules

  • Generic parameters and arguments use square brackets.
  • Generic parameters are compile-time type symbols.
  • Generic parameters do not exist at runtime.
  • Generic argument order and arity are significant.
  • Generic type arguments must be types.
  • Generic types require all generic arguments.
  • Generic function arguments may be inferred.
  • Explicit generic calls must supply the full argument list.
  • One parameter must infer to one consistent concrete type.
  • Expected result types may complete inference in typed contexts.
  • Different argument lists create different concrete types.
  • Identical instantiations share one canonical concrete identity.
  • Named types, units, enums and unions preserve their identity.
  • Generic structs and unions are specialized after substitution.
  • Generic impl blocks use the parameters of their target type.
  • Interfaces provide compile-time generic constraints.
  • Unconstrained parameters cannot assume methods, arithmetic, equality or defaults.
  • Generics follow normal ownership, copy, move and borrowing rules.
  • Direct recursive generic storage is invalid.
  • Generic code is monomorphized into concrete code.
  • No runtime generic dispatch, hidden boxing or type erasure is introduced.
