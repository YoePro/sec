# MD-143 — Compiler-known build metadata API

**Date:** 2026-11-22  
**Revision:** 1  
**Status:** Decision approved; specification and implementation pending  
**Governance owner:** `tooling.project-version-model`  
**Applies to:** `rules/projects/projects.md`, `rules/library/core-library.md`, `rules/compiler/compiler_known_members.md`

## 1. Decision

Expose the resolved project and target build metadata through one compiler-known type in `core`:

```sec
module core

type BuildInfo struct {
    ProjectUUID: string,
    ProjectName: string,
    TargetName: string,
    VariantName: string,

    VersionMajor: uint64,
    VersionMinor: uint64,
    VersionRevision: uint64,
    VersionBuild: uint64,
    VersionUserDefined: Option[string],
    VersionRendered: string,

    OperatingSystem: string,
    Architecture: string,
    BuildProfile: string,
    TargetProfile: string,

    SourceRevision: Option[string],
    DirtySourceStatus: Option[bool],
}

impl BuildInfo {
    static fn Current() BuildInfo
}
```

The version components use `uint64`, which covers the defined `VersionNumber` range (`0..9223372036854775807`). Identifiers and target descriptors are strings. `BuildProfile` and `TargetProfile` are distinct; a single ambiguous `Profile` field is not provided.

## 2. Access and evaluation

`BuildInfo.Current()` is a pure compiler-known operation. It exposes a single, internally consistent snapshot of the selected `CompilationPlan` and its resolved build metadata.

- It is available to ordinary Sec code and to **semantic compile-time evaluation (CTE)**. Runtime use is statically materialized by the compiler, without runtime environment inspection or implicit runtime allocation.
- It is **not** available to plan-time evaluation that determines the source selection or the `CompilationPlan` on which the value depends; circular dependencies are invalid.
- Values describe the selected target, not the compiler host. No host OS, architecture, profile, time, or environment value is substituted.
- A concrete target and variant are required. If either cannot be resolved, report a diagnostic rather than inventing a default.

## 3. Optional source metadata

`VersionUserDefined`, `SourceRevision`, and `DirtySourceStatus` use `Option` to distinguish absence from a present value. Do not replace missing data with empty strings or `false`.

`SourceRevision` and `DirtySourceStatus` are `None` unless their collection was explicitly requested **and** the corresponding fact is available. Any requested source facts must be resolved before evaluation and supplied as explicit compiler inputs, in accordance with `projects.md` § 33(4). CTE and `Current()` must not inspect Git or the filesystem themselves. This decision introduces no new metadata configuration syntax.

## 4. Build number, reproducibility, and caching

- During `sec build`, `VersionBuild` and `VersionRendered` reflect the resolved build number for that invocation, including an automatic candidate number before its persistence/commit.
- During `sec check` and LSP analysis without an explicit build invocation, they reflect the **stored** build number and the version rendered from it. Analysis neither reserves nor increments the build number.
- The result is reproducible for the same complete `CompilationPlan` and explicit metadata inputs. Different resolved build numbers are different inputs and may deliberately yield different binaries; this does not constitute nondeterminism for a fixed plan.
- Build metadata observable by compiled code participates in the appropriate semantic/code-generation cache identity and invalidation. Cached output must not be reused across incompatible metadata snapshots.

## 5. Specification and implementation scope

Synchronize the API declaration and its contract into `core-library.md` and `compiler_known_members.md`; reference the finalized API from `projects.md` § 32 and maintain its § 33–34 reproducibility/cache requirements. Implement compiler population from the already resolved project/target/version data; do not introduce a new keyword, CTE mechanism, runtime probe, or metadata format.

Acceptance checks must cover the field types, distinct profiles, ordinary-runtime and semantic-CTE use, missing optional facts, absent target/variant diagnostics, cross-compilation target values, `sec build` versus `sec check`/LSP build-number behavior, and cache invalidation when observable metadata changes.

**Resolution:** MD-143 is a specification and implementation task; no further language-design decision is required for this API.
