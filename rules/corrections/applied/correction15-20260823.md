# Correction 15 — static declaration context and receiver/storage semantics are inconsistent with revision 2.0

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/declarations/static.md`
- Document revision: **2.0**
- Created: `2026-08-13`
- Last updated: `2026-08-14`

## Classification

Implementation bugs.

These are not language-rule changes.

Revision 2.0 separates three concepts that the current frontend still partially
conflates:

1. module-level static storage duration;
2. function-local `static` storage;
3. type-associated static members.

The current implementation has three concrete semantic mismatches:

- static impl methods are analyzed with an implicit instance receiver and
  implicit instance-member aliases;
- ordinary module-level bindings are not classified with static storage origin
  unless the redundant `static` keyword is present;
- `static fn` is accepted at module/function statement level even though the
  revision-2.0 source form is a type-associated member declared in `impl`.

The first defect directly contradicts an item currently marked implemented in
the root governance ledger.

# Bug 1 — `static fn` bodies receive implicit `self` and instance members

## Normative requirement

`rules/declarations/static.md` revision 2.0 states:

```text
static fn has no instance receiver and may not use self.
```

Ordinary instance methods are the opposite:

```text
fn        -> implicit self
static fn -> no instance receiver
```

The distinction is semantic, not merely call syntax.

## Affected code

`internal/sema/analyzer.go`

All functions declared inside an `impl`, static or not, are registered with an
implementation target:

```go
if a.currentImplTarget != "" {
    function.ImplTarget = a.currentImplTarget
    if target, ok := a.types[a.currentImplTarget]; ok {
        function.ReceiverMutable =
            a.functionBodyWritesTargetMember(
                fn.Body,
                target,
                functionParameterNames(fn),
            )
    }
}
```

There is no `!fn.Static` guard.

During body analysis, every impl function then executes:

```go
a.defineImplicitImplInstanceSymbols(
    fn.Body,
    function.ReceiverMutable,
)
```

Again there is no static check.

`defineImplicitImplInstanceSymbols()` invokes:

```go
a.defineImplicitImplSelfSymbol(...)
```

and `defineInstanceSymbols()` inserts:

```text
self
all instance fields
register fields
properties
events
```

as implicit symbols.

`analyzeImplBody()` runs both ordinary and static `FunctionDeclaration` bodies
inside `withImplTarget(...)`, so the condition needed for that injection is true
for static methods as well.

## Consequence

A static method can see an instance environment that does not exist.

Conceptually invalid source:

```sec
type Counter struct {
    value: int
}

impl Counter {
    static fn Reset() void {
        self.value = 0
    }
}
```

must receive the revision-2.0 diagnostic that `self` cannot be used in a static
method.

Current Sema instead creates a `self: Counter` symbol before analyzing the body.

The same problem affects unqualified instance members:

```sec
impl Counter {
    static fn Reset() void {
        value = 0
    }
}
```

The static function must not gain an implicit instance field named `value`,
because there is no receiver from which that field could be selected.

## Additional receiver-fact inconsistency

The helper:

```go
func functionUsesReceiver(function Function) bool {
    return function.ImplTarget != ""
}
```

also classifies a static impl function as receiver-using solely because its
owner type is stored in `ImplTarget`.

Ownership of a type-associated member and possession of an instance receiver
are different semantic facts.

The static flag must participate in receiver classification, or the semantic
representation should separate:

```text
OwningType
ReceiverKind
```

rather than overloading `ImplTarget` for both concepts.

## Required correction

For static functions:

- retain the owning type for qualification/coherence;
- do not create implicit `self`;
- do not create implicit instance field/property/event aliases;
- do not infer receiver mutability/consumption;
- do not classify the callable as receiver-using;
- reject explicit or implicit instance-member access unless the source supplies
  an ordinary explicit instance expression permitted by normal rules;
- preserve type-qualified static-member access.

Instance methods must retain their current implicit-self behavior.

# Bug 2 — ordinary module-level bindings are not classified as static storage

## Normative requirement

Revision 2.0 states:

```text
Module-level bindings already have static storage duration.
```

and:

```text
Writing static explicitly at module scope is accepted but semantically
redundant.
```

Therefore these declarations must have the same semantic storage duration:

```sec
let State: int := 1
static let State: int := 1
```

apart from the redundant-source modifier and formatter/informational diagnostic.

## Affected code

`defineSymbol()` creates ordinary symbols using:

```go
Storage: StorageOriginInline,
Local:   a.inFunctionBody,
```

`analyzeLetStatement()` changes the storage origin only when the AST declaration
contains the explicit modifier:

```go
if stmt.Static {
    symbol := a.symbols[stmt.Name.Value]
    symbol.Storage = StorageOriginStatic
    symbol.Local = false
    a.symbols[stmt.Name.Value] = symbol
}
```

Thus an ordinary module-level declaration has:

```text
Local   = false
Storage = StorageOriginInline
```

while the redundant spelling has:

```text
Local   = false
Storage = StorageOriginStatic
```

That makes a semantically redundant keyword change the compiler's storage fact.

## Why this matters

Storage origin feeds or will feed:

- reference-origin facts;
- lifetime reasoning;
- escape analysis;
- static initialization planning;
- destruction planning;
- concurrency analysis;
- Semantic IR;
- backend storage placement.

Some current analyses partly compensate by using `Local == false`, but that does
not make the storage fact correct.

Canonical semantic metadata must not depend on whether the programmer wrote a
redundant keyword.

## Required correction

When defining a binding, Sema must know its declaration context.

At minimum distinguish:

```text
module-level binding         -> Static
function-local ordinary let -> Inline/automatic
function-local static let   -> Static
type-associated static let  -> Static
```

Do not infer module static duration from the textual presence of `static`.

The AST may retain the explicit modifier separately so formatter/LSP can explain
that it was redundant.

# Bug 3 — `static fn` is accepted outside `impl`

## Normative requirement

Revision 2.0 defines `static fn` as a type-level method:

```text
A type-level method is declared explicitly with static fn.
```

Type-associated static members belong in `impl`.

The semantic-analysis section separately requires the compiler to determine:

```text
whether static is valid in the declaration context
```

Module-level storage may redundantly use `static`, but that exception is stated
for module-level **bindings** (`static let`), not for ordinary free functions.

A free module function already belongs to the module; `static fn` does not
define a second function-storage-duration concept.

## Affected code

`internal/parser/parser.go`

The general statement parser accepts `STATIC` and calls:

```go
parseStaticStatement()
```

That helper accepts:

```go
if p.peekToken.Type == lexer.FN {
    ...
    fn.Static = true
    return fn
}
```

with no requirement that parsing is currently inside an `impl`.

The impl parser has a separate valid `static fn` branch, but the generic
statement path means the same syntax is also accepted at top level and wherever
general statements are permitted.

## Sema

`registerFunctionDeclarationBody()` records:

```go
Static: fn.Static
```

but does not reject:

```text
fn.Static == true
AND
currentImplTarget == ""
```

Therefore parser and Sema together fail the revision-2.0 context validation.

## Required correction

Canonical context rules should be explicit:

- module level:
  - `let` valid;
  - redundant `static let` valid;
  - ordinary `fn` valid;
  - `static fn` invalid;
- function/block scope:
  - ordinary local declarations valid as owned elsewhere;
  - `static let` valid;
  - `static fn` invalid;
- impl / impl extends:
  - `static let` valid;
  - `static fn` valid;
  - `static property` valid once implemented.

Prefer a focused parser or Sema diagnostic that explains that `static fn`
belongs in an `impl`.

Do not merely strip `static` and reinterpret it as a normal free function.

# Governance reconciliation

The root entry `frontend.static-declarations-members` currently says:

```text
ordinary impl fn declarations remain instance-bound with compiler-provided
implicit self while static fn bodies receive no self
```

That implemented claim is false at baseline `c515862`.

Replace it with a partial statement until corrected.

The governance entry also says:

```text
static-let symbols are classified with Static storage origin by Sema
```

This is true only for explicitly spelled `static let`.

Add the missing requirement that every module-level binding has static storage
origin even without the redundant keyword.

The current entry does not document top-level/function-level `static fn`
acceptance. Add declaration-context validation as partial/remaining.

Existing remaining items for:

- static properties;
- Type.Name writes and instance-qualified rejection;
- compile-time initializer evaluation;
- initialization dependency cycles;
- generic static specialization;
- concurrency;
- deterministic destruction;
- Semantic IR/lowering;

remain valid and are separate from these corrections.

# Required regression tests

> **Applied 2026-08-23:** Static methods retain their owner type but receive no
> receiver or instance aliases; receiver mutability is not inferred for them.
> Module bindings receive static storage independently of source spelling, and
> `static fn` outside `impl` is rejected by Sema.

## Static methods

1. static method may not reference `self`;
2. static method may not read an instance field by unqualified name;
3. static method may not write an instance field by unqualified name;
4. static method may not access an instance property as an implicit member;
5. static method may access valid type-associated static members;
6. ordinary instance method continues to receive implicit `self`;
7. ordinary instance method continues to receive permitted implicit member
   access;
8. static method semantic callable fact says it has no receiver;
9. static method owner type remains available for qualification/coherence
   without becoming an instance receiver.

## Module-level storage

10. ordinary module-level immutable binding has `StorageOriginStatic`;
11. ordinary module-level mutable binding has `StorageOriginStatic`;
12. redundant `static let` produces the same semantic storage origin;
13. function-local ordinary `let` remains automatic/inline;
14. function-local `static let` has static origin;
15. reference-origin/lifetime facts are identical for module storage with and
    without redundant `static`;
16. formatter may remove module-level `static` without changing semantics.

## Declaration context

17. `static fn` inside an ordinary `impl` is accepted;
18. `static fn` inside valid `impl extends` is accepted;
19. module-level `static fn` is rejected;
20. function-local/block `static fn` is rejected;
21. module-level `static let` remains accepted as redundant;
22. function-local `static let` remains accepted;
23. future `static property` remains restricted to valid impl contexts.
