# Correction 19 — explicit discard of aggregate temporaries does not apply move-only source ownership

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-19`
- Primary rulebook: `rules/control-flow/discard.md`
- Document revision: **2.0**
- Created: `2026-07-31`
- Last updated metadata: `2026-08-16`
- Later synchronization commit: `20b3606` on `2026-08-17`

## Classification

Implementation bug.

This is not a language-rule change.

Revision 2.0 defines `discard expression` as evaluating the expression exactly
once, validating it, consuming the resulting value, and performing ordinary
deterministic destruction. The surrounding discard does not suspend the normal
ownership rules required to construct that result.

Current Sema correctly invalidates a discarded local identifier, but if the
discard operand is a non-identifier expression it returns immediately after
type/discardability validation. It does not apply the ordinary ownership
preparation used when the same aggregate expression is assigned, returned, or
bound.

Consequently move-only source values embedded in a discarded aggregate
temporary can remain incorrectly available after their value was semantically
transferred into the temporary and then destroyed.

---

## Normative requirements

`rules/control-flow/discard.md` revision 2.0 requires:

```text
1. evaluate and resolve the operand;
2. validate explicit discard legality;
3. consume the resulting value or place;
4. execute deterministic destruction;
5. end ownership/borrow responsibility;
6. mark consumed storage unavailable when applicable.
```

It also states for expression-result discard:

> Receiver, argument, ownership, borrow, error, and effect checks are unchanged
> by the surrounding discard.

Therefore construction of:

```sec
discard Holder {
    session: session
}
```

must obey exactly the ownership rules that construction of the same `Holder`
would obey in any other consuming context.

If `session` is move-only and the aggregate temporary takes ownership of that
value, the source cannot remain available merely because the temporary is
immediately discarded.

# Bug — non-identifier discard never applies aggregate ownership transfer

## Affected code

`internal/sema/analyzer.go`

Current explicit discard flow:

```go
valueType, _ := a.inferExpression(stmt.Value)
...
if !isDiscardableType(valueType) {
    ...
    return
}

ident, ok := stmt.Value.(*ast.Identifier)
if !ok {
    return
}
```

Only an identifier operand proceeds to ownership state changes:

```go
a.moved[ident.Value] = ident.Token
a.moveReasons[ident.Value] = "discarded"
...
```

Every non-identifier expression exits before any generic aggregate ownership
preparation is applied.

---

## Existing ownership machinery demonstrates the missing step

Normal let initialization invokes:

```go
a.applyLetOwnership(stmt)
```

which calls:

```go
a.markMoveSource(stmt.Value)
```

for inferred ownership.

`markMoveSource()` already recursively understands:

- struct literals;
- array literals;
- `Ok(...)`;
- `Err(...)`;
- spread expressions;
- conversion expressions.

For example:

```go
case *ast.StructLiteral:
    for _, field := range expr.Fields {
        a.markMoveSource(field.Value)
    }
```

and:

```go
case *ast.ArrayLiteral:
    for _, element := range expr.Elements {
        a.markMoveSource(element)
    }
```

Explicit discard does not invoke this machinery for aggregate temporaries.

---

# Example — discarded struct temporary

```sec
@noCopy
type Session struct {
    id: int
}

type Holder struct {
    session: Session
}

fn Test() void {
    let session := Session { id: 1 }

    discard Holder {
        session: session
    }

    Use(session)
}
```

Semantically:

1. construct a `Holder`;
2. its `session` field receives ownership of the move-only `Session`;
3. discard the completed `Holder`;
4. destroy its owned `Session` field.

The original `session` binding must not remain a second live owner afterward.

Current discard analysis type-checks the struct literal and then returns because
the discard operand is not an identifier. The source binding is not marked
unavailable by the discard path.

The same aggregate expression used as an ordinary let initializer does reach
`markMoveSource()`.

---

# Example — discarded array temporary

The same issue exists for inline arrays containing move-only elements:

```sec
@noCopy
type Session struct {
    id: int
}

fn Test() void {
    let first := Session { id: 1 }
    let second := Session { id: 2 }

    discard [first, second]

    Use(first)
    Use(second)
}
```

If the array construction owns its elements, destruction of the discarded array
also destroys those prepared element values.

The reusable source bindings cannot remain available as though the construction
had copied them.

---

# Important boundary — do not recursively move arbitrary call arguments

The correction must not simply call `markMoveSource()` blindly for every
possible discard expression.

Ordinary function/method call ownership is already resolved according to
parameter modes during call analysis.

For:

```sec
discard ProduceValue(argument)
```

the discard applies to the returned temporary; argument ownership remains the
callee's ordinary call semantics.

Likewise union variant constructors need their own resolved constructor
preparation facts; their missing unnamed move-only payload transfer is already
tracked separately by `correction17.md`.

The correct architecture is to distinguish:

```text
ownership required to evaluate/construct operand result
```

from:

```text
terminal discard of the produced result
```

---

# Required correction

## 1. Preserve resolved operand-preparation ownership facts

Every expression that constructs an owned temporary should expose the ownership
actions required to produce that temporary.

For aggregate literals this includes at least:

- struct field preparation;
- array element preparation;
- wrapper payload preparation;
- union payload preparation through the union-constructor fix;
- spread/copy preparation where applicable.

Explicit discard should consume the prepared result after those ownership
actions have been committed.

## 2. Apply aggregate source invalidation before terminal discard

For a successfully validated aggregate discard:

```text
evaluate/prepare source values
-> commit required moves/copies into temporary
-> construct temporary
-> terminally discard temporary
-> destroy temporary
```

Reusable move-only source places transferred during preparation become
unavailable at the transfer point.

## 3. Preserve explicit discard of a binding

The existing binding rule remains:

```sec
discard value
```

consumes the binding's current value even when it is copyable.

Do not replace this with ordinary `markMoveSource()` logic, because discard of a
copyable binding is intentionally consuming while an ordinary read might copy.

## 4. Preserve ordinary call semantics

Do not treat a call expression as an aggregate move tree.

Call argument ownership must remain determined from the selected callable's
resolved parameter preparation.

Discard only terminates the produced return temporary after that normal call has
completed.

## 5. Integrate deterministic destruction

The eventual Semantic IR should distinguish:

```text
operand preparation ownership actions
DiscardValue(result, Explicit)
```

and attach the resolved destruction plan to the discarded result.

This prevents the backend from reconstructing ownership from syntax.

# Governance reconciliation

The current `frontend.discard-v2` summary and implemented list correctly describe:

- explicit discard expression parsing;
- simple-binding invalidation;
- temporary function/method result discard;
- mutable binding reinitialization;
- reference-holder release.

It already records arbitrary Place support as remaining.

However, aggregate **expression-result ownership preparation** is not the same as
arbitrary Place discard and is not currently documented.

Add it as a separate partial/remaining item.

Also note a positive current-state correction:

Named error bindings are now explicitly discardable in try/match handlers.
Current tests include forms such as:

```sec
Err(error) => { discard error }
```

and pass. The previously observed implementation failure for `discard error`
should therefore not remain listed as current missing work at baseline
`c515862`.

`Err(_)` remains intentionally rejected under the newer try/match rule; that is
not a discard bug.

# Required regression tests

> **Applied 2026-08-23:** Explicit discard now commits represented aggregate
> construction moves for struct, array, wrapper, spread, and conversion
> temporaries while preserving ordinary call argument ownership semantics.
> Semantic IR destruction-plan work remains in governance.

## Aggregate temporary ownership

1. discarded struct temporary with only copyable fields leaves source bindings
   usable;
2. discarded struct temporary containing a move-only source transfers ownership
   and makes that source unavailable;
3. several move-only struct fields are all transferred before destruction;
4. discarded fixed-array temporary of move-only elements transfers every
   reusable source element value;
5. later use of any transferred source is rejected with the transfer/discard
   provenance;
6. borrow conflict prevents required transfer into a discarded aggregate;
7. defer-required source cannot be transferred into a discarded aggregate while
   the deferred use is pending.

## Existing discard behavior

8. discard of a copyable binding still makes the binding unavailable;
9. discard of a move-only binding still consumes it exactly once;
10. discard of an ordinary function result does not move unrelated call
    arguments beyond their normal parameter semantics;
11. explicit discard of a named `Err(error)` handler binding remains valid;
12. bare `discard _` remains invalid;
13. `Err(_)` handling remains governed by the current try/match rule and is not
    made valid by this correction.

## Cross-layer

14. resolved aggregate construction facts precede `DiscardValue`;
15. Semantic IR represents one explicit discard of the completed temporary;
16. destruction lowering does not double-destroy transferred payloads or the
    original source places.
