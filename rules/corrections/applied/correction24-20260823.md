# Correction 24 — switch case execution, fallthrough flow, and enum coverage are not represented canonically

## Audit context

- Repository: `github.com/YoePro/sec`
- Repository baseline: `c515862`
- Audited: `2026-08-20`
- Primary rulebook: `rules/control-flow/flowcontrol_switch.md`
- Document revision: **2.0**
- Created: `2026-08-16`
- Last updated: `2026-08-16`
- Reviewed rulebook baseline: `56be75d`

## Classification

Implementation bugs.

These are not language-rule changes.

Revision 2.0 defines switch as ordered control flow:

- the subject is evaluated exactly once;
- case tests are evaluated lazily in source order;
- comma alternatives stop after the first matching alternative;
- later cases are not evaluated after a match;
- fallthrough transfers the complete runtime state into the next case body
  without evaluating that case's tests;
- complete statically proven subject coverage removes the unmatched path.

Current frontend analysis does not model those rules as one resolved CFG.
Instead it independently:

1. evaluates every case item through live `inferExpression` state;
2. analyzes every case body from essentially the same pre-case state;
3. discards the state of a case ending in `fallthrough`;
4. tracks enum cases by declaration name rather than runtime numeric value class;
5. considers only explicit bool `true`/`false` coverage exhaustive.

This produces multiple concrete semantic errors.

---

# Bug 1 — lazy case expressions commit execution effects eagerly

## Normative requirement

Revision 2.0 states:

> Cases are considered from top to bottom in source order.

> The first matching case body executes.

> After a case matches, later case tests are not evaluated.

and:

> Dynamic case expressions are evaluated only when execution reaches them.

For a subjectless switch, comma-separated conditions additionally have
left-to-right short-circuit semantics.

Therefore static validation of a case expression must not imply that its runtime
effects occur on every switch execution.

## Affected code

`analyzeSwitchStatement()` iterates every case and calls:

```go
a.analyzeSwitchCaseItems(clause, hasSubject, subjectType, tracker)
a.analyzeSwitchFallthrough(clause, i == len(clauses)-1)
branches = append(branches, a.analyzeSwitchCaseBody(clause.Body))
```

`analyzeSwitchCaseItems()` performs live expression inference for every value
item, relational operand, range bound, and subjectless condition.

`inferExpression` is stateful. A case-test call can:

- consume a `->` argument;
- update resource state;
- advance arena generations;
- create borrow/reference facts;
- record call/effect facts.

No switch-case reachability state isolates those runtime effects.

## Example

```sec
@noCopy
type Token struct {
    id: int
}

fn Probe(-> token: Token) int {
    return 42
}

fn Test(value: int) void {
    let token := Token { id: 1 }

    switch value {
    case 0:
        Zero()

    case Probe(token):
        Found()
    }

    Use(token)
}
```

When `value == 0`, runtime semantics never evaluate `Probe(token)`.

Current Sema nevertheless infers the later case expression. If `Probe`
consumes its argument, `token` can be marked consumed on executions where that
call is impossible.

The same defect applies to subjectless cases and comma alternatives.

## Required correction

Switch case tests need path-specific analysis:

```text
subject
  -> case 1 item 1
      match -> body 1
      no    -> item 2 / next case
  -> ...
  -> default/unmatched
```

Source must still be statically type-checked, but runtime ownership/resource/
arena/borrow/effect mutations may only be committed on the path where the test
is actually evaluated.

# Bug 2 — fallthrough source state is discarded instead of entering the destination case

## Normative requirement

Revision 2.0 states:

> `fallthrough` explicitly transfers control from the current case body to the
> body of the immediately following case.

The next case's tests are not evaluated.

The destination body therefore has potentially multiple incoming states:

1. direct selection by its own case tests; and
2. fallthrough from the preceding case.

Those incoming states must be merged before analyzing operations that can run in
the destination body.

## Current implementation

`analyzeSwitchCaseBody()` computes:

```go
hasFallthrough := blockEndsWithFallthrough(block)
...
continues: blockCanFallThrough(block) && !hasFallthrough
```

So a source case ending in fallthrough gets `continues = false`.

Its resulting ownership/assignment/resource state is excluded from the
post-switch continuing merge.

But that state is not routed to the next case either. Each later body is
analyzed after `analyzeSwitchCaseBody()` restores the outer state.

There is no semantic edge:

```text
sourceCase.exitState -> destinationCase.entryState
```

## Observable ownership failure

```sec
@noCopy
type Token struct {
    id: int
}

fn Consume(-> token: Token) void {}

fn Test(value: int) void {
    let token := Token { id: 1 }

    switch value {
    case 1:
        Consume(token)
        fallthrough

    case 2:
        ContinueWork()

    default:
        Other()
    }

    Use(token)
}
```

For `value == 1`, `token` is moved before control reaches case 2 and remains
unavailable after case 2 completes.

Current analysis excludes the source case from the post-switch merge and
analyzes case 2 independently from the restored state, so the move can be lost.

The destination body itself can also be analyzed unsoundly because it does not
merge direct-entry and fallthrough-entry ownership/assignment states.

## Required correction

Build explicit case-body CFG edges:

```text
selected entry
fallthrough entry
normal switch-continuation edge
terminating edge
fallthrough edge to next body
```

A fallthrough source state is not dead. It is continuing control whose target is
the next case body rather than the switch continuation.

# Bug 3 — enum aliases bypass duplicate switch-case detection

## Normative requirements

The switch rulebook says:

> Two compile-time case values that are equal under the subject's equality
> semantics are invalid.

The enum rulebook says numeric aliases with the same numeric representation
belong to the same runtime value class, and equality compares the semantic
numeric enum value.

Therefore:

```sec
enum State int {
    Ready = 1,
    AlsoReady = 1,
    Busy = 2,
}

switch state {
case State.Ready:
    First()

case State.AlsoReady:
    Second()
}
```

contains duplicate switch cases.

## Current implementation

`checkSwitchValueCoverage()` special-cases enum members:

```go
if variant, ok := a.switchEnumCaseVariant(expr, tracker.subjectType); ok {
    tracker.enumValues[variant] = expressionToken(expr)
    return
}
```

`switchEnumCaseVariant()` returns the member **name**:

```go
return member.Property.Value, true
```

There is no duplicate comparison using `EnumConsts[name].Value`.

Thus two aliases with numeric value `1` occupy separate tracker keys.

## Required correction

Normalize enum switch coverage to the semantic numeric value class, as canonical
match coverage already does.

Track at least:

```text
numeric value -> first source member/token
```

and reject a later enum case whose numeric value class is already covered.

# Bug 4 — complete closed-enum coverage does not remove the unmatched path

## Normative requirement

Revision 2.0 says termination can use:

> complete branch coverage, typically through `default` or another statically
> proven complete subject domain.

Ordinary Sec enums are closed over their unique declared numeric runtime value
classes.

Switch is not required to be exhaustive, but if every possible closed-enum
runtime value is covered, there is no unmatched continuation path.

## Current implementation

`switchCoverageTracker.isExhaustive()` is:

```go
func (t *switchCoverageTracker) isExhaustive() bool {
    return t != nil &&
        t.subjectType.Kind == BoolType &&
        len(t.boolValues) == 2
}
```

Only bool coverage is recognized.

Without `default`, a fully covered closed-enum switch therefore still receives
a synthetic unmatched continuing branch.

The independent `switchDefinitelyReturns()` helper has the same limitation:
without `default`, only literal bool `true` + `false` is recognized as complete.

Consequences include false results in:

- definite assignment;
- termination analysis;
- function return-path analysis;
- unreachable-code reasoning.

## Required correction

For a closed ordinary enum:

```text
covered unique numeric value classes
==
declared unique numeric value classes
```

proves complete switch coverage.

For an open bit-backed enum, declared names alone do not prove coverage of the
complete bit domain.

# Architectural correction

These bugs share one cause: switch semantics are reconstructed in several
independent mechanisms rather than represented by one resolved CFG.

Sema should produce a canonical switch plan containing at least:

```text
resolved subject
ordered case-test nodes
resolved comparison/range operation
case-test execution edges
case body entry nodes
fallthrough edges
normal continuation edges
terminating edges
normalized compile-time coverage classes
unmatched-path existence
per-edge ownership/assignment/resource/borrow state
```

Later consumers should use the same plan for:

- definite assignment;
- ownership/move merging;
- resource lifecycle;
- arena generations;
- borrow/reference provenance;
- termination and return analysis;
- call/effect reachability;
- Semantic IR;
- LLVM/MLIR lowering;
- diagnostics and LSP.

# Governance reconciliation

The current `frontend.switch-statements-v2` entry marks as implemented:

```text
independent case scopes and definite-assignment merging over continuing paths
```

```text
switch termination analysis including explicit fallthrough chains
```

```text
exactly-once subject evaluation and ordered lazy case evaluation
```

Those claims are too broad at baseline `c515862`.

More precise current state:

- subject inference is once;
- source order is preserved syntactically;
- backend subsets lower cases lazily;
- frontend runtime effects from case tests are eager;
- fallthrough source state is not propagated into the destination body;
- enum duplicate/coverage identity is member-name based;
- complete closed-enum coverage does not eliminate unmatched flow.

Existing remaining work for loop-control boundary tests, dedicated switch syntax
diagnostics, cleanup/destruction edges, broader MLIR lowering, unit-aware
coverage, formatter/LSP, and end-to-end coverage remains valid.

# Required regression tests

## Lazy case evaluation

1. later dynamic case call is not committed when an earlier case matches;
2. consuming argument in a skipped case expression does not move its source;
3. skipped case expression does not close a resource;
4. skipped case expression does not advance arena generation;
5. skipped case expression does not register a reachable call/effect;
6. subjectless later case condition has the same behavior;
7. subjectless comma alternatives short-circuit;
8. value-case comma alternatives preserve conditional left-to-right evaluation.

## Fallthrough flow

9. move in source case remains moved after fallthrough destination completes;
10. destination body merges direct and fallthrough ownership states;
11. assignment in source case reaches destination through fallthrough;
12. direct destination entry does not inherit assignment existing only on
    fallthrough;
13. resource, arena, borrow and reference-origin state propagates across
    fallthrough;
14. multi-case fallthrough chains preserve state;
15. destination case tests are not evaluated on a fallthrough edge.

## Enum aliases and coverage

16. enum aliases with the same numeric value are duplicate switch cases;
17. alias diagnostic identifies the earlier equivalent case;
18. incomplete-enum warning reasons by unique runtime value classes rather than
    alias spellings;
19. closed enum covering every unique value class has no unmatched path;
20. all-terminating complete closed-enum switch satisfies function return
    analysis;
21. complete closed-enum switch participates correctly in definite assignment;
22. open bit-backed named members alone do not prove exhaustive coverage.

## Cross-layer

23. one resolved switch plan drives frontend flow and Semantic IR;
24. maintained backends consume the same case/fallthrough edges;
25. optimization occurs only after canonical source-order semantics are resolved.

## Applied 2026-08-23

Switch analysis now preserves direct case-test state separately from body state,
propagates complete fallthrough state into the next body without evaluating its
tests, normalizes closed-enum cases by numeric value class, and uses complete
closed-enum coverage in return flow. A durable cross-layer `ResolvedSwitchPlan`
and fully split comma-alternative CFG remain tracked in
`implementation-status.yaml`.
